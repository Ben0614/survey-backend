# 第一段 ① 分頁

## 核心概念

### query string 永遠是字串

這是整章的地基。`?page=2` 進到程式裡是 `'2'`，`?page=abc` 是 `'abc'`，`?page=` 是 `''` —— 網址本身就是一段文字，裡面**沒有「數字」這種東西**。

而 `setup-app.ts` 的 `transform: true` 常被誤解成「會自動依型別轉」。它做的事情是**把收到的 plain object 變成 DTO class 的實例**，不是依型別註記轉型。兩者是不同的事。

要轉型有兩條路：

| 做法 | 性質 |
| --- | --- |
| `@Type(() => Number)` | 逐欄位明講，看檔案就知道會發生什麼事 |
| `transformOptions: { enableImplicitConversion: true }` | 全域，依 TypeScript 型別註記自動猜 |

**選了 `@Type()`**，理由在「決策取捨」。

### 兩階段：轉型在驗證之前

```
'2' ──> class-transformer 建實例 + @Type 轉型 ──> 2 ──> class-validator 跑規則 ──> 過
        └────────── 第一階段 ──────────┘              └──── 第二階段 ────┘
```

**裝飾器寫的上下順序不影響這件事** —— 它們登記在兩個不同階段，不是「由上往下執行的四行程式碼」。

這一點有一個很漂亮的實證：`?page=abc` 回的是**兩則**錯誤訊息。

```json
{"message":["page must not be less than 1","page must be an integer number"]}
```

因為 `@Type` 先把 `'abc'` 轉成 `NaN`，而 `NaN` 對 `@IsInt` 和 `@Min(1)` 兩條規則都不過。如果 `@Type` 沒跑過，訊息會只有 `@IsInt` 那一則（字串不是整數，但字串也不會觸發 `@Min` 的數值比較）。

### `@Query()` 的括號有沒有東西，差別很大

```ts
@Query('page') page: number          // 只取這一個 key，拿到 primitive
@Query() query: FindSurveysQueryDto  // 整包接成 DTO
```

**只有下面那種會被驗證。** ValidationPipe 拿到參數時先看它的型別，`String` / `Boolean` / `Number` / `Array` / `Object` 這五個一律直接放行 —— 因為**驗證規則是掛在 class 的屬性上的**，沒有 class 就沒有屬性，也就沒有規則可查。

這跟 `@Body()` 是同一套機制（`emitDecoratorMetadata`），`@Body('title') title: string` 一樣不會被驗證。

### `skip` / `take` 是 `OFFSET` / `LIMIT`

| Prisma | SQL | 意思 |
| --- | --- | --- |
| `take: 10` | `LIMIT 10` | 最多給我 10 筆 |
| `skip: 20` | `OFFSET 20` | 前 20 筆不要 |

執行順序是**先 `ORDER BY` 排好 → 再 `OFFSET` 跳過 → 再 `LIMIT` 取**。

換算是 `skip = (page - 1) * pageSize`。寫成 `skip: page` 是很自然的誤解，而且**第 1 頁看不出來**（兩種寫法都是 0），要翻到第 2 頁才現形。

### `orderBy` 從「好習慣」升級成「必要條件」

Ch1 就寫過「表是集合、列沒有固有順序」。在 Ch2 那還只是個好習慣；加了分頁之後它變成**正確性的前提**：

順序不固定的話，第 1 頁和第 2 頁可能是資料庫用兩種不同順序排出來的，同一筆資料會在兩頁都出現、另一筆一頁都不出現。**沒有穩定排序的分頁是壞的。**

### 交易的第二個能力

`$transaction` 的語法與觀念寫在 [`docs/關聯式資料庫基礎.md`](../關聯式資料庫基礎.md) 第 7 節（那是跨章節的資料庫基礎，Ch5 還要再用）。這裡只記這一章用到的那一面：

兩句都是 SELECT、不可能「做一半」，所以用的**不是原子性，是一致的讀取視角** —— 讓 `data` 與 `total` 來自同一個瞬間，不會出現「data 來自 47 筆的世界、total 說 48」。

最容易寫錯的一點：**陣列裡那兩句不能加 `await`**。Prisma 的查詢方法回傳的是「還沒送出的查詢」，先各自 `await` 再丟進 `$transaction`，它收到的就是「結果」而不是「查詢」。

### `count()` 不帶 `skip` / `take`

它要數的是**符合條件的全部**，不是這一頁。跟著分頁一起切的話 `total` 會永遠等於 `pageSize`，分頁變成自己證明自己。

## 決策取捨

### 回應形狀：`{ data, meta }` 而不是裸陣列

```json
{
  "data": [ ... ],
  "meta": { "page": 1, "pageSize": 10, "total": 47, "totalPages": 5 }
}
```

對照組是「body 仍是陣列、總筆數放 `X-Total-Count` 標頭」。

選 `{ data, meta }` 的理由：前端要畫頁碼就需要總數與頁數，放在 body 裡一次拿到；而且 **Ch7 的 Swagger 描述得出 body 的形狀，描述標頭則麻煩得多**。

代價是**這是一個 breaking change** —— 兩條既有 E2E 立刻紅。這件事本身就是這一段最好的教材（見「踩到的坑」第 2 條）。

### `@Type()` 而不是全域 `enableImplicitConversion`

隱式轉型是「依 TypeScript 的型別註記猜」，規則要另外記，而且對 boolean 特別容易出錯（`?flag=false` 會怎樣？③ 會實測）。`@Type()` 是逐欄位明講，讀檔案就知道會發生什麼事。

代價是每個數字欄位都要多寫一行。這個專案的 query 參數不多，划算。

### `page` / `pageSize` 而不是 `skip` / `take`

前端的心智模型是「第幾頁」，不是「跳過幾筆」。中間隔一層換算的好處是 **API 契約與 ORM 參數解耦** —— 哪天換掉 Prisma，前端不必改網址。

代價就是那一行換算，以及它是錯誤的溫床（見上）。

### `@Max(100)` 是功能，不是保守

沒有上限的話 `?pageSize=999999` 等於把分頁整個繞過去：資料庫撈 99 萬列、Node 全部組成物件、序列化成幾百 MB 的 JSON。這是公開端點，任何人都能打。

常見的誤解是「資料量大就該把上限開大」。不對 —— **`pageSize` 是「一頁幾筆」，資料量是靠頁數變多承載的**。100 萬筆配 `pageSize=100` 就是 1 萬頁，完全正常。真的需要一次拿全部（匯出 CSV），那是另一支端點的事（串流或背景任務）。

### `total = 0` 時 `totalPages` 是 0，不是 1

`page: 1, totalPages: 0` 乍看矛盾，其實不是 —— 那兩個欄位回答的是**不同問題**：

| 欄位 | 回答什麼 |
| --- | --- |
| `page` | 「**你要求的是**第幾頁」（query 參數的回音，跟資料量無關） |
| `totalPages` | 「**資料總共有**幾頁」 |

最有力的說法：你覺得怪的其實不是空資料庫，而是「請求的頁碼超出範圍」，而它在資料非空時天天發生 —— 3 筆資料打 `?page=99` 會得到 `page: 99, totalPages: 1, data: []`，沒人覺得矛盾。**空資料庫只是這個一般情況的極端值。**

選 1 的話反而製造真矛盾：宣稱有 1 頁，`data` 卻是空的，前端會畫出一個點下去沒東西的按鈕。而且 `Math.ceil(0 / 10)` 本來就是 0，選 1 得多寫 `Math.max(1, ...)` —— **多出來的那一行本身就是在提醒你這是特例**。

如果前端元件不吃 `totalPages: 0`，那是前端一行 `Math.max(1, totalPages)` 的事。**別為了 UI 元件在 API 裡藏特例** —— 後端藏的特例前端看不見，前端遲早再藏一層，兩層打架時沒人查得出來。

### 這一章不寫單元測試

`(page - 1) * pageSize` 與 `Math.ceil(total / pageSize)` 看起來「純、無依賴」，很像單元測試的料。但判準是「**拿掉外部依賴之後還剩什麼判斷邏輯**」——這兩行是機械算術，不是商業規則，而且 E2E 一定會覆蓋到。

所以 `survey.rules.ts` **不新增規則**，第三條仍然留給 Ch5 的「只有 `PUBLISHED` 的問卷能被填答」。

「什麼時候**不**寫單元測試」跟「什麼時候要寫」一樣重要 —— Ch3 立的判準，這一章是它的反例。

### 不實作 cursor 分頁

課綱要求對比 `skip/take` 與 cursor，但只做到「講解 + 實測 offset 的 SQL」，不留 cursor 端點。

理由：這個專案是**後台管理介面**，需要跳頁（「第 5 頁」），資料量也不大 —— offset 是正確的選擇。同一支 API 塞兩種分頁只會增加 cursor 編碼、與 `page` 參數共存的取捨，換不到任何實際好處。

## 踩到的坑

### 1. DTO 寫了，但從頭到尾沒有被用到

第一版的 controller 是：

```ts
findAll(@Query('page') page: number, @Query('pageSize') pageSize: number)
```

`FindSurveysQueryDto` 一次都沒被 import。**一個決定推倒四件事**：驗證沒生效、`whitelist` 沒生效、預設值沒地方放、`page: number` 這個型別註記在執行期根本不存在。

實測七種網址（`pnpm start` 之後用 `api.http` 或 curl）：

| 網址 | 接上 DTO 之前 | 之後 |
| --- | --- | --- |
| `/surveys` | 200，全部 | 200，第 1 頁 |
| `?page=2&pageSize=1` | 200 → 問卷**1** ❌ | 200 → 問卷**2** ✅ |
| `?page=abc` | **500** | 400 |
| `?page=2.5&pageSize=1` | 200（悄悄當成 2） | 400 |
| `?page=-1` | **500** | 400 |
| `?pageSize=999999` | 200，全撈 | 400 |
| `?evil=1` | 200（沒人取它） | 200（被 whitelist 丟掉） |

**七種輸入有兩種直接把伺服器打成 500。**

這是 Ch3 坑 #3（`whitelist` 只認驗證裝飾器、不認 TypeScript 的型別宣告）的第二次現場。

> **同時：`pnpm test:e2e` 是 20 passed 全綠。** 因為那 20 條沒有任何一條帶 query 參數。
> 判準：**「既有測試全綠」只證明你沒弄壞舊行為，完全不證明新功能是對的。**
> 這跟前面幾章的「假綠」不同 —— 那些是測試寫錯，這次是測試**還不存在**。

### 2. 改回應形狀就是 breaking change

`findAll` 改回 `{ data, meta }` 之後，兩條既有測試立刻紅：

```
● 沒有任何問卷時回空陣列
  Expected: []
  Received: {"data": [], "meta": {...}}

● 回傳所有問卷，最新的在前面
  TypeError: received value must have a length property
```

這次只有兩條在喊，真實專案是**所有接了這支 API 的前端頁面**。Ch7 的 Swagger 之所以有價值，就是讓這種改動能被前端事先看見。

### 3. 改了共用型別的「意思」，炸掉六個無關的地方

修測試時把 `SurveyBody` 從「一份問卷」直接改成「列表回應」，然後把每個使用處機械地加上 `.data[0]`。結果從 2 條紅變成 **8 條紅**。

`SurveyBody` 有七個使用者，**只有一個是列表**：

| 端點 | 回的是 |
| --- | --- |
| `POST /surveys` ×2 | 一份問卷 |
| `GET /surveys` | ← 只有這個是列表 |
| `PATCH /surveys/:id` ×2 | 一份問卷 |
| `PATCH /:id/publish` `/unpublish` | 一份問卷 |

`POST /surveys` 的回應**一個字都沒變**，卻被改成 `.data[0].status` → `undefined[0]` → `TypeError`。

正解是**新增** `SurveyBodyList`，不是改寫 `SurveyBody`。判準跟 Ch3 的 `assertExists` 同一條：**改了一個東西的形狀，先回頭問「誰在用它、用來做什麼」。**

> **那六處 `tsc` 全是綠的。** `res.body` 是 `any`，`as SurveyBody` 是型別**斷言** ——
> 意思是「相信我」，不是「檢查一下」。**`as` 關掉的是檢查，不是風險。**

### 4. `totalPages` 少了 `Math.ceil`

```ts
totalPages: total / take,   // 7 / 2 = 3.5
```

實測 `?pageSize=10` 時 `totalPages` 是 **0.7** —— 7 筆資料明明就是 1 頁。前端拿去畫 `for (i = 1; i <= 0.7; i++)` 會一個按鈕都不畫，使用者看不到任何資料（即使資料就在 `data` 裡）。

**`tsc` 與 `lint` 都不會抗議**：number 除以 number 就是 number，3.5 是完全合法的值。只有把實際數字看一眼才抓得到。跟 Ch3 的「查錯欄位」同一族 —— 型別對、語法對、語義錯。

### 5. 測試寫了，但沒蓋到那個剛修好的 bug

補完四條分頁測試、24 passed 之後，`totalPages` 的斷言只出現在**一條**測試裡，而那條的 `total` 是 0 —— 但 `0 / 10` 和 `Math.ceil(0 / 10)` **都是 0**，兩種寫法在那條測試上完全無法區分。

也就是說：**把坑 #4 的 bug 放回去，24 條測試依然全綠。**

判準：**想知道一條測試有沒有價值，就把它該抓的 bug 放回去跑一次。** 這跟 `ch03` 作業第 1 題是同一個手法。

### 6. 測試名稱重複，而且其中一條的名字是錯的

兩條測試都叫 `it('不帶參數')`，而第二條打的是 `?page=0` 驗 400 —— 它**帶了參數**。

Jest 失敗時只印測試名稱，兩條同名就分不出是哪一條壞了，診斷價值歸零。這是「貼上測試時沒核對名字跟內容」的第五次，只是這次錯在名字而不是動詞。

**測試名稱要說「驗什麼」，不是「測哪個功能」** —— `分頁` / `分頁2` 這種名字失敗時給不出任何線索。

### 7. 教練問了一個 log 答不出來的問題

實驗要求「確認 `LIMIT` / `OFFSET` 的數字跟 `skip` 換算對得上」，但 log 印出來是：

```sql
... ORDER BY "createdAt" DESC LIMIT $1 OFFSET $2
```

`$1` / `$2` 是**佔位符，不是值**。`prisma.service.ts` 用的 `log: ['query']` 只印 SQL 文字；要看到參數得改成事件形式（`{ emit: 'event', level: 'query' }` 配 `$on('query', e => ...)`，`e.params` 才有值）。

**但這個「缺陷」本身是重點**：SQL 和參數是分開送到資料庫的（參數化查詢 / prepared statement），值永遠不會被當成 SQL 解析 —— 這就是為什麼用 Prisma 寫查詢不會有 SQL injection。② 寫關鍵字搜尋時會再碰到。

## ① 的 SQL 觀察

`PRISMA_LOG_QUERIES=1 pnpm start:dev`（PowerShell 是 `$env:PRISMA_LOG_QUERIES=1; pnpm start:dev`），然後打 `GET /surveys?page=3&pageSize=2`：

```sql
BEGIN
SELECT "id","title","status"::text,"createdAt","updatedAt" FROM "Survey"
  WHERE 1=1 ORDER BY "createdAt" DESC LIMIT $1 OFFSET $2
SELECT COUNT(*) AS "_count$_all" FROM (SELECT "id" FROM "Survey" WHERE 1=1 OFFSET $1) AS "sub"
COMMIT
```

四件事：

1. **`BEGIN` / `COMMIT` 包住兩句** —— `$transaction` 真的生效了。（沒有 `BEGIN` 就 `COMMIT`，PostgreSQL 會直接報錯，所以看到 `COMMIT` 就代表 `BEGIN` 一定在。）
2. **`COUNT(*)` 那句沒有 `LIMIT`** —— 對的，理由見「核心概念」。
3. **但它有 `OFFSET $1`**，而且包了一層只選 `id` 的子查詢。程式碼裡 `count()` 完全沒帶參數，所以那個值只可能是 0，不影響結果 —— 這是 Prisma 產生 count 的固定模板。
   **判準：看到不認識的東西，先問「它會不會改變結果」。**
   （注意這是**推論**不是觀測 —— 看不到值，見坑 #7。）
4. **`WHERE 1=1`** 是「沒有任何篩選條件」的佔位符。② 加上 `status` 與 `q` 之後這裡會長出真正的條件，到時候回來對照。

再打一個 `PATCH /surveys/:id`（或任何借 `assertExists` 丟 404 的端點）：

```sql
SELECT "id","status"::text FROM "Survey" WHERE ("id" = $1 AND 1=1) LIMIT $2 OFFSET $3
```

兩個觀察：

- **只撈 `id` 和 `status` 是 `assertExists` 的指紋**（`select: { id: true, status: true }`）。`findOne` 會撈全部欄位，而且後面一定跟著第二句撈 questions。**從 SQL 的形狀反推是哪一支方法在跑** —— 這正是 Ch3 第二段量出「同一批題目撈兩次」用的方法。
- **`findUnique` 也帶 `LIMIT` / `OFFSET`**，而它根本沒有分頁。所以**「看到 LIMIT 就是分頁」是錯的推論** —— Prisma 幾乎每句 SELECT 都帶。分頁的證據不是「有沒有 `LIMIT`」，是「那個值是不是你的 `take`」。

> 另外：帶參數與不帶參數的兩次 `GET /surveys`，**SQL 文字一模一樣**，差別完全在參數裡。這也解釋了為什麼裸打 `/surveys` 的**輸出**跟加分頁之前一樣（3 筆資料裝得進第 1 頁），但**行為**完全不同 —— 以前的 log 裡沒有 `LIMIT` / `OFFSET`。**輸出一樣 ≠ 行為一樣。**

## offset vs cursor

現在的實作是 **offset 分頁**：直覺、能跳頁、實作簡單。它有兩個問題是**機制決定的、改程式碼解不掉**：

**一、頁碼越後面越慢。** `OFFSET 100000` 不是「直接跳到第 100001 筆」——資料庫必須真的把前 10 萬列讀出來、排好序、然後丟掉。第 1 頁和第 10000 頁的成本差好幾個數量級。

**二、翻頁期間資料變動會漏看或重複。** 按 `createdAt DESC` 排，看完第 1 頁之後有人新增一筆，所有東西往後推一格，第 2 頁（`OFFSET 10`）的第一筆就是你剛才看過的那筆。刪除則相反 —— 有一筆完全沒被看到就跳過去了。

**`$transaction` 救不了第二個問題**：它只保證同一次請求裡的兩句 SQL 看到同一個瞬間，但第 1 頁和第 2 頁是**兩次獨立的請求**，中間隔了使用者思考的幾秒鐘。

cursor 的作法是不說「跳過 N 筆」，而是「**從這個位置之後開始**」：

```sql
-- offset
ORDER BY "createdAt" DESC LIMIT 10 OFFSET 10

-- cursor
WHERE "createdAt" < $1          -- $1 = 上一頁最後一筆的 createdAt
ORDER BY "createdAt" DESC LIMIT 10
```

兩個問題同時消失：`createdAt` 有索引的話資料庫直接定位，第 1 頁和第 10000 頁一樣快；判準是「值」而不是「位置」，中間插入幾筆都不影響「比這個時間更早的下一批是誰」。

代價：

- **不能跳頁。** cursor 只知道「上一批的結尾」，所以只能一直「下一頁」。這就是為什麼社群軟體是無限捲動、後台管理介面是頁碼。
- **cursor 欄位必須唯一且穩定。** `createdAt` 是 `TIMESTAMP(3)`，同毫秒建立的兩筆會相等（`surveys.e2e-spec.ts` 的測試註解早就寫過這個坑），`<` 就會跳過其中一筆。實務上要用 `(createdAt, id)` 組合。

**判準**：能跳頁、資料量不大、後台管理 → offset。無限捲動、資料量大 → cursor。這個專案兩個條件都指向 offset。
