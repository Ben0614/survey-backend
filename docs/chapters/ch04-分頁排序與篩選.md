# 第一段 ① 分頁

## 核心概念

### query string 永遠是字串

這是整章的地基。`?page=2` 進到程式裡是 `'2'`，`?page=abc` 是 `'abc'`，`?page=` 是 `''` —— 網址本身就是一段文字，裡面**沒有「數字」這種東西**。

而 `setup-app.ts` 的 `transform: true` 常被誤解成「會自動依型別轉」。它做的事情是**把收到的 plain object 變成 DTO class 的實例**，不是依型別註記轉型。兩者是不同的事。

要轉型有兩條路：

| 做法 | 性質 |
| --- | --- |
| `@Type(() => Number)` | 逐欄位明講，看檔案就知道會發生什麼事 |
| `transformOptions: { enableImplicitConversion: true }` | 全域，依 TypeScript 型別註記自動猜 |

**選了 `@Type()`**，理由在「決策取捨」。

### 兩階段：轉型在驗證之前

```
'2' ──> class-transformer 建實例 + @Type 轉型 ──> 2 ──> class-validator 跑規則 ──> 過
        └────────── 第一階段 ──────────┘              └──── 第二階段 ────┘
```

**裝飾器寫的上下順序不影響這件事** —— 它們登記在兩個不同階段，不是「由上往下執行的四行程式碼」。

這一點有一個很漂亮的實證：`?page=abc` 回的是**兩則**錯誤訊息。

```json
{"message":["page must not be less than 1","page must be an integer number"]}
```

因為 `@Type` 先把 `'abc'` 轉成 `NaN`，而 `NaN` 對 `@IsInt` 和 `@Min(1)` 兩條規則都不過。如果 `@Type` 沒跑過，訊息會只有 `@IsInt` 那一則（字串不是整數，但字串也不會觸發 `@Min` 的數值比較）。

### `@Query()` 的括號有沒有東西，差別很大

```ts
@Query('page') page: number          // 只取這一個 key，拿到 primitive
@Query() query: FindSurveysQueryDto  // 整包接成 DTO
```

**只有下面那種會被驗證。** ValidationPipe 拿到參數時先看它的型別，`String` / `Boolean` / `Number` / `Array` / `Object` 這五個一律直接放行 —— 因為**驗證規則是掛在 class 的屬性上的**，沒有 class 就沒有屬性，也就沒有規則可查。

這跟 `@Body()` 是同一套機制（`emitDecoratorMetadata`），`@Body('title') title: string` 一樣不會被驗證。

### `skip` / `take` 是 `OFFSET` / `LIMIT`

| Prisma | SQL | 意思 |
| --- | --- | --- |
| `take: 10` | `LIMIT 10` | 最多給我 10 筆 |
| `skip: 20` | `OFFSET 20` | 前 20 筆不要 |

執行順序是**先 `ORDER BY` 排好 → 再 `OFFSET` 跳過 → 再 `LIMIT` 取**。

換算是 `skip = (page - 1) * pageSize`。寫成 `skip: page` 是很自然的誤解，而且**第 1 頁看不出來**（兩種寫法都是 0），要翻到第 2 頁才現形。

### `orderBy` 從「好習慣」升級成「必要條件」

Ch1 就寫過「表是集合、列沒有固有順序」。在 Ch2 那還只是個好習慣；加了分頁之後它變成**正確性的前提**：

順序不固定的話，第 1 頁和第 2 頁可能是資料庫用兩種不同順序排出來的，同一筆資料會在兩頁都出現、另一筆一頁都不出現。**沒有穩定排序的分頁是壞的。**

### 交易的第二個能力

`$transaction` 的語法與觀念寫在 [`docs/關聯式資料庫基礎.md`](../關聯式資料庫基礎.md) 第 7 節（那是跨章節的資料庫基礎，Ch5 還要再用）。這裡只記這一章用到的那一面：

兩句都是 SELECT、不可能「做一半」，所以用的**不是原子性，是一致的讀取視角** —— 讓 `data` 與 `total` 來自同一個瞬間，不會出現「data 來自 47 筆的世界、total 說 48」。

最容易寫錯的一點：**陣列裡那兩句不能加 `await`**。Prisma 的查詢方法回傳的是「還沒送出的查詢」，先各自 `await` 再丟進 `$transaction`，它收到的就是「結果」而不是「查詢」。

### `count()` 不帶 `skip` / `take`

它要數的是**符合條件的全部**，不是這一頁。跟著分頁一起切的話 `total` 會永遠等於 `pageSize`，分頁變成自己證明自己。

## 決策取捨

### 回應形狀：`{ data, meta }` 而不是裸陣列

```json
{
  "data": [ ... ],
  "meta": { "page": 1, "pageSize": 10, "total": 47, "totalPages": 5 }
}
```

對照組是「body 仍是陣列、總筆數放 `X-Total-Count` 標頭」。

選 `{ data, meta }` 的理由：前端要畫頁碼就需要總數與頁數，放在 body 裡一次拿到；而且 **Ch7 的 Swagger 描述得出 body 的形狀，描述標頭則麻煩得多**。

代價是**這是一個 breaking change** —— 兩條既有 E2E 立刻紅。這件事本身就是這一段最好的教材（見「踩到的坑」第 2 條）。

### `@Type()` 而不是全域 `enableImplicitConversion`

隱式轉型是「依 TypeScript 的型別註記猜」，規則要另外記，而且對 boolean 特別容易出錯（`?flag=false` 會怎樣？③ 會實測）。`@Type()` 是逐欄位明講，讀檔案就知道會發生什麼事。

代價是每個數字欄位都要多寫一行。這個專案的 query 參數不多，划算。

### `page` / `pageSize` 而不是 `skip` / `take`

前端的心智模型是「第幾頁」，不是「跳過幾筆」。中間隔一層換算的好處是 **API 契約與 ORM 參數解耦** —— 哪天換掉 Prisma，前端不必改網址。

代價就是那一行換算，以及它是錯誤的溫床（見上）。

### `@Max(100)` 是功能，不是保守

沒有上限的話 `?pageSize=999999` 等於把分頁整個繞過去：資料庫撈 99 萬列、Node 全部組成物件、序列化成幾百 MB 的 JSON。這是公開端點，任何人都能打。

常見的誤解是「資料量大就該把上限開大」。不對 —— **`pageSize` 是「一頁幾筆」，資料量是靠頁數變多承載的**。100 萬筆配 `pageSize=100` 就是 1 萬頁，完全正常。真的需要一次拿全部（匯出 CSV），那是另一支端點的事（串流或背景任務）。

### `total = 0` 時 `totalPages` 是 0，不是 1

`page: 1, totalPages: 0` 乍看矛盾，其實不是 —— 那兩個欄位回答的是**不同問題**：

| 欄位 | 回答什麼 |
| --- | --- |
| `page` | 「**你要求的是**第幾頁」（query 參數的回音，跟資料量無關） |
| `totalPages` | 「**資料總共有**幾頁」 |

最有力的說法：你覺得怪的其實不是空資料庫，而是「請求的頁碼超出範圍」，而它在資料非空時天天發生 —— 3 筆資料打 `?page=99` 會得到 `page: 99, totalPages: 1, data: []`，沒人覺得矛盾。**空資料庫只是這個一般情況的極端值。**

選 1 的話反而製造真矛盾：宣稱有 1 頁，`data` 卻是空的，前端會畫出一個點下去沒東西的按鈕。而且 `Math.ceil(0 / 10)` 本來就是 0，選 1 得多寫 `Math.max(1, ...)` —— **多出來的那一行本身就是在提醒你這是特例**。

如果前端元件不吃 `totalPages: 0`，那是前端一行 `Math.max(1, totalPages)` 的事。**別為了 UI 元件在 API 裡藏特例** —— 後端藏的特例前端看不見，前端遲早再藏一層，兩層打架時沒人查得出來。

### 這一章不寫單元測試

`(page - 1) * pageSize` 與 `Math.ceil(total / pageSize)` 看起來「純、無依賴」，很像單元測試的料。但判準是「**拿掉外部依賴之後還剩什麼判斷邏輯**」——這兩行是機械算術，不是商業規則，而且 E2E 一定會覆蓋到。

所以 `survey.rules.ts` **不新增規則**，第三條仍然留給 Ch5 的「只有 `PUBLISHED` 的問卷能被填答」。

「什麼時候**不**寫單元測試」跟「什麼時候要寫」一樣重要 —— Ch3 立的判準，這一章是它的反例。

### 不實作 cursor 分頁

課綱要求對比 `skip/take` 與 cursor，但只做到「講解 + 實測 offset 的 SQL」，不留 cursor 端點。

理由：這個專案是**後台管理介面**，需要跳頁（「第 5 頁」），資料量也不大 —— offset 是正確的選擇。同一支 API 塞兩種分頁只會增加 cursor 編碼、與 `page` 參數共存的取捨，換不到任何實際好處。

## 踩到的坑

### 1. DTO 寫了，但從頭到尾沒有被用到

第一版的 controller 是：

```ts
findAll(@Query('page') page: number, @Query('pageSize') pageSize: number)
```

`FindSurveysQueryDto` 一次都沒被 import。**一個決定推倒四件事**：驗證沒生效、`whitelist` 沒生效、預設值沒地方放、`page: number` 這個型別註記在執行期根本不存在。

實測七種網址（`pnpm start` 之後用 `api.http` 或 curl）：

| 網址 | 接上 DTO 之前 | 之後 |
| --- | --- | --- |
| `/surveys` | 200，全部 | 200，第 1 頁 |
| `?page=2&pageSize=1` | 200 → 問卷**1** ❌ | 200 → 問卷**2** ✅ |
| `?page=abc` | **500** | 400 |
| `?page=2.5&pageSize=1` | 200（悄悄當成 2） | 400 |
| `?page=-1` | **500** | 400 |
| `?pageSize=999999` | 200，全撈 | 400 |
| `?evil=1` | 200（沒人取它） | 200（被 whitelist 丟掉） |

**七種輸入有兩種直接把伺服器打成 500。**

這是 Ch3 坑 #3（`whitelist` 只認驗證裝飾器、不認 TypeScript 的型別宣告）的第二次現場。

> **同時：`pnpm test:e2e` 是 20 passed 全綠。** 因為那 20 條沒有任何一條帶 query 參數。
> 判準：**「既有測試全綠」只證明你沒弄壞舊行為，完全不證明新功能是對的。**
> 這跟前面幾章的「假綠」不同 —— 那些是測試寫錯，這次是測試**還不存在**。

### 2. 改回應形狀就是 breaking change

`findAll` 改回 `{ data, meta }` 之後，兩條既有測試立刻紅：

```
● 沒有任何問卷時回空陣列
  Expected: []
  Received: {"data": [], "meta": {...}}

● 回傳所有問卷，最新的在前面
  TypeError: received value must have a length property
```

這次只有兩條在喊，真實專案是**所有接了這支 API 的前端頁面**。Ch7 的 Swagger 之所以有價值，就是讓這種改動能被前端事先看見。

### 3. 改了共用型別的「意思」，炸掉六個無關的地方

修測試時把 `SurveyBody` 從「一份問卷」直接改成「列表回應」，然後把每個使用處機械地加上 `.data[0]`。結果從 2 條紅變成 **8 條紅**。

`SurveyBody` 有七個使用者，**只有一個是列表**：

| 端點 | 回的是 |
| --- | --- |
| `POST /surveys` ×2 | 一份問卷 |
| `GET /surveys` | ← 只有這個是列表 |
| `PATCH /surveys/:id` ×2 | 一份問卷 |
| `PATCH /:id/publish` `/unpublish` | 一份問卷 |

`POST /surveys` 的回應**一個字都沒變**，卻被改成 `.data[0].status` → `undefined[0]` → `TypeError`。

正解是**新增** `SurveyBodyList`，不是改寫 `SurveyBody`。判準跟 Ch3 的 `assertExists` 同一條：**改了一個東西的形狀，先回頭問「誰在用它、用來做什麼」。**

> **那六處 `tsc` 全是綠的。** `res.body` 是 `any`，`as SurveyBody` 是型別**斷言** ——
> 意思是「相信我」，不是「檢查一下」。**`as` 關掉的是檢查，不是風險。**

### 4. `totalPages` 少了 `Math.ceil`

```ts
totalPages: total / take,   // 7 / 2 = 3.5
```

實測 `?pageSize=10` 時 `totalPages` 是 **0.7** —— 7 筆資料明明就是 1 頁。前端拿去畫 `for (i = 1; i <= 0.7; i++)` 會一個按鈕都不畫，使用者看不到任何資料（即使資料就在 `data` 裡）。

**`tsc` 與 `lint` 都不會抗議**：number 除以 number 就是 number，3.5 是完全合法的值。只有把實際數字看一眼才抓得到。跟 Ch3 的「查錯欄位」同一族 —— 型別對、語法對、語義錯。

### 5. 測試寫了，但沒蓋到那個剛修好的 bug

補完四條分頁測試、24 passed 之後，`totalPages` 的斷言只出現在**一條**測試裡，而那條的 `total` 是 0 —— 但 `0 / 10` 和 `Math.ceil(0 / 10)` **都是 0**，兩種寫法在那條測試上完全無法區分。

也就是說：**把坑 #4 的 bug 放回去，24 條測試依然全綠。**

判準：**想知道一條測試有沒有價值，就把它該抓的 bug 放回去跑一次。** 這跟 `ch03` 作業第 1 題是同一個手法。

### 6. 測試名稱重複，而且其中一條的名字是錯的

兩條測試都叫 `it('不帶參數')`，而第二條打的是 `?page=0` 驗 400 —— 它**帶了參數**。

Jest 失敗時只印測試名稱，兩條同名就分不出是哪一條壞了，診斷價值歸零。這是「貼上測試時沒核對名字跟內容」的第五次，只是這次錯在名字而不是動詞。

**測試名稱要說「驗什麼」，不是「測哪個功能」** —— `分頁` / `分頁2` 這種名字失敗時給不出任何線索。

### 7. 教練問了一個 log 答不出來的問題

實驗要求「確認 `LIMIT` / `OFFSET` 的數字跟 `skip` 換算對得上」，但 log 印出來是：

```sql
... ORDER BY "createdAt" DESC LIMIT $1 OFFSET $2
```

`$1` / `$2` 是**佔位符，不是值**。`prisma.service.ts` 用的 `log: ['query']` 只印 SQL 文字；要看到參數得改成事件形式（`{ emit: 'event', level: 'query' }` 配 `$on('query', e => ...)`，`e.params` 才有值）。

**但這個「缺陷」本身是重點**：SQL 和參數是分開送到資料庫的（參數化查詢 / prepared statement），值永遠不會被當成 SQL 解析 —— 這就是為什麼用 Prisma 寫查詢不會有 SQL injection。② 寫關鍵字搜尋時會再碰到。

## ① 的 SQL 觀察

`PRISMA_LOG_QUERIES=1 pnpm start:dev`（PowerShell 是 `$env:PRISMA_LOG_QUERIES=1; pnpm start:dev`），然後打 `GET /surveys?page=3&pageSize=2`：

```sql
BEGIN
SELECT "id","title","status"::text,"createdAt","updatedAt" FROM "Survey"
  WHERE 1=1 ORDER BY "createdAt" DESC LIMIT $1 OFFSET $2
SELECT COUNT(*) AS "_count$_all" FROM (SELECT "id" FROM "Survey" WHERE 1=1 OFFSET $1) AS "sub"
COMMIT
```

四件事：

1. **`BEGIN` / `COMMIT` 包住兩句** —— `$transaction` 真的生效了。（沒有 `BEGIN` 就 `COMMIT`，PostgreSQL 會直接報錯，所以看到 `COMMIT` 就代表 `BEGIN` 一定在。）
2. **`COUNT(*)` 那句沒有 `LIMIT`** —— 對的，理由見「核心概念」。
3. **但它有 `OFFSET $1`**，而且包了一層只選 `id` 的子查詢。程式碼裡 `count()` 完全沒帶參數，所以那個值只可能是 0，不影響結果 —— 這是 Prisma 產生 count 的固定模板。
   **判準：看到不認識的東西，先問「它會不會改變結果」。**
   （注意這是**推論**不是觀測 —— 看不到值，見坑 #7。）
4. **`WHERE 1=1`** 是「沒有任何篩選條件」的佔位符。② 加上 `status` 與 `q` 之後這裡會長出真正的條件，到時候回來對照。

再打一個 `PATCH /surveys/:id`（或任何借 `assertExists` 丟 404 的端點）：

```sql
SELECT "id","status"::text FROM "Survey" WHERE ("id" = $1 AND 1=1) LIMIT $2 OFFSET $3
```

兩個觀察：

- **只撈 `id` 和 `status` 是 `assertExists` 的指紋**（`select: { id: true, status: true }`）。`findOne` 會撈全部欄位，而且後面一定跟著第二句撈 questions。**從 SQL 的形狀反推是哪一支方法在跑** —— 這正是 Ch3 第二段量出「同一批題目撈兩次」用的方法。
- **`findUnique` 也帶 `LIMIT` / `OFFSET`**，而它根本沒有分頁。所以**「看到 LIMIT 就是分頁」是錯的推論** —— Prisma 幾乎每句 SELECT 都帶。分頁的證據不是「有沒有 `LIMIT`」，是「那個值是不是你的 `take`」。

> 另外：帶參數與不帶參數的兩次 `GET /surveys`，**SQL 文字一模一樣**，差別完全在參數裡。這也解釋了為什麼裸打 `/surveys` 的**輸出**跟加分頁之前一樣（3 筆資料裝得進第 1 頁），但**行為**完全不同 —— 以前的 log 裡沒有 `LIMIT` / `OFFSET`。**輸出一樣 ≠ 行為一樣。**

## offset vs cursor

現在的實作是 **offset 分頁**：直覺、能跳頁、實作簡單。它有兩個問題是**機制決定的、改程式碼解不掉**：

**一、頁碼越後面越慢。** `OFFSET 100000` 不是「直接跳到第 100001 筆」——資料庫必須真的把前 10 萬列讀出來、排好序、然後丟掉。第 1 頁和第 10000 頁的成本差好幾個數量級。

**二、翻頁期間資料變動會漏看或重複。** 按 `createdAt DESC` 排，看完第 1 頁之後有人新增一筆，所有東西往後推一格，第 2 頁（`OFFSET 10`）的第一筆就是你剛才看過的那筆。刪除則相反 —— 有一筆完全沒被看到就跳過去了。

**`$transaction` 救不了第二個問題**：它只保證同一次請求裡的兩句 SQL 看到同一個瞬間，但第 1 頁和第 2 頁是**兩次獨立的請求**，中間隔了使用者思考的幾秒鐘。

cursor 的作法是不說「跳過 N 筆」，而是「**從這個位置之後開始**」：

```sql
-- offset
ORDER BY "createdAt" DESC LIMIT 10 OFFSET 10

-- cursor
WHERE "createdAt" < $1          -- $1 = 上一頁最後一筆的 createdAt
ORDER BY "createdAt" DESC LIMIT 10
```

兩個問題同時消失：`createdAt` 有索引的話資料庫直接定位，第 1 頁和第 10000 頁一樣快；判準是「值」而不是「位置」，中間插入幾筆都不影響「比這個時間更早的下一批是誰」。

代價：

- **不能跳頁。** cursor 只知道「上一批的結尾」，所以只能一直「下一頁」。這就是為什麼社群軟體是無限捲動、後台管理介面是頁碼。
- **cursor 欄位必須唯一且穩定。** `createdAt` 是 `TIMESTAMP(3)`，同毫秒建立的兩筆會相等（`surveys.e2e-spec.ts` 的測試註解早就寫過這個坑），`<` 就會跳過其中一筆。實務上要用 `(createdAt, id)` 組合。

**判準**：能跳頁、資料量不大、後台管理 → offset。無限捲動、資料量大 → cursor。這個專案兩個條件都指向 offset。

# 第二段 ② 排序 + 篩選

四個新的 query 參數，全部加進既有的 `FindSurveysQueryDto`：`sort` / `order`（動 `orderBy`）、
`status` / `q`（動 `where`）。分兩輪做，因為兩輪踩的坑性質完全不同。

## 核心概念

### 排序欄位一定要白名單，但理由不是 SQL injection

Prisma 的 `orderBy` 是型別安全的，前端傳什麼都不會變成一段 SQL 被執行。
但欄位名不存在時 Prisma 在**執行期**丟 `PrismaClientValidationError`，
Nest 不認識這個錯誤 → **500**。

所以 `@IsIn(['createdAt', 'title'])` 擋的是兩件事：

1. 前端一個手誤（`?sort=name`）就把伺服器打成 500
2. 有人用試錯把資料表的內部欄位名一個一個探出來

**把它說成「防 injection」是錯的教學**，而且會讓人以為「反正 Prisma 安全」就可以不加。

### computed property name —— 方括號在做什麼

`orderBy: { [query.sort]: query.order }`。物件字面值的 key **預設是「字面上那串文字」**，
方括號才代表「先把裡面的運算式求值，結果當屬性名」：

```ts
{ query.sort: v }     // 語法錯誤
{ sort: v }           // 合法，但意思是「照一個叫 sort 的欄位排」——沒這欄位
{ [query.sort]: v }   // query.sort 是 'title' → { title: v }
```

值那一側本來就是運算式，不需要方括號。反向的例子是 `where: { id }` 這個簡寫
（完整是 `{ id: id }`）：左邊是欄位名、右邊是變數，只是剛好同名才簡寫得起來。

### `undefined` = 不加這個條件（這次用在 `where`）

Ch2 的 `update` 講過「Prisma 眼中 `undefined` 是不要動它」，那是用在 `data`。
這次是同一個約定用在 `where`：

```ts
const where: Prisma.SurveyWhereInput = {
  status: query.status,                                // 沒給 → 不篩 status
  title: { contains: query.q, mode: 'insensitive' },   // 沒給 → 整個 title 條件消失
};
```

**一個 `if` 都不用寫**，而且連巢狀的 `contains: undefined` 也一樣被忽略
（教練原本以為這裡會出事，實測推翻 —— 見坑 #11）。

SQL 是證據：什麼都不帶時 `WHERE 1=1`，帶了 `q` 才長出 `title ILIKE`。
**那些條件不是被跳過，是從來沒被產生。**

### `count` 與 `findMany` 的 `where` 必須一模一樣

這是這一段最該記住的一條。只給 `findMany` 加篩選、`count` 忘了加，回應是**完全合法的 JSON**：

- `data` 是篩過的 ✔
- `total` 是全表筆數 ✘
- `totalPages` 算出 5 頁，但第 2 頁開始全是空的

沒有錯誤訊息、沒有紅燈、前端也不會發現。**對策不是「記得兩邊都加」**（人一定會忘），
是把 `where` 抽成一個變數給兩邊共用，讓「兩邊不一致」在結構上不可能發生。

### 字串的大小由 collation 決定，不是由語義

`ORDER BY title` 是一個字一個字比、第一個不同的位置決勝負（跟字典一樣）。
但「哪個字比較大」是 **PostgreSQL 的 collation（定序）** 說了算，不是應用程式。

這台資料庫用 Unicode 碼位：`一 U+4E00` < `三 U+4E09` < `二 U+4E8C`，
所以「第一份 / 第二份 / 第三份」排出來是 **一、三、二**。

**資料庫不知道 `三` 是 3。** 「一二三」的大小是中文的語義，不是字元的順序 ——
在英文裡兩者剛好重合（`a` 的碼位就是比 `b` 小），所以平常感覺不到。
同一個機制的其他意外：`'10' < '2'`、某些 collation 下 `'Z' < 'a'`。

真要讓中文照使用者的直覺排，得在資料庫層指定 ICU collation（筆劃或拼音），不在這一章範圍。

### `mode: 'insensitive'` 就是 `ILIKE`，而它有代價

```sql
"title" ILIKE ('%' || $1 || '%')
```

`ILIKE` 是 PostgreSQL 專屬的「不分大小寫的 LIKE」，`||` 是字串串接。
**前面那個 `%` 是關鍵**：B-tree 索引是照「開頭」排序的，`'%...'` 等於說「開頭我不管」，
索引就完全用不上 → **全表掃描**。

現在幾十筆看不出來，幾十萬筆就是每打一次搜尋掃一次全表。
真正的解法是全文檢索或 trigram 索引，這一章不做，但要知道**「加一個搜尋框」不是免費的**。

### 交易的兩個能力（① 的補講）

進 ② 之前的驗收問到「`$transaction` 包住兩句 `SELECT` 是為了什麼」，
答成「怕一個成功一個失敗」——那是**原子性**，而兩句 `SELECT` 不會做一半、也沒東西要回滾。

這裡用到的是另一個能力：**一致的讀取視角**（同一個時間點的快照）。
分開跑的話 `findMany` 和 `count` 是兩個時間點，中間有人新增一筆，
回應就自相矛盾：`data` 來自 47 筆的世界、`total` 說 48。

**判準：「這幾句查詢的結果會不會被拿來互相比較？」會，就包起來，跟有沒有寫入無關。**
照「怕失敗才用交易」的理解去推，這種場合永遠不會想到 —— 而它的 bug 只在有人同時操作時出現，
本機測不到、e2e 也測不到。（原子性那一面 Ch5 會實際用到。）

## 決策取捨

### `@IsOptional()` 只加在 `status` / `q`，不加在 `sort` / `order`

判準是**有沒有預設值**，不是「感覺上是不是選填」：

| | 預設值 | 進到驗證階段時 | `@IsOptional()` |
| --- | --- | --- | :---: |
| `sort` / `order` | 有 | 永遠不是 `undefined` | 不需要 |
| `status` / `q` | 無 | 沒帶就是 `undefined` | 需要 |

型別的 `?` 要跟 `@IsOptional()` **成對出現**，一個管執行期、一個管編譯期。
少了 `?`，型別會宣稱「這個值一定存在」，於是 `query.q.toLowerCase()` 這種寫法
`tsc` 全綠、執行期直接 500。

### 為什麼 `status` / `q` 不給預設值

預設值的意思是「沒指定就用這個」，但「沒指定篩選條件」要的是**不要篩**，
不是「篩某個特定值」。而 `undefined` 在 Prisma 眼中正好就是「不加這個條件」——
需求和機制剛好對上，不需要額外發明一個「全部」的哨兵值。

### `where` 用型別註記，不用 `as const`

抽成變數後 `mode: 'insensitive'` 會被推論成 `string`，跟 Prisma 的 `QueryMode` 對不上
（坑 #12）。兩種解法：

```ts
title: { contains: query.q, mode: 'insensitive' as const }   // 只解決型別
const where: Prisma.SurveyWhereInput = { ... }               // 選這個
```

選後者的理由不是「比較正式」，是**它讓 `tsc` 真的幫你檢查欄位名**（打錯 `titel` 會紅）。
對照正下方的 `orderBy` 動態 key —— 那裡 `tsc` 什麼都檢查不到。
**同一支方法裡，一個地方型別有用、一個地方沒用；有用的地方就別放過。**

型別名字有規律：`Prisma.<Model><用途>Input`（`SurveyWhereInput` /
`SurveyOrderByWithRelationInput` / `SurveyCreateInput`），不用背，打 `Prisma.Survey` 會列出來。

**界線：`Prisma.` 開頭的型別只能出現在 service 這一層。** 讓它跑到 controller 或 DTO 上，
等於把「我們用 Prisma」寫進對前端的契約 —— 跟 `page` / `pageSize` 不叫 `skip` / `take` 同一個理由。

### 不用 `if` 一條一條組 `where`

實務上條件多的時候常見這種寫法：

```ts
const where: Prisma.SurveyWhereInput = {};
if (query.status) where.status = query.status;
if (query.q) where.title = { contains: query.q, mode: 'insensitive' };
```

這個專案不用它。有「`undefined` = 不加條件」這條約定，一個物件字面值就夠了，
多寫五行 `if` 只是把同一件事講得更囉唆。等到條件之間開始互相牽扯
（例如「有 `q` 時才允許某種排序」）才輪到 `if`。

### 測試資料改用 ASCII 開頭的標題

`sort=title` 那條測試原本用「第一份 / 第二份 / 第三份」，結果撞上 collation（坑 #10）。

改法**不是**把斷言改成實測到的順序 —— 那是把「這台資料庫今天的 collation」寫死進測試，
換一台就紅，而且看的人不知道為什麼是那個順序。**斷言要寫「我要的」，不是「我觀察到的」。**

正解是換前提資料：`A問卷` / `B問卷` / `C問卷`，第一個字就分出勝負，
`A < B < C` 在任何 collation 下都成立。這樣這條測試才專心驗它該驗的事
（`sort=title` 有沒有生效），而不是順便驗中文排序規則。

## 踩到的坑

> 接續第一段的 #1–#7。

### 8. `createAt` 少一個 `d`，三處一致地錯

DTO 寫成：

```ts
@IsIn(['createAt', 'title'])
sort: 'createAt' | 'title' = 'createAt';
```

三個地方**一致地錯**，於是：

- `tsc` 綠（字面值聯集自己跟自己對得上）
- `@IsIn` 綠（白名單裡就是這個錯字）
- 執行期 `orderBy: { createAt: 'desc' }` → `PrismaClientValidationError` → **`GET /surveys` 每一次都 500**，連不帶參數的預設路徑都是
- 而 `?sort=createdAt`（正確拼法）會被白名單擋成 **400**

實測過的事實（跑 `tsc --noEmit` 對三個情境）：

```ts
prisma.survey.findMany({ orderBy: { [sortAsString]: order } });   // ✅ 綠
prisma.survey.findMany({ orderBy: { [sortAsUnion]:  order } });   // ✅ 綠
prisma.survey.findMany({ orderBy: { nope: 'asc' } });             // ❌ TS2353
```

**只有寫死的欄位名會被抓到，動態 key 一律放行**，連宣告成 `string` 都放行。
原因是兩條 TypeScript 規則疊在一起：computed key 不算「已宣告的屬性」，
所以 excess property check 整個關掉；而 `SurveyOrderByWithRelationInput` 的欄位又全是選用的，
沒有任何一個「缺了」。兩邊都沒東西可查。

**留下的結論：那一行的欄位名，`tsc` 完全不會幫你檢查。唯一擋在它前面的是 `@IsIn`。**
（加型別註記也沒用，實測一樣綠 —— 它是給人看的文件，不是保護。）

### 9. `WHERE` 那邊剛好相反 —— 型別是有用的

同一支方法裡，`where` 的欄位名是寫死的，加了 `Prisma.SurveyWhereInput` 註記之後
`tsc` 就抓得到拼錯。**兩個相鄰的地方，型別的保護力天差地遠。**

判準：**欄位名是寫死的 → 型別有用，記得給註記；欄位名是動態的 → 型別無用，必須有執行期白名單。**

### 10. 字串排序不照中文的語義

`sort=title&order=asc` 那條測試第一次跑就紅：期望 `第二份`、實際 `第三份`。
不是程式碼錯，是預期錯 —— 詳見「核心概念」的 collation 那節。

值得記的是它的形狀：**測試紅了，但錯的是測試不是實作。**
遇到紅燈先問「我的預期本身站不站得住」，而不是直接去改程式碼。

### 11. 教練講錯兩次，兩次都被實測推翻

- **「動態 key 的型別會跟 Prisma 對不上」** —— 錯。實測是綠的，而且綠得比預期更危險（坑 #8）。
- **「`contains: undefined` 不能這樣寫」** —— 錯。Prisma 連巢狀的 `undefined` 也忽略，
  28 條測試全綠、沒有 500。

兩次都是**先給結論、沒有先量**。這跟 Ch3 那次「`.env` 在 e2e 裡是被誰讀進去的」是同一種錯：
結論方向對（「這裡有坑要小心」），機制錯。**照錯的機制去推下一步就會錯**，
而且它比「沒有結論」更糟，因為它聽起來很有把握。

**判準：可以在三分鐘內實測的事，不要用推論代替。** 這一章兩次實測都不到三分鐘。

### 12. 抽成變數之後 `mode` 被推論成 `string`

```
error TS2322: Type '{ contains: string; mode: string; }' is not assignable ...
  Type 'string' is not assignable to type 'QueryMode | undefined'.
```

內嵌在 `findMany({ ... })` 裡時不會發生，因為 TypeScript 會拿 Prisma 的參數型別回頭對
（contextual typing），字面值 `'insensitive'` 被保留。**一抽成獨立變數，那條線就斷了**，
TS 只好自己猜，猜成 `string`。

這是「把 `where` 抽成變數」的代價，解法見「決策取捨」。
**記住這個形狀**：把內嵌的物件抽出去變成變數，型別推論的結果會改變。

### 13. 兩個排序欄位算出同一個答案，測試就等於沒寫

`sort=title` 那條測試第一版的前提資料是：

| 標題 | createdAt |
| --- | --- |
| A問卷 | 01-01（最舊）|
| B問卷 | 01-02 |
| C問卷 | 01-03（最新）|

`title` asc = A、B、C；`createdAt` asc = A、B、C —— **一樣**。
於是把 service 改成 `orderBy: { createdAt: query.order }`（**完全忽略 `query.sort`**），
28 條測試**全綠**。

`create` 的**呼叫順序**確實被刻意打亂了，但那擋的是另一個 bug（「根本沒有 `orderBy`」）。

修法是讓 `createdAt` 的順序跟標題**既不相同、也不相反**（相反會撞上 `desc`）：
`A=01-02`、`B=01-01`、`C=01-03`。驗算：`title` asc = A、B、C；
`createdAt` asc = B、A、C；`createdAt` desc = C、A、B —— 三者互不相同。
改完再放一次 bug，這次紅了。

**這是坑 #5「測試存在不等於蓋到」的第二次現場**，形狀一模一樣：
上次是 `0/10` 和 `Math.ceil(0/10)` 都等於 0，這次是兩個排序欄位算出同一個答案。
**前提資料讓正確與錯誤的行為看起來一樣，那條測試就沒有價值。**

## ② 的 SQL 觀察

打開 `PRISMA_LOG_QUERIES=1`，四種 query 的 `WHERE` 對照：

```sql
-- 什麼都不帶
WHERE 1=1

-- 只帶 q
WHERE "title" ILIKE ('%' || $1 || '%')

-- status + q
WHERE ("status" = CAST($1::text AS "public"."SurveyStatus")
       AND "title" ILIKE ('%' || $2 || '%'))
```

四件事：

1. **`undefined` 沒留下任何痕跡。** 不是 `status = NULL`、也不是某種「跳過」的判斷，
   **是整條不存在**。`1=1` 是 Prisma 在「一個條件都沒有」時放的恆真佔位符
   （`WHERE` 後面總得有東西）。這是 ① 那條「② 會長出真正的條件，到時候回來對照」的兌現。

2. **`count` 那句裡有一個你沒寫的 `OFFSET`。**

   ```sql
   SELECT COUNT(*) AS "_count$_all" FROM (SELECT "id" FROM "Survey" WHERE ... OFFSET $1) AS "sub"
   ```

   ① 推論它是常數 0（見坑 #7：log 看不到值），**② 確認了**：既有那條「`page=2` 回最後 1 筆」
   的測試斷言 `meta.total` 是 3，如果 `OFFSET` 跟著 `skip` 走，`total` 會變成 2，那條早就紅了。
   **推論 → 找到現成的證據把它變成觀測**，這比再看一次 log 便宜。

3. **enum 在資料庫裡是真的型別。**

   ```sql
   "status" = CAST($1::text AS "public"."SurveyStatus")   -- 進去
   SELECT "Survey"."status"::text                          -- 出來
   ```

   值以文字送進去、**轉成 PostgreSQL 的 `SurveyStatus` 型別**才比對，回來時再轉回文字。
   所以 `status` 有**兩道防線**：`@IsEnum` 在 Node、enum 型別在資料庫 ——
   繞過 API 直接下 SQL 寫 `'PPAP'` 也會被擋。

   這跟 Ch3 那次意外正好互補：當時拔掉 `@IsEnum` 想看資料庫會不會擋，
   結果**根本沒走到資料庫**（`whitelist` 先丟掉了）。現在看到第二道防線長什麼樣了。

   對照 `sort`：欄位名不是任何型別，**沒有第二道防線**，所以白名單是唯一的。

4. **`ILIKE ('%' || $1 || '%')`** —— 代價見「核心概念」。

# 第三段 ③ `?includeQuestions=true`

兌現 Ch3 `findOne` 那句「由 query 決定要不要帶題目是 Ch4 的事」。
範圍最小的一段，但它是這一章唯一**改到既有端點回應形狀**的一段。

**52 passed**（+3），`pnpm test` 4 passed。

## 核心概念

### boolean 是 query string 轉型最容易錯的型別

`page` 用 `@Type(() => Number)` 沒問題，`includeQuestions` 用 `@Type(() => Boolean)` 會壞。
差別**不在「轉得對不對」，在「轉壞了看不看得出來」**：

| 輸入 | `Number` | `Boolean` |
| --- | --- | --- |
| `'2'` / `'true'` | `2` ✔ | `true` ✔ |
| `'false'` | — | **`true`** ✘ |
| `'abc'` | **`NaN`** | **`true`** ✘ |
| 驗證抓得到嗎 | `@IsInt()` 抓得到 `NaN` → 400 | `@IsBoolean()` 看到合法的 `true` → 放行 |

因為 JS 的 `Boolean(字串)` 問的不是「這個字串寫什麼」，而是**「這個字串是不是空的」**：

```js
Boolean('true')   // true
Boolean('false')  // true   ← 非空字串
Boolean('0')      // true
Boolean('')       // false  ← 唯一的 false
```

**`Number` 有一個代表失敗的值（`NaN`），`Boolean` 沒有。** 沒有 `NaB` 這種東西 ——
任何字串都被映射成一個完全合法的布林值，驗證那一層因此**分不出
「使用者說了什麼」和「轉型把它變成什麼」**。

這就是 ① 決定不開全域 `enableImplicitConversion` 的理由（見第一段「決策取捨」）的現場。

### `@Type` 與 `@Transform` 的差別是「誰決定怎麼轉」

兩個都是 class-transformer 的裝飾器，**執行時機完全一樣**（第一階段建實例，驗證是第二階段）。

- `@Type(() => X)` —— 把工作交給 `X`。對 primitive 來說就是呼叫 `X(value)`，
  所以它繼承了 JS 建構函式的轉型行為（包含上面那個坑）。
  （它原本的主要用途是**巢狀物件**：告訴 class-transformer「這個屬性要建成 `Address` 的實例」。）
- `@Transform(fn)` —— 轉換函式自己寫，回傳值就是那個屬性最後的值。

因為 `@IsBoolean()` 檢查的是**轉換之後**的值，所以「能不能擋下非法輸入」完全取決於
`@Transform` 怎麼寫。

### `: value` 那個 fallback 不是隨手寫的

```ts
value === 'true' ? true : value === 'false' ? false : value
```

寫成只比對一種（`value === 'true'`）的話，`?includeQuestions=ture`（手誤）→ `false`
→ **200 配沒有題目**。使用者以為自己要了題目，伺服器安靜地當作沒要。

原封不動回傳，那個屬性還是 `string`，`@IsBoolean()` 就擋得下來 → 400。
**「沒有錯誤」不等於「正確」**，這是這個專案第三次遇到（Ch3 是 `findAll` 少一行 404
變成 200 配空陣列，② 是 `count` 忘了 `where`）。

### 邊界上的值標 `unknown`，不要標 `any`

`@Transform` 的回呼參數 `TransformFnParams` 裡 `value: any`（class-transformer
不可能知道你會收到什麼），所以 `return value` 會被 ESLint 的 `no-unsafe-return` 擋下。
那條規則在做的事是**擋住 `any` 的擴散** —— 一個 `any` 溜進來，它碰到的每個東西都失去檢查。

```ts
@Transform(({ value }: { value: unknown }) => ...)
```

- `any` —— 「什麼都行，別檢查我」。`value.foo.bar()` 直接放行，執行期才炸
- `unknown` —— 「我不知道它是什麼，**所以你不准直接用它**」，要先縮小型別才能動

而這個函式本來就先比對過才使用，標成 `unknown` 一行都不用改。
**通則：處理外部輸入時邊界標 `unknown`，逼自己先驗證再使用。**

### `undefined` = 這個參數不存在（同一條約定的第三次）

```ts
include: includeQuestions ? { questions: { orderBy: { order: 'asc' } } } : undefined,
```

不必寫兩個 `findUnique` 分支。這條約定至此用過三個位置：

| | 用在哪 | 意思 |
| --- | --- | --- |
| Ch2 `update` | `data` 的**欄位**上 | 不要動這個欄位 |
| Ch4 ② `findAll` | `where` 的**欄位**上 | 不加這個條件 |
| Ch4 ③ `findOne` | **最外層的參數**上 | 不加 `include` |

## 決策取捨

### 參數形狀選 boolean，不選列舉

另一個選項是 `?include=questions` 配 `@IsIn(['questions'])`，實務上更接近 REST 慣例、
而且有擴充空間（之後可以 `?include=questions,responses`）。

**沒有選它是因為這是教學專案**：`@IsIn` 白名單在 ② 才剛寫過一次，沒有新東西；
而 boolean 轉型是 Ch4「query string 轉型驗證」這個主題最後一塊拼圖，
也是三種型別裡唯一**內建轉型會靜靜給出錯誤答案**的那一個。

**真的在做產品的話選列舉**。判準是「這個參數之後會不會長出第三種值」——
會的話 boolean 遲早要改成列舉，而那時它已經是公開契約了。

### 預設不帶題目

Ch3 以來 `GET /surveys/:id` **一律**帶題目，改成預設不帶是一次 **breaking change**
（這一章第二次，第一次是 ① 把回應改成 `{ data, meta }`）。

選它的理由是**時機**：前端 Ch13 才建，現在改是免費的；Ch9 之後就不是了。
而且預設帶的話幾乎沒人會主動去關它，那句撈題目的 SQL 實際上會一直存在 ——
「提供了關閉的選項」和「有人真的關掉」是兩件事。

代價是**回傳形狀隨條件而變**：帶了才有 `questions` 欄位，前端得判斷自己拿到的是哪一種。
這跟 Ch3 `publish` 那條「冪等連回應的形狀都算」是同一個問題的兩面 ——
那裡刻意選了「只有一種形狀」，這裡刻意選了「兩種」。差別在於**誰決定**：
`publish` 的形狀由伺服器內部狀態決定（前端無從預期），這裡由前端自己送的參數決定。

### 型別精確 vs 程式碼重複：選了重複比較少的那邊

三元運算式讓 Prisma 的型別推導**退回保守的那一邊**，回傳型別塌成「沒有 `questions`」那種。實測：

```ts
const s = await this.findOne(id, true);
s.questions;
// error TS2339: Property 'questions' does not exist on type
//   '{ id: string; title: string; status: SurveyStatus; createdAt: Date; updatedAt: Date; }'
```

**執行期完全正確**（真的有題目、JSON 回應也有），只是編譯期不知道 ——
因為 Prisma 的型別魔法靠「`include` 字面上長什麼樣」推導，而編譯期它只看得到 `X | undefined`。

想要型別精確就得寫成兩個分支（各一句 `findUnique`），代價是 `where` 與 404 判斷重複一次。
這個專案接受型別不精確，因為**沒有任何 TypeScript 程式碼會去讀 `.questions`**：
controller 直接回傳、Nest 序列化成 JSON、e2e 用 `as` 斷言。受影響的只有未來想在 service
裡用那個欄位的人。

**帶走的判準：在 API 上多給一個選項，型別系統就少知道一件事。**

### service 收 boolean，不收整包 DTO

跟 `findAll(query: FindSurveysQueryDto)` 不一致，是刻意的。判準是**這支方法需要幾個值**：

| | 需要的值 | 傳法 |
| --- | --- | --- |
| `findAll` | 六個 | 傳 DTO（六個參數的方法沒人叫得動，加篩選條件還要改簽名）|
| `findOne` | 一個 | 傳 boolean |

檢驗方式：**「如果哪天不是 HTTP 在呼叫這支方法，它得先準備什麼？」**
`findAll` 得準備六個值，包成物件本來就合理；`findOne` 得為了一個 boolean 先 `new`
一份由 HTTP 形狀決定的 DTO。**「service 不能碰 DTO」不是鐵律，看欄位數決定。**

## 踩到的坑

> 接續第一段的 #1–#7、第二段的 #8–#13。

### 14. 參數名稱三種寫法混用，其中一條測試是假綠

實作與測試之間，`includeQuestions` / `includesQuestion` / `includeQuestion` 三種拼法都出現過。
最糟的一次是：DTO 屬性叫 `includesQuestion`，但「`=false` 時沒有 questions」那條測試
打的是 `?includeQuestions=false`。

於是：DTO 沒宣告 `includeQuestions` → **whitelist 無聲丟掉** → 屬性維持預設 `false`
→ 沒有題目 → **測試通過**。

**它通過的理由跟它想驗的事完全無關** —— 那時把 `@Transform` 整行刪掉，它照樣綠。

這是假綠的第七種，而且形狀是新的：前六種都是**測試本身寫錯**（動詞錯、路徑錯、
少了 `await`、查錯欄位、名字撞號、前提資料讓兩種行為看起來一樣），
這次是**測試沒錯，但它送出的參數被伺服器合法地忽略了**。

**判準：query 參數改名時，`whitelist` 會讓舊名字「安靜地失效」而不是報錯。**
改名的當下要全域搜一次那個字串。

### 15. `no-unsafe-return` 不是在挑剔，是在擋 `any` 的擴散

`@Transform` 的 `value` 是 `any`，直接 `return value` 會被擋。
第一反應是「加個 `as boolean` 就好」——**那是關掉檢查，不是解決問題**
（`as` 關掉的是檢查、不是風險，② 坑 #8 付過學費）。

正解是把參數標成 `unknown`：程式碼一行不用改，因為它本來就先比對過才使用。

### 16. 註解過期第六次 —— 這次錯的那句，是同一輪剛被實測推翻的內容

收尾之後回頭查核（「註解與文件都補好了嗎」），才發現 `findOne` 尾端還留著 Ch3 寫的：

> 而且它現在也不只是 `Survey`，是 `Survey & { questions: Question[] }` ——
> **加了 `include`，回傳型別自己就跟著變了**。把游標移到 `survey` 上看一眼。

**這在 ③ 之後是錯的**（型別塌成沒有 `questions` 的那一種），而且它還**叫讀者照做** ——
把游標移上去會看到跟註解**相反**的東西。

前五次的形狀都是「改的是 A 檔案，而描述 A 的那句話在 B 檔案」。**這次不是**：
同一個檔案、同一支方法、上下相距二十行 —— 而且正確版本就寫在上面那段 `include` 註解裡，
是我在**同一輪**實測出來、親手寫下的。

**判準補強：實測推翻了某個既有說法時，要立刻全域搜一次那個說法。**
只在新寫的地方記錄正確版本是不夠的 —— 舊的那句還躺在原地，而且它通常更容易被先讀到
（這裡就是：錯的那句在方法的**結尾**，是讀完程式碼之後最後看到的東西）。

同一次查核還發現 `docs/專案速查.md` 的**檔案地圖**漏了兩份 query DTO，
其中 `find-surveys-query.dto.ts` 從 ① 就漏了、漏了兩段沒人發現。原因很明確：
「新增檔案要接進**閱讀動線**」是明文規定，「加進**檔案地圖**」不是 ——
兩者在同一份文件裡，只有被寫成規則的那個被記住了。**已補進 `CLAUDE.md`。**

## ③ 的 SQL 觀察

不帶參數與帶 `?includeQuestions=true` 的差別，是**第二句 SQL 存不存在**：

```sql
-- 不帶（預設）
SELECT "id","title","status"::text,"createdAt","updatedAt" FROM "Survey"
  WHERE ("id" = $1 AND 1=1) LIMIT $2 OFFSET $3

-- ?includeQuestions=true
SELECT ... FROM "Survey" WHERE ("id" = $1 AND 1=1) LIMIT $2 OFFSET $3
SELECT ... FROM "Question" WHERE "Question"."surveyId" IN ($1) ORDER BY "order" ASC
```

這是 Ch3 第二段那個觀察的直接延續：**`include` 是兩句 SQL，不是 JOIN**。
③ 做的事就是讓第二句變成有條件的。

（`1=1` 與 `LIMIT` / `OFFSET` 是 Prisma 的固定模板，跟這一段無關 —— 見第一段的 SQL 觀察。）
