# Ch16 — 環境變數分離與 production build

> 階段三第四章,兩輪:① CORS 的 origin 依環境切換 ② 前端 `.env` 與第一次 `pnpm build`。
> **這份文件只寫後端相關的部分**(`CLAUDE.md` 的規則)——
> 前端的實測結果寫在 `survey-frontend/docs/前端分層慣例.md` §6。

開工前實測線上那台:

```
$ curl -H "Origin: https://survey-frontend.example.com" .../health
access-control-allow-origin: http://localhost:3000     ← 不管誰來問都回這個
```

**線上的白名單從 Ch14 起就是寫死的 `localhost`。** 前端一部署上去,不管網址是什麼,
整站 CORS 全紅 —— 而那個症狀 Ch14 已經確認過會騙人(Console 一片紅、`curl` 完全正常)。

---

## 核心概念

### 1. 設定值來自外部,就要決定「外部沒給」怎麼辦

這是這一章真正的主題,CORS 只是它的第一個現場。兩條路:

```
給預設值    方便，但「忘了設」會安靜地生效成另一種行為
大聲失敗    啟動就死掉，換來「不會有一台半殘的伺服器在線上」
```

判準**不是**「哪個比較嚴謹」,而是 **預設值安不安全**:

| 變數 | 沒設會怎樣 | 選擇 |
| --- | --- | --- |
| `PRISMA_LOG_QUERIES` | 少印一些 SQL | 預設關 |
| `DATABASE_POOL_MAX` | 用 pg 的預設值 10 | 不設 |
| `CORS_ORIGIN` | **線上整站不能用,而且症狀騙人** | 大聲失敗 |

專案早就有這條通則,寫在 `test/setup-env.ts`:
**會造成資料遺失的設定,寧可大聲失敗,也不要有預設值。** Ch16 把它推廣了一步 ——
不只是資料遺失,**「壞掉但看起來沒壞」也算**。

而前端剛好是反例:`NUXT_PUBLIC_API_BASE` 沒設就退回 `http://localhost:3100`,
那在本機開發正是你要的。**同一個問題,兩邊給了相反的答案,而判準是同一條。**

### 2. `origin` 給字串跟給陣列,cors 的行為完全不同

```
字串  一律回那個固定值，根本不看請求的 Origin —— 沒有「不匹配」這回事
陣列  比對請求的 Origin：中了把它原樣回去，沒中就完全不加這個標頭
```

不管哪一種,真正擋下來的都是**瀏覽器**(拿 `Access-Control-Allow-Origin` 跟自己的
origin 比)。伺服器這一端從頭到尾都照常執行 —— 如果那是 `DELETE`,東西已經刪了。

### 3. 「跑幾次」決定失敗時該降級還是炸掉

`src/common/` 底下現在有兩個純函式檔案,結論相反:

| | 什麼時候跑 | 出錯時 |
| --- | --- | --- |
| `field-errors.ts` | **每個請求**都可能跑 | **降級** —— 拿不到欄位名就回 `undefined`,409 照樣回 |
| `cors-origins.ts` | **啟動時只跑一次** | **炸掉** —— 讓 process 死掉 |

同一個資料夾、相反的判斷,而判準只有一條:**壞掉的影響範圍是一個請求,還是整台伺服器。**

### 4. e2e 看不到部署平台

`.env.example` 從 Ch8 就寫著這句話,Ch16 是它的第二次現場:

> `test/setup-env.ts` 的防呆只看得到本機這兩個檔案,**看不到部署平台上填了什麼**。

所以「Render 上的 `CORS_ORIGIN` 填錯」這件事,**沒有任何測試抓得到**。
唯一的對策是讓應用自己在啟動時檢查 —— 那個檢查會在 Deploy 日誌裡大聲說話。

## 決策取捨

### 逗號分隔的清單

環境變數的值只能是字串,而部署平台的 UI 只給你一個輸入框。
Django 的 `CORS_ALLOWED_ORIGINS`、Spring 的 `allowed-origins` 都是這個形狀。

### 結尾斜線:拒絕,不自動去掉

`http://localhost:3000/` 是 CORS 最常見的填錯法(瀏覽器送來的 `Origin` 標頭
**永遠沒有路徑部分**,所以那個值永遠匹配不到)。

框架層幾乎都不驗:express 的 `cors`、Spring、Rails 都是純字串比對。
所以擋不擋是應用自己的決定。選「拒絕」而不是「正規化」,理由是
**靜默修正會讓「你以為設的」跟「實際生效的」不一致** —— 下一個看的人不知道發生過修正。
安全相關的設定,業界主流也是這一派。

### 不引 Joi(`ConfigModule.forRoot({ validationSchema })`)

那是 NestJS 官方示範的環境變數驗證位置,而且是成熟服務的做法。這裡不用,兩個理由:
為一個變數多一個依賴不划算;而 `validationSchema` 表達不了「split 完至少要剩一個」
這種條件,那本來就得寫在函式裡。**等環境變數多到七八個、彼此有關係時再整批搬過去。**

### e2e 的白名單寫死在 `test/setup-env.ts`,不讀 `.env`

`.env` 不進版控,換一台機器時它的內容誰也不知道 —— 測試會變成
「斷言你本機那個檔案剛好寫了什麼」,紅了也分不出是程式壞了還是環境沒填。

而**期望值在測試裡自己寫一次**,不去 import 那個常數:兩邊讀同一個變數的話,
值被改錯了測試照樣綠。**「測試自己寫一次期望值」跟「不要重複」是有衝突的,這裡選前者。**

## 踩到的坑

### 1. `getOrThrow` 只擋 `undefined` —— 同一個坑的第二次現場

```
ConfigService.getOrThrow  原始碼是 isUndefined(value) 才 throw
CORS_ORIGIN=              dotenv 給的是空字串 → 這一關會過
''.split(',')             → ['']  一個永遠不會等於任何 Origin 的字串
```

後果:**部署成功、`/health` 綠、Swagger 打得開、`pnpm test:e2e` 全綠,只有真的瀏覽器 100% 紅。**

第一次現場是 `JWT_SECRET`(記在 `.env.example`),那次的症狀是第一次登入 500。
這次更安靜。**結構性對策**:把「什麼算沒設」整個交給 `parseCorsOrigins` 一個地方判斷,
`undefined` / `''` / `',  ,'` 三種形狀走同一條路 —— 而那個地方有單元測試守著。

用 `getOrThrow` 再事後補一個檢查也行,但那是兩個地方各擋一半,而空字串那一半沒人守。

### 2. 同一條測試的名稱被改過兩次,而兩次都是對的

```
Ch14 一開始   不在白名單的 Origin，回應不帶 Allow-Origin        ← 實測推翻，改掉
Ch14 改成     換一個 Origin 來問，Allow-Origin 不會跟著變
Ch16 改回     不在白名單的 Origin，回應不帶 Allow-Origin        ← 換成陣列之後成立了
```

教訓不是「當初寫錯了」,而是:**測試名稱的對錯是綁在實作的形狀上的。**
換了形狀就要回頭讀一次那些名稱還成不成立 —— 而註解也是,
那條測試上面那段「origin 給字串時…」在改完之後跟它下面的測試**在講兩件相反的事**。

### 3. 逗號分隔是環境變數的格式,不是 HTTP 標頭的格式

「測清單裡的第二個 origin」第一版寫成:

```ts
.set('Origin', 'http://localhost:3000,http://localhost:3001')   // ❌
```

`Origin` 標頭永遠只有一個值(就是「我是誰」),瀏覽器不會送逗號分隔的清單。
測第二個的意思是**拿第二個當 Origin 去問**。

而它紅的訊息剛好證明了新行為是對的:`Received: undefined` ——
那個帶逗號的字串不在白名單裡,所以 cors 什麼都沒回。

### 4. 「專案唯一的單元測試」—— 第四次拿掉一個會過期的數字

`docs/專案速查.md` 有兩處寫著「目前只有 `survey.rules.spec.ts`」「專案唯一的單元測試」。
Ch16 加了第二支,那兩句就過期了。

照慣例**把那個數字拿掉**,不要維護它。前三次是 `survey.rules.ts` 檔頭的「四條規則」
(過期三次)與 `CLAUDE.md` 的「18 章課綱」。

順帶掃出另一處從 **Ch10** 就過期的:Render 那張表寫著「環境變數:只有 `DATABASE_URL`」,
而 JWT 兩個變數在六章之前就加上去了。

## 這一章新增的驗證動作

前十五章的驗收都是「跑測試」。這一章有兩件**測試證明不了**的事,所以多了兩個動作:

```powershell
# 1. fail-fast 真的會讓 process 死掉（測試只能證明函式會 throw）
CORS_ORIGIN= pnpm start        # 預期：exit 1，訊息看得懂

# 2. 線上真的換過來了（e2e 看不到部署平台）
curl -s -i -H "Origin: https://evil.example.com" \
  https://survey-backend-0dku.onrender.com/health | grep -i access-control
# 預期：什麼都沒有
```

第二條也定下了一條部署紀律:**新增必填的環境變數時,先在平台上填好,再 push。**
反過來做的話新版本起不來,而 Render 免費方案沒有自動回滾。
