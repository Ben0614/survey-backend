## 核心概念

### 一句話:e2e 全綠也抓不到「不好用」

這一章六個交付**沒有一個是 bug 修正**。前十六章的測試從頭到尾都是綠的,
API 也完全照規格運作 —— 問題全部是**「照規格運作,但沒有人能拿它做出一個畫面」**:

| 撞到的地方 | 症狀 |
| --- | --- |
| 列表要顯示題數/填答數 | API 不給 → 十筆問卷要打 21 次請求 |
| 建立一份 5 題的問卷 | 6 次請求,第 3 次失敗留下半成品草稿 |
| 編輯一份問卷 | 1 + N 次請求,而且**題目順序完全改不了** |
| 按下「發布」 | 0 題的問卷可以上架,點進去一片空白 |
| 填寫問卷 | 只答一題也能送出;單選題可以送任意文字 |
| 看結果 | 列表只回一串時間戳;**沒有統計端點** |

Ch15 已經說過同一句話,這一章是它的第二次現場 —— 差別在 Ch15 撞到的是
**安全與正確性**(草稿外流、403 洩漏 id),這一章撞到的是**可用性**。
兩者都要「有人真的去用」才會出現。

### 第二句話:同一份資料的兩種檢視,對分頁的需求是相反的

這一章的原始命題是「Ch4 定的 `page` / `pageSize` / `sort` / `order` 好不好用」。
答案不是好或不好,是**看你在做哪一種頁面**:

```
逐筆瀏覽（個別回應）  需要分頁 —— 那正是它設計的用途
統計（摘要）          完全不能用 —— 分頁是為了「不給你全部」，統計卻需要全部
```

所以 `GET /surveys/:id/responses/summary` **刻意不分頁**,而它不分頁也不會把
資料搬回來:`groupBy` 在資料庫算完才回,回傳量只跟「有幾題、幾個選項」有關,
**跟填答數無關**。3000 份填答與 30 份填答,回來的東西一樣大。

## 決策取捨

### 整份取代 vs diff(輪 ③)

編輯頁需要一次送出「標題 + 題目 + 順序」。兩條路:

- **整份取代**(選了這條):`PUT /surveys/:id/questions`,一次請求一個交易,
  **順序就是陣列位置** —— 不必為 `order` 另外設計欄位或第二支端點
- diff(依 id 分成 create/update/delete):實務上 master-detail save 的標準做法,
  好處是**保住 id**(附件、稽核紀錄、外鍵都掛在 id 上)

選整份取代的理由是**三條規則湊出來的保證**:`canEditQuestions` 要 `DRAFT`、
`canSubmitResponse` 要 `PUBLISHED`、`canUnpublish` 要零填答
→ **`DRAFT` 的問卷不可能有答案**,全刪重建不會銷毀任何人的填答。

但那是**推導**不是保證,所以交易的第一步是 `responseCount > 0 → 409`。
它預期永遠不觸發,而那正是它存在的理由:哪天有人放寬 `canEditQuestions`,
這裡會大聲失敗,而不是安靜地 cascade 掉別人的答案。

代價寫成了測試:「回傳的題目 id 全是新的」。哪天改成 diff,那條會紅 ——
**那是正確的紅**,它在提醒「這個對外承諾變了」。

### 規則放哪一個檔案(輪 ④)

`CLAUDE.md` 原本寫「新規則一律加進 `survey.rules.ts`」。輪 ④ 的兩條規則
(整份必答、單選答案要在選項裡)講的是**作答**,不是問卷,所以新開了
`src/responses/responses.rules.ts`。

**判準因此改寫成「這條規則屬於哪個概念」,不是「規則都放同一份」。**

順帶一個沒進 rules 的例子:上面那道 `responseCount > 0` 的保險留在 service。
`survey.rules.ts` 那幾條回答「這件事現在能不能做」,而使用者**真的做得到**那件事;
那一條回答的是「我推導出來的前提還成立嗎」,預期永遠不觸發 —— **它是斷言,不是規則。**

### N+1 什麼時候可以接受(輪 ⑤a)

輪 ① 才剛消掉一個 N+1,輪 ⑤a 又刻意留了一個(簡答題的樣本每題查一次)。
**判準不是「有沒有 N+1」,是 N 有沒有上界:**

```
輪 ①   N = 這一頁的問卷數     使用者改 pageSize 就能拉大 → 沒有上界 → 必須消掉
輪 ⑤a  N = 這份問卷的簡答題數  由問卷本身決定，只算簡答題 → 有上界 → 可以接受
```

### 列表要不要帶關聯資料(輪 ⑤b 推翻了 Ch5 的一句話)

`responses.service.ts` 原本寫著「列表**刻意不帶** answers:100 份作答 ×
每份 20 題 = 2000 筆答案塞進一個回應」。那句話漏掉一件事:**列表是分頁的** ——
一頁 10 筆就是 200 筆,有上界而且由 `pageSize` 控制。

不帶的代價才是真的大:前端要顯示內容得對每一筆再打 `GET /responses/:id`。
判準因此修正成:**「回傳形狀由呼叫端決定」不等於「預設給最少」**,
而是「別讓呼叫端為了拼出一個畫面而發 N 次請求」。

但**列表的 `answers` 不含 `question`** —— 題目屬於問卷,不屬於每一筆填答,
帶著它會讓題目文字在每一筆裡重複一次(10 筆 × 4 題 = 40 份)。

## 踩到的坑

### 1. `@Put('surveyId')` —— 括號裡的字串是路徑,不是參數名

註冊到的路由變成 `/surveys/:surveyId/questions/surveyId`(字面上那八個字),
所有請求 404 **而且是經過 filter 的漂亮 404**,看起來像 service 的 `assertExists` 在叫。
會從 service 一路往回查。真正對接 `:surveyId` 的是 `@Param('surveyId')`,兩者無關。

### 2. `groupBy` 不會回「零筆」的分類

一個「滿意/普通/不滿意」的題目沒有人選「不滿意」時,那一組**根本不在查詢結果裡**。
以 `groupBy` 的結果為基準組裝的話,那個選項會整個消失 —— 畫面上只有兩條長條,
百分比還會算對(2/3、1/3),使用者理解成「這題只有兩個選項」。**沒有錯誤、沒有 0。**

對策是結構性的:**以 `question.options` 為基準去查 `groupBy` 的結果**,
前者天然產生 0,後者天然漏掉。順便也處理了「一份填答都沒有」那個極端。

### 3. `include` 底下要再包一層 `select`

`include: { answers: { id: true } }` 不是有效的 Prisma 查詢。
`include` 收的是「要不要帶這個關聯」,`select` 才是「帶哪些欄位」。

### 4. 推了一份編譯不過的 commit

`@IsNotEmpty({ each: true }` 少一個右括號,而 `git add` 一整包就 commit + push,
**沒有重跑驗證**。結果是 Render 的 build 直接失敗,線上停在舊版 ——
而部署驗證的輪詢等滿十分鐘也沒看到新契約,那就是症狀。

TS 的訊息是「`@IsNotEmpty` 應有 0-1 個引數,但得到 4 個」,那 4 個其實是
`{ each: true }`、`@Validate(...)`、`options`、`string[]` ——
**這類訊息要往上一行看,不是看它指的那一行。**

### 5. 註解過期第七次,而這次是「說了一句不成立的話」

三處:`responses.service.ts` 的「列表刻意不帶 answers」、
`response.entity.ts` 檔頭那張「三支端點三種形狀」對照表、
`find-responses-query.dto.ts` 的「只有分頁,沒有排序」。

三處都是**當時正確、後來被自己的改動推翻**。檔頭裡的對照表尤其危險:
它比程式碼更容易被先讀到。

### 6. 前端的權限判斷跟後端不一致,而沒有任何工具會叫

輪 ① 的刪除鈕寫 `v-if="auth.isAdmin"`(當時後端是 `@Roles(Role.ADMIN)`),
輪 ② 後端放寬成「擁有者或 ADMIN」,**那一行留在原地** —— 於是擁有者看不到
自己問卷的刪除鈕。`tsc` 不會紅,契約 diff 也看不出來:
**型別能從契約產,權限規則不能。**

### 7. 舊測試的前提會因為「規則變嚴」而過期

加上 `canPublish`(一題都沒有不能發布)之後,「調整問卷成發布狀態」那條舊測試
用的問卷是空的,於是從 200 變 409 —— 而它紅的地方跟真正的改動無關,
訊息只會說「expected 200, got 409」。

## 這一章新增的驗證動作

- 每一輪結束都要 `pnpm gen:api` 重產前端契約 —— 六個交付有五個動到契約
- **`swagger.e2e-spec.ts` 的「paths 共 N 條」是設計成會紅的**:新增端點時它強迫你
  回頭確認契約標齊了。這個數字**留著**,因為它是斷言本身;
  專案裡被刪掉的那些數字只是「某份清單有幾項」
- 瀏覽器驗收要**看 console** —— 那是 `createVuetify` 少了 `ssr: true` 造成的
  hydration mismatch 被發現的唯一途徑(畫面完全正常)
