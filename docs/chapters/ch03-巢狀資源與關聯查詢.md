# Ch3 — 巢狀資源與關聯查詢（Questions）

**成果：** Questions 四支端點可用、`GET /surveys/:id` 用 `include` 帶出題目、
`assertExists` 砍掉重複查詢、兩條商業規則與 `publish` / `unpublish`。
`pnpm test:e2e` **36 passed**、`pnpm test` **4 passed**（專案第一支單元測試）。

> **這一章分兩段。** 第一段是 ① 巢狀 CRUD 與 ② `include`/`select`；
> 第二段是 ③ 看 Prisma 產生的 SQL、④ 商業規則與第一次單元測試。
> 切兩段的理由見下方「決策取捨」。**兩段都已完成。**

Ch2 學的是「一個資源怎麼做完 CRUD」，這一章的每一件事都來自同一個新前提：
**題目不能單獨存在，它一定屬於某一份問卷。** 路由形狀、404 的來源、module 之間的依賴、
測試的前提資料，全部是這句話的後果。

## 核心概念

### 子資源：多出來的那一層「父資源存不存在」

Ch2 的每一支端點只需要問一個問題：「這筆資料在不在？」這一章多了一層：**「它的父資源在不在？」**

```ts
async findAll(surveyId: string) {
  await this.surveysService.findOne(surveyId);   // ← 多出來的那一層
  return this.prisma.question.findMany({ where: { surveyId }, orderBy: { order: 'asc' } });
}
```

那行沒有接回傳值，作用是**借 `SurveysService` 丟例外** —— 跟 Ch2 的 `update` 借自己的 `findOne`
是同一個手法，差別只在借的對象是別人。

**少了它會怎樣，答案跟直覺不同 —— 而且兩個地方的下場還不一樣。**

| 少掉的那一行 | 結果 | 為什麼 |
| --- | --- | --- |
| `findAll` 的 `surveysService.findOne` | **200 配一個空陣列** | `findMany` 找不到符合的列不是錯誤，是正常結果 |
| `remove` 的 `findOne` | **500** | `delete` 找不到目標時 Prisma 丟 `P2025`，Nest 不認識 |

（兩個都實測過，見作業第 1、2 題。）

第一種特別值得記：**它不會噴任何錯誤**，回應也是合法的 JSON。前端拿到 `200 []` 的時候，
沒有辦法分辨「這份問卷還沒出題」和「根本沒有這份問卷」。

> **判準：子資源的列表端點幾乎都要先確認父資源** —— 因為「查無此列」和「查無此父資源」
> 在資料庫層是同一件事，只有這一層能把它們分開。

`update` / `remove` 走的是另一條路：它們的網址是扁平的（`/questions/:id`），沒有 `surveyId`
可以借，所以借的是 `QuestionsService` 自己的 `findOne`。

### 路由形狀：巢狀與扁平的混合

```text
GET    /surveys/:surveyId/questions   巢狀
POST   /surveys/:surveyId/questions   巢狀
PATCH  /questions/:id                 扁平
DELETE /questions/:id                 扁平
```

不是為了整齊而統一，判準只有一個：**少了父資源，這句話還講不講得完整？**

| | 說得完整嗎 | 結論 |
| --- | --- | --- |
| 「列出題目」 | 列**誰的**題目？不完整 | 網址要帶父資源 |
| 「建立題目」 | 建在**誰**底下？不完整 | 網址要帶父資源 |
| 「改第 `abc123` 題」 | 完整 —— `id` 是 cuid，本來就唯一 | 不需要父資源 |
| 「刪第 `abc123` 題」 | 完整 | 不需要父資源 |

改與刪硬要寫成 `/surveys/:surveyId/questions/:id` 不會多提供任何資訊，卻多了一個
「兩者對不起來」的狀況要處理：`/surveys/A/questions/屬於B的題目` 該回什麼？404？400？
**多一個參數就多一種不一致的可能。**

### 一個 `@Controller()` 只能有一個前綴

上面的混合形狀直接導致一個結構後果：**同一個功能要拆成兩個 controller。**

| 檔案 | 前綴 | 裝什麼 |
| --- | --- | --- |
| `survey-questions.controller.ts` | `surveys/:surveyId/questions` | `@Get()` `@Post()` |
| `questions.controller.ts` | `questions` | `@Patch(':id')` `@Delete(':id')` |

兩個 class 注入的是**同一個 `QuestionsService` 實例**（provider 預設是單例）。

> **路由形狀可以有兩種，但「題目該怎麼被建立」只能有一份。**
> controller 是「網址長什麼樣」的問題，service 是「這件事怎麼做」的問題 —— 兩者本來就不必一對一。

順帶一提：前綴裡**可以放路徑參數**（`:surveyId`），不是只能放固定文字，
底下的 `@Param('surveyId')` 照樣抓得到。

### module 邊界第一次真的起作用

`QuestionsService` 要注入 `SurveysService`，這是**第一次 feature module 依賴另一個 feature module**。
要通必須兩邊都做：

```ts
// surveys.module.ts —— 我允許外面用
exports: [SurveysService]

// questions.module.ts —— 我要用
imports: [SurveysModule]
```

只做一邊會在啟動時就失敗（Nest 找不到可注入的零件）。

Ch2 寫 `surveys.module.ts` 時刻意留空 `exports`，並註明「等 Ch3 的 `QuestionsModule` 需要它時再加」——
現在兌現了。**沒 export 就等於 private，這是 module 邊界的意義。**

對照組是 `PrismaService`：它同樣來自別的 module，卻誰都不必 import，因為 `PrismaModule` 是
`@Global()`。

> **`@Global()` 是刻意的例外（全應用共用一個連線池），不要套用到業務 service。**
> 全部 `@Global()` 等於沒有 module 邊界 —— 「誰用了誰」就再也看不出來了，
> 而那正是日後拆分或重構時唯一能依賴的資訊。

### `include`：把關聯資料一起帶回來

`schema.prisma` 裡的 `questions Question[]` 是**虛擬欄位**，不對應任何資料庫欄位（Ch1 講過），
所以 Prisma 預設不會回傳它。加了 `include` 才會：

```ts
const survey = await this.prisma.survey.findUnique({
  where: { id },
  include: {
    questions: { orderBy: { order: 'asc' } },
  },
});
```

| | 意思 |
| --- | --- |
| `include` | 本表欄位**全要**，額外再帶關聯 |
| `select` | **只要我列的**（連純量欄位也是，沒列的都不回） |

同一層互斥。值可以是 `true`（全帶、不排序）或一個物件（可放 `orderBy` / `where` / `select`，甚至巢狀 `include`）。

**`orderBy` 不能省** —— 表沒有固有順序，這是 Ch1 的老話題。實測拿掉之後，
Prisma 回的是**插入順序**，跟你要的 `order` 無關（作業第 3 題）。

**回傳型別自己就跟著變了。** 加了 `include` 之後，`findOne` 的型別從 `Survey` 變成
`Survey & { questions: Question[] }` —— 我們沒有寫任何型別註記。這是 Prisma 型別系統最有感的地方，
把游標移上去看一眼。

**代價要記著：** `SurveysService.findOne` 有四個呼叫者，其中三個（`update`、`remove`、
`QuestionsService`）只是借它丟 404、根本不看回傳值，但它們現在也會一起把題目撈出來。
現階段接受 —— 「這一次 `include` 到底跑了幾句 SQL」正是第二段打開 query log 要親眼確認的第一件事。

### 兩個新的驗證裝飾器

```ts
@IsEnum(QuestionType)
type: QuestionType;

@IsArray()
@IsString({ each: true })
options: string[];
```

**`QuestionType` 同時是值也是型別。** `@IsEnum(QuestionType)` 用的是「值」（執行期要拿它比對），
`type: QuestionType` 用的是「型別」（編譯期的事）。一次 `import` 兩種用途都拿到 ——
這是 TypeScript 的 `enum` 比較特別的地方。

**`{ each: true }` 是「套用到每一個元素」**，幾乎所有 `@Is...` 都支援。
少了它，`@IsString()` 的意思會變成「這個陣列本身必須是字串」，永遠不會通過。

## 決策取捨

### `order` 不進 DTO，由 `count()` 算

前端各自算容易撞號，而 Ch1 決定過不加 `@@unique([surveyId, order])` —— 撞了資料庫也不會擋。
**既然沒有守門員，就不要把球交給外面。**

已知的洞：`count` 和 `create` 是兩次獨立的查詢，兩個請求同時進來可能都讀到 2、都寫 `order: 2`。
現階段接受，根治要靠交易（Ch5）。

還有一個洞是刪除造成的：刪掉中間某題之後 `order` 出現空隙（0,1,2 刪掉 1 → 剩 0,2），
下一次 `count()` 會回 2 而撞到既有的那題。重排題目是 Ch4 之後的事。

### `UpdateQuestionDto` 全開，不用 `OmitType` 擋掉 `type`

`PartialType(CreateQuestionDto)` 讓 `title` / `type` / `options` 都可改。代價是
可以把 `SINGLE_CHOICE` 改成 `TEXT` 卻留著 `options`，做出「不需要選項卻有選項」的髒資料。

另一個選項 `PartialType(OmitType(CreateQuestionDto, ['type']))` 沒有被採用，理由有兩層：

1. **這一章的主題不是驗證。**
2. **`OmitType` 擋掉的方式不乾淨。** 沒有裝飾器的屬性會被 `whitelist` **無聲丟掉** ——
   不是回 400 說「不准改」，而是前端送了 `type`、沒生效、也沒有任何錯誤訊息。
   要真的拒絕得改用 `forbidNonWhitelisted`，那是一個全域決定。

「`type` 與 `options` 要一致」本質上是一條**商業規則**，適合跟第二段那條
「`DRAFT` 才能改題目」放在一起處理。

### 沒有 `GET /questions/:id`

`QuestionsService` 有 `findOne`，但 controller **刻意不開這支路由**。

寫它是三行的事，但它不在 Ch3 的範圍、也就沒有任何測試。
**一個對外開放、沒被驗證過的端點比沒有它更糟** —— 前端會在你不知道的時候用上它，
然後它壞掉時沒有人會先發現。

同理，`questions.controller.ts` 這個檔案本身也是等到真的有 `PATCH` 時才建立的。
跟 Ch2「先不 exports」是同一條原則：**不要預先開放。**

順帶帶出一個觀念：**service 的方法不一定要對應到端點。**
`findOne` 存在純粹是因為 `update` 和 `remove` 都需要「不存在就 404」，抽出來就不必寫兩次。
service 是按**要做的事**切的，不是按路由切的。

### `include` 一律帶題目，不由 query 決定

`GET /surveys/:id` 這一章永遠帶題目。「讓前端用 `?include=questions` 決定要不要帶」
是 Ch4 的事（query string 的轉型與驗證是那一章的主題）。

### 這一章切成兩段

Ch3 的內容比 Ch2 多，而且後半（看 SQL、N+1、商業規則與單元測試）跟前半
（巢狀 CRUD、`include`）是兩種不同的工作。切開的好處是第一段可以先跑綠、先 commit，
不會把四塊東西堆在一起做到失去節奏。

## 踩到的坑

| # | 症狀 | 根因 |
| --- | --- | --- |
| 1 | `pnpm start:dev` 成功，但端點全部 404 | `QuestionsModule` 忘了註冊進 `AppModule` |
| 2 | 「id 不存在回 404」綠燈，但 404 邏輯從沒被執行 | 那個 404 來自「Nest 找不到路由」 |
| 3 | 拔掉 `@IsEnum` 之後回 500，看起來像 Prisma 的問題 | `whitelist` 只認裝飾器，兇手在 `setup-app.ts` |
| 4 | 驗證測試拿到 `expected 400, got 404` | 測試打了 `nonexistent-id`，變因不只一個 |
| 5 | 每次失敗的組合都不一樣，紅的常是上一章的測試 | Jest 並行跑測試檔，而它們共用同一個測試資料庫 |
| 6 | 複製測試忘了改動詞（**第三、四次**） | 都是「從對照版本複製」 |
| 7 | 註解說「沒有 exports」，但已經有了（**第三次**） | 改程式碼時沒回頭看註解 |

下面挑四個展開。

### 1. 「跑起來了」不等於「接上了」

`QuestionsModule` 忘了寫進 `AppModule.imports`，`pnpm start:dev` **照樣成功**。

因為那個 module 不在依賴樹上，Nest 根本沒去建立它 —— 裡面寫什麼都不會報錯，
controller 不會被掃描、service 不會被實例化。

> **沒被載入的程式碼不會報錯。** 這跟「程式碼有錯會報錯」的直覺相反，
> 而且它偽裝成「我的路由寫錯了」，會讓人往完全錯的方向查。

### 2. 假綠的第五種樣態：端點還沒接上，404 測試也會綠

Ch2 記了四種假綠，這是第五種，而且它**跟坑 1 是連體嬰**。

第一次跑 `PATCH` 那組出來是「2 紅 1 綠」，三條的網址都少了一個 `s`（打成 `/question/`）：

```text
× 修改題目                      expected 200, got 404
√ id 不存在時回 404             ← 綠的
× options 含有非字串元素時回 400  expected 400, got 404
```

那條綠的，它的 404 來自「Nest 找不到路由」，不是來自 service 丟的 `NotFoundException`。
**404 的邏輯一行都沒被執行過，測試卻是綠的。**

更麻煩的是**它的診斷價值是負的**：看到「兩紅一綠」，直覺會去查那兩條有什麼不一樣，
但三條錯在同一件事，綠的那條只是剛好被自己的錯誤救了。

> **判準：同一組測試裡「404 那條綠、其他全紅」時，先懷疑路由沒接上，不要先看實作。**

### 3. `whitelist` 只認驗證裝飾器，不認 TypeScript 的型別宣告

為了看「資料庫的 enum 會不會擋住錯的值」，把 `@IsEnum(QuestionType)` 拔掉試跑 ——
結果**根本沒到資料庫**：

```text
@IsEnum 被拔掉
  → whitelist 判定「type 沒有驗證裝飾器」→ 整個屬性丟掉
  → service 收到 dto.type === undefined
  → prisma.create 缺必填欄位 → 500
```

> **`type: QuestionType` 這個型別註記對 `whitelist` 毫無意義。**
> TypeScript 的型別在編譯後就消失了，執行期擋不了任何東西。

這是 Ch2 坑「新增欄位怎麼傳都存不進去」的現場重演，只是這次的症狀更會騙人：
它看起來像「Prisma 的問題」，兇手其實在 `setup-app.ts` 的 `ValidationPipe`。

### 7. 註解過期，第三次

補債時才發現 `surveys.module.ts` 的檔頭還寫著：

```ts
// 沒有 exports —— 目前沒有別的 module 需要用 SurveysService。
// 等 Ch3 的 QuestionsModule 需要它時再加，**不要預先開放**
```

底下是 `exports: [SurveysService]` —— **早就加了。**

Ch2 已經為這件事寫過一節（「改程式碼會讓註解過期」），這是第三次。
而且這一次特別誤導：它讓人以為 module 邊界還是關著的，而「什麼時候該開放 export」
正是這一章的教學重點之一。

同一輪還找到兩處：`surveys.service.ts` 的 `findOne` 沒跟上 `include`、
`surveys.e2e-spec.ts` 自稱「動線終點」（questions 的 e2e 接上去之後就不是了）。

> **共同觸發條件是「這次改的是 A 檔案，而描述 A 的那句話在 B 檔案」。**
> 三次都是這個形狀。改完一個決策後，值得搜尋一次那個決策的關鍵字。

### 其他三條（不展開）

- **坑 4：測試裡除了「被驗的那件事」，其他前提都要保持正常。** 驗證測試若打
  `nonexistent-id`，平常是綠的（驗證比 service 早跑），但驗證真的失效時會拿到
  `expected 400, got 404` —— 訊息把人帶往「路由或父資源有問題」的錯方向。建一份真的問卷，變因只剩一個。
- **坑 5：`maxWorkers: 1`。** `.env.test` 隔離的是「測試 vs 開發」，`maxWorkers` 隔離的是
  「測試 vs 測試」，兩層不同。Ch2 建的隔離只擋了前者，第二個會清資料庫的 e2e 檔一出現就穿幫了。
  **隔離做得夠不夠，要等第二個參與者出現才知道。**（設定說明在 `docs/設定檔導讀.md`。）
- **坑 6：複製測試忘了改動詞，第三、四次。** 已升級成習慣：**貼上的當下就核對動詞與路徑跟
  `describe` 一致。**

### 兩個新的判準（不算坑，但是這一章換來的）

**`PartialType` 和 Prisma 的 `undefined` 是兩個各自獨立的機制。**

「空 body 回 200 且不改動任何欄位」這條測試同時保護著兩件事：

| 機制 | 負責什麼 | 弄壞它會怎樣 |
| --- | --- | --- |
| `PartialType` | 讓 `{}` **通過驗證** | 400 |
| Prisma 的 `undefined` | 「不要動這個欄位」 | 200，但資料被清空 |

只斷言 `.expect(200)` 只驗到第一個。要兩個都保護，回應 body 也得斷言。

**測試名字要寫「保證什麼行為」，不是「用了什麼工具」。**

一度把那條測試命名為 `'PartialType測試'`。兩個問題：哪天 `PartialType` 換成手寫 DTO，
名字就變成謊；而且紅燈時 Jest 只印名字 —— 「PartialType測試 失敗」不告訴你什麼壞了。
改成 `'空 body 回 200 且不改動任何欄位'`。

## 作業

每一題都是同一個形狀：**把某個東西弄壞，看測試會不會叫、以及叫的方式對不對。**
這是 `ch02`「綠燈不等於有被保護」那節的操作版本。

1. 把 `questions.service.ts` 的 `remove` 開頭那行 `await this.findOne(id)` 註解掉，
   跑 `pnpm test:e2e -- test/questions.e2e-spec.ts`。哪條紅？回的是幾？
2. 換成把 `findAll` 開頭那行 `await this.surveysService.findOne(surveyId)` 註解掉。
   這次哪條紅？回的是幾？**跟第 1 題一樣嗎？**
3. 把 `surveys.service.ts` 的 `include` 從
   `questions: { orderBy: { order: 'asc' } }` 改成 `questions: true`，
   跑 `pnpm test:e2e -- test/surveys.e2e-spec.ts`。測試會紅嗎？（先猜再看）
4. 把 `update-question.dto.ts` 的 `extends PartialType(CreateQuestionDto)`
   改成 `extends CreateQuestionDto`。哪幾條紅？
5. 把 `create-question.dto.ts` 的 `@IsEnum(QuestionType)` 那行刪掉。哪幾條紅、

> 每題做完記得改回來。五題都不動 `schema.prisma`，所以不會在 `prisma/migrations/` 留下垃圾。

### 解答

> **五題的結果全部是實際跑出來的**（貼的是真實輸出）。
> `ch02` 的第 3 題是唯一用推導的，這一章沒有例外。

**第 1 題 —— `DELETE` 的 404 那條紅，回 500。**

```text
● Questions (e2e) › DELETE /questions/:id › id 不存在時回 404
  expected 404 "Not Found", got 500 "Internal Server Error"
Tests: 1 failed, 11 passed, 12 total
```

`delete` 找不到目標時 Prisma 丟 `P2025`，Nest 不認識這個錯誤碼，當成沒預期的例外。
這跟 Ch2 作業第 2 題（`update` 少了那一行）是同一個機制。

**這一題在實作時真的發生過** —— 寫 `DELETE` 時漏了那一行，測試當場就抓到了。

**第 2 題 —— `GET` 的 404 那條紅，回 200。跟第 1 題完全不一樣。**

```text
● Questions (e2e) › GET /surveys/:surveyId/questions › surveyId 不存在時回 404
  expected 404 "Not Found", got 200 "OK"
Tests: 1 failed, 11 passed, 12 total
```

**這題才是重點：同樣是「少一行借來的 404」，一個變 500、一個變 200。**

差別在下一步做什麼：`delete` 需要目標存在（不存在就是錯誤），
`findMany` 不需要（找不到符合的列是**正常結果**，回空陣列）。

而 200 比 500 危險得多：

- 500 至少會在 log 裡留下堆疊，而且前端一定會發現
- **200 `[]` 是一個完全合法的回應**，沒有任何地方會亮紅燈。
  前端拿到它，只能顯示「這份問卷還沒有題目」—— 但真相是這份問卷不存在

> 收穫：**「沒有錯誤」不等於「正確」。** 最貴的 bug 都長得像正常回應。

**第 3 題 —— 會紅。**

```text
● Surveys (e2e) › GET /surveys/:id › 帶出題目且依 order 排序
  expect(received).toBe(expected) // Object.is equality
  Expected: 0
  Received: 1
Tests: 1 failed, 16 passed, 17 total
```

如果你猜「不會紅，反正只有兩筆」，那是很自然但錯誤的推論。

拿掉 `orderBy` 之後 Prisma 回的是**插入順序**，而那條測試**故意倒著建**
（先 `order: 1`、再 `order: 0`），所以第一筆拿到的是 `order: 1`。

這就是當初寫那條測試時堅持要倒著建的原因：

> **要驗排序，前提資料的順序就必須跟期望的順序不一樣。**
> 照順序建的話這題會是綠的 —— 那條測試就等於沒在保護排序。

**第 4 題 —— 兩條紅，而且 lint 也會叫。**

```text
● Questions (e2e) › PATCH /questions/:id › 修改題目
  expected 200 "OK", got 400 "Bad Request"
● Questions (e2e) › PATCH /questions/:id › 空 body 回 200 且不改動任何欄位
  expected 200 "OK", got 400 "Bad Request"
Tests: 2 failed, 10 passed, 12 total
```

沒有 `PartialType` 就沒有 `@IsOptional()`，三個欄位全部變回必填：

- `空 body` 那條送 `{}` —— 三個都缺 → 400
- `修改題目` 那條只送了 `title` 和 `options`、**沒送 `type`** → 400

第二條紅得很有價值：它證明「部分更新」不只是空 body 的問題，
**只要少送任何一個欄位就已經不成立了。**

另外 `tsc` 與 `eslint` 會同時報 `'PartialType' is defined but never used` ——
改動一個 `extends` 就讓一個 import 變成孤兒，這是免費的提醒。

**第 5 題 —— 兩條紅，都是 500。而狀態碼會把你帶錯方向。**

```text
● Questions (e2e) › POST /surveys/:surveyId/questions › 建立指定問卷的題目
  expected 201 "Created", got 500 "Internal Server Error"
● Questions (e2e) › POST /surveys/:surveyId/questions › type 不在允許的值之內時回 400
  expected 400 "Bad Request", got 500 "Internal Server Error"
Tests: 2 failed, 10 passed, 12 total
```

第一條就是關鍵：**連合法的請求都掛了。**

拔掉 `@IsEnum` 的直覺是「驗證變鬆，錯的值會溜到資料庫、然後被資料庫的 enum 擋下」。
實際上完全相反 —— `whitelist` 判斷的是「這個屬性**有沒有驗證裝飾器**」，
沒有就整個丟掉，於是 `dto.type` 是 `undefined`，`prisma.create` 缺必填欄位直接炸。

**根本沒有走到資料庫，所以資料庫的 enum 從頭到尾沒有參與。**

至於「你會往哪裡查」：500 的堆疊指向 `prisma.question.create`，
看起來像 Prisma 或資料庫的問題 —— 而兇手在 `setup-app.ts` 的 `ValidationPipe`，
另外兩個檔案之外。

> 收穫：**錯誤發生的位置，通常不是原因所在的位置。**
> 500 的堆疊告訴你「誰倒下了」，不是「誰推的」。

（`eslint` 一樣會報 `'IsEnum' is defined but never used`。這一章兩題都靠它多給一個訊號 ——
**lint 不只是排版**，Ch2 已經用 `no-floating-promises` 說過一次。）

## ③ 打開 query log，看 ORM 底下真正發生什麼事

### 開關怎麼開

`src/prisma/prisma.service.ts` 把 `log` 交給環境變數控制，**預設關**：

```ts
const logQueries = config.get<string>('PRISMA_LOG_QUERIES') === '1';
super({
  adapter: new PrismaPg({ connectionString }),
  log: logQueries ? ['query'] : [],
});
```

- 用 `get` 不是 `getOrThrow` —— 這個變數沒設也要能正常跑
- **預設關**：開著會把每次測試的輸出淹掉，而它只在「想看清楚某段程式碼跑了幾句查詢」時才有用
- 留成開關而不是「改了再改回來」，是因為 Ch4（分頁）與 Ch5（交易）還會用到

它對 `pnpm test:e2e` **也有效**（實測過），但機制跟直覺不同，值得看清楚 ——
這裡一度寫錯過一次：

- `test/setup-env.ts` 確實有讀 `.env`，但它是讀進一個**丟棄用的物件**
  （`config({ path: ENV_PATH, processEnv: devEnv })`），只拿來比對兩個 `DATABASE_URL`
  一不一樣。**它完全沒有碰 `process.env`。**
- 真正把 `.env` 灌進 `process.env` 的是 **`AppModule` 的 `ConfigModule.forRoot()`** ——
  測試建立應用時一樣會執行它。
- `DATABASE_URL` 之所以沒被 `.env` 蓋掉，是因為 `setup-env.ts` **更早**把 `.env.test`
  灌進去了，而 dotenv 不覆寫已存在的變數。

所以結果是：`DATABASE_URL` 用測試資料庫的、`PRISMA_LOG_QUERIES` 用 `.env` 的 ——
**結論對，但如果照「setup-env 載完 .env.test 再載 .env」去理解，下次改動時會推錯。**

> **PowerShell 不吃 `PRISMA_LOG_QUERIES=1 pnpm start:dev`**（那是 bash 語法，會被當成指令名稱）。
> 要臨時開就 `$env:PRISMA_LOG_QUERIES=1; pnpm start:dev`，或直接改 `.env`。

### 怎麼讀那些 log（實際卡住過的地方）

**第一件事：不要在 `pnpm test:e2e` 上讀。** 30 條測試的查詢會全部混在一起，
分不出哪幾句屬於哪個請求；而且 Jest 會替每一行 `console.log` 加上兩層框：

```text
    console.log                                    ← Jest 加的標題
      prisma:query SELECT ...                      ← 只有這行是內容
      at Object.Ru (...logger.ts:13:11)            ← Jest 說 console.log 在哪被呼叫
```

**改用 `pnpm start:dev` + 在 `api.http` 點一個請求**，剛冒出來的那幾行就是它，
一句一行、沒有雜訊。

**第二件事：一句 SQL 只要看三樣東西** —— `SELECT` 了哪些欄位、`FROM` 哪張表、總共幾句。
其餘全是噪音：

| 看到 | 意思 | 要在意嗎 |
| --- | --- | --- |
| `$1` `$2` | **參數佔位符**，值分開送給資料庫 —— 這正是 Prisma 不會有 SQL injection 的原因 | 觀念記著，讀 log 時忽略 |
| `LIMIT $2 OFFSET $3` | `findUnique` 編譯出來自帶的「最多一筆」 | 忽略 |
| `AND 1=1` | Prisma 組 WHERE 時的填充物，永遠成立 | 忽略 |
| `"status"::text` | enum 轉成文字回傳 | 忽略 |
| `AS "sub"` | `count` 被包成子查詢 | 忽略 |

舉一次實際的 `POST /surveys/:surveyId/questions`（修正後）：

```sql
SELECT "Survey"."id", "Survey"."status"::text FROM "Survey" WHERE ("Survey"."id" = $1 AND 1=1) LIMIT $2 OFFSET $3
SELECT COUNT(*) AS "_count$_all" FROM (SELECT "Question"."id" FROM "Question" WHERE "Question"."surveyId" = $1 OFFSET $2) AS "sub"
INSERT INTO "Question" (...) RETURNING ...
```

三句分別對應 `assertExists` → `question.count()` → `question.create()`。
第一句只 `SELECT` 兩欄，就是 `select: { id: true, status: true }` 的樣子。

### 發現 1：`include` 是**兩句**，不是 JOIN

單獨跑 `GET /surveys/:id`（實際 log，`"public".` 前綴已略）：

```sql
SELECT Survey.*   FROM Survey   WHERE id = $1
SELECT Question.* FROM Question WHERE surveyId = $1 ORDER BY "order" ASC
```

Prisma 對一對多的預設策略是**分開查、在應用層組裝**（`relationLoadStrategy` 預設 `query`；
PostgreSQL 可以改成 `join` 走 lateral join）。

**為什麼預設不用 JOIN —— JOIN 會讓資料重複膨脹。**

一份問卷 5 題，JOIN 回來是 5 列，而**每一列都重複帶著整份問卷的 `title` / `createdAt` / `status`**。
再多一層更慘：

```text
survey ─ 5 questions ─ 每題 10 answers
JOIN → 50 列，每列重複著問卷資料與題目資料
```

這叫 cartesian explosion，關聯越多層乘得越兇。兩句查詢則是 1 + 5 筆，各自只帶自己的欄位。

**代價是多一次網路往返**，對 Neon 這種遠端資料庫是真的成本。所以這是明確的取捨：
**用「多一次往返」換「不重複傳輸 + 語義單純」。**

語義那半在 Ch4 會有感：`include` 配分頁時，JOIN 的 `LIMIT 10` 限制的是 **join 之後的列數**、
不是問卷數 —— 分開查就沒有這個陷阱。

> **這不是 N+1。** N+1 是「1 句查父 + **N 句**各查一個子」，查詢數**隨資料量成長**；
> 這裡不管幾題永遠是兩句。差別在「固定 2」和「隨資料量成長」——
> 這也是為什麼 `include` 是 N+1 的**解法**而不是成因。

### 發現 2：`PATCH /surveys/:id` 有一句是純粹浪費的

```sql
SELECT Survey.*   FROM Survey   WHERE id = $1                       -- 確認存在，必要
SELECT Question.* FROM Question WHERE surveyId = $1 ORDER BY ...    -- ← 純浪費
UPDATE Survey SET title = $1, updatedAt = $2 WHERE id = $3          -- 正事
```

`update` 的第一行是 `await this.findOne(id)`，而 `findOne` 帶著 `include`。
它**把題目全部撈回來，然後整個丟掉** —— 那一行沒有接回傳值，只是借它丟 404。

這正是加 `include` 當下就預告過的代價（`surveys.service.ts` 的註解裡寫著），現在有數字了。

### 發現 3：`GET /surveys/:surveyId/questions` 把同一批題目撈了**兩次**

這個比上一個嚴重，而且是實測才發現的（原本沒預期到）：

```sql
SELECT Survey.*   FROM Survey   WHERE id = $1                     -- 借它丟 404
SELECT Question.* FROM Question WHERE surveyId = $1 ORDER BY ...  -- include 撈的，丟掉
SELECT Question.* FROM Question WHERE surveyId = $1 ORDER BY ...  -- findAll 自己撈的
```

**最後兩句一模一樣。** 第一次的結果原封不動被丟掉。

而且**不打開 log 永遠不會有人發現**：回應完全正確、測試全綠、沒有任何錯誤訊息。

> 這是 ③ 最該帶走的一句：**ORM 讓你用一行程式碼換到不知道幾句 SQL。**
> 「程式碼看起來很短」跟「它做的事很少」是兩回事，而唯一能分辨的方法就是把 log 打開看。

### 這些浪費為什麼非處理不可

現在題目少，感覺不出來。**問題在它隨資料量線性成長** ——
一份 500 題的問卷：

- 每次 `PATCH /surveys/:id` 只為了改標題，就跨網路搬 500 筆題目再丟掉
- 每次 `GET /surveys/:surveyId/questions` 搬 **1000 筆**（同一批兩次）

**平常測不出來、資料長大才爆**，是最難察覺的一類效能問題。

### 修正：`assertExists`

把「確認存在」和「取得完整內容」分成兩支方法：

```ts
/** 只確認問卷存在（並取得判斷用的狀態），不撈題目。 */
async assertExists(id: string) {
  const survey = await this.prisma.survey.findUnique({
    where: { id },
    select: { id: true, status: true },   // 只要兩欄，完全不碰 Question
  });
  if (!survey) throw new NotFoundException('問卷不存在');
  return survey;
}
```

| 呼叫者 | 該用哪一支 |
| --- | --- |
| `GET /surveys/:id`（controller） | `findOne` —— 要完整內容，維持 `include` |
| `SurveysService.update` / `remove` | `assertExists` |
| `QuestionsService.findAll` / `create` | `assertExists` |

命名用 `assertExists` 而不是 `findOneLite`：**它的用途是斷言、不是取值**。
名字說清楚「呼叫我是為了讓不存在的情況直接中止」，就不會有人拿它的回傳值當完整資料用。

`select: { id: true, status: true }` 裡的 `status` 不是湊的 —— ④ 的
「`DRAFT` 才能改題目」剛好需要它，兩個需求一次滿足。

**改完之後實測**（`PRISMA_LOG_QUERIES=1`，`GET /surveys/:surveyId/questions`）：

```sql
SELECT "Survey"."id", "Survey"."status"::text FROM "Survey" WHERE ...
SELECT "Question"."id", ... FROM "Question" WHERE "Question"."surveyId" = $1 ORDER BY "Question"."order" ASC OFFSET $2
```

**兩句。** 原本夾在中間那句重複的 `SELECT ... FROM "Question"` 消失了。
E2E 仍然是 30 passed —— 行為完全沒變，只是少撈東西。

> 這一步的驗收方式值得記：**行為沒變的重構，測試數字必須一模一樣。**
> 如果 30 變成 29 或 31，那就不是重構，是不小心改了行為。

## ④ 商業規則與專案第一支單元測試

前面三段（①②③）都在處理「資料怎麼進出」。這一段第一次出現**「什麼情況下不准做」** ——
也就是商業規則。它換來三樣新東西：一個新的狀態碼、一個不是 provider 的檔案、
還有專案至今唯一的單元測試。

### 兩條規則，以及它們為什麼不是同一條

`LEARNING.md` 原本寫的是「`DRAFT` 才能自由增刪題目；一旦有人填答就不能再改題目」。
寫到這裡才發現**那是兩條不同的規則**，而且它們只在「已發布但還沒人填答」時給出不同答案。

| 規則 | 判準 | 為什麼 |
| --- | --- | --- |
| 能不能**改題目** | `status === 'DRAFT'` | 已發布代表**可能有人正在填寫**，那跟「目前有幾筆填答紀錄」不是同一件事 —— 有人開著頁面還沒送出時，填答數仍然是 0。用填答數當判準會漏掉這些人 |
| 能不能**撤回發布** | 還沒有任何填答 | 這是「要改已發布的問卷」的正式路徑：先撤回、再改。已經有人填過就不給撤回，否則舊答案會對不上新題目 |

> 這一段最值得帶走的不是結論，是**「把一句話拆成兩句話」這個動作本身**。
> 原本那句讀起來很順，是因為它把兩個判準寫在一起 —— 而寫程式時必須各自挑一個。

### 409 Conflict：第三種「拒絕」

專案到目前為止只有兩種拒絕：`400`（body 不合規則，`ValidationPipe` 丟的）和
`404`（東西不存在）。這一章多了第三種。

| 狀態碼 | 語義 | 為什麼不選它 |
| --- | --- | --- |
| **409 Conflict** | 請求沒問題，是**跟資源目前的狀態**衝突 | ← 選這個 |
| 403 Forbidden | 你沒有權限 | 這不是權限問題，換一個人來也一樣不能改 |
| 400 Bad Request | 請求本身有錯 | body 完全合法；而且會跟 `ValidationPipe` 的 400 混在一起，前端分不出來 |

**判準：先問「換一個人來會不會成功」。** 會 → 403；不會，而且是因為東西現在的狀態 → 409。

### 規則寫成純函式，而不是 provider

新檔 `src/surveys/survey.rules.ts`：

```ts
export function canEditQuestions(status: SurveyStatus): boolean {
  return status === SurveyStatus.DRAFT;
}

export function canUnpublish(responseCount: number): boolean {
  return responseCount === 0;
}
```

兩個刻意的決定：

**① 沒有 `@Injectable()`，也不註冊進任何 module。**
到這一章為止看到的零件（`SurveysService`、`PrismaService`）都是 provider，很容易以為
「NestJS 的東西都要注入」。不是 —— **DI 是用來解決「我需要別人幫我準備好的東西」**。
這兩個函式沒有依賴、沒有狀態，`import` 就能用，包成 provider 只是多繞一圈。

**② 回 `boolean`，不直接 `throw`。**
丟 `ConflictException` 是 HTTP 的事，由 service 翻譯。規則檔一旦認識 HTTP，
「不必假裝發請求就能測」這個唯一的好處就沒了。

### 專案第一支單元測試

`src/surveys/survey.rules.spec.ts` —— 用 `pnpm test` 跑（`rootDir: src`、`*.spec.ts`，
設定在 `package.json`）。這個指令從 Ch0 到現在都靠 `--passWithNoTests` 空轉。

它跟你寫過的 e2e 最大的差別是**它沒有什麼**：

| | e2e (`*.e2e-spec.ts`) | 單元測試 (`*.spec.ts`) |
| --- | --- | --- |
| `beforeAll` | `Test.createTestingModule` → `app.init()` | 不需要 |
| `beforeEach` | `resetDb(prisma)` | 不需要 |
| 怎麼呼叫 | `request(app.getHttpServer()).patch(...)` | 直接呼叫函式 |
| mock | 不 mock（連真實資料庫） | 沒有東西可 mock |
| 一次要多久 | **約 12 秒** | **0.5 秒** |

那 11 秒半全部花在啟動 Nest 和連 Neon 上。**能省掉它們，唯一的原因是被測的東西沒有依賴。**

> **這是全專案唯一適合單元測試的地方。** 其他 service 幾乎都是
> 「收參數 → 交給 Prisma → 回結果」，把 Prisma mock 掉之後測到的只剩下 mock 自己。
> 判準不是「這段程式碼重不重要」，是**「拿掉外部依賴之後還剩下什麼」** ——
> 剩下判斷邏輯就值得單元測試，什麼都不剩就別寫。

### 規則套在哪，以及 `include` 的第二次出場

改題目的規則要擋三支（`QuestionsService` 的 `create` / `update` / `remove`），
但它們手上的資訊不一樣：

- `create` 有 `surveyId` → `assertExists` 回傳值裡就有 `status`（`select` 早就準備好了）
- `update` / `remove` 只有 `question.id` → 拿不到問卷

第二種的解法是把 `QuestionsService.findOne` 改成：

```ts
const question = await this.prisma.question.findUnique({
  where: { id },
  include: { survey: true },
});
```

**這是 `include` 第二次出場，而且方向反過來了。** 前面是「問卷帶題目」（一對多），
這次是「題目帶問卷」（多對一）。兩個方向都走得通，因為 `schema.prisma` 兩邊都宣告了
關聯欄位（`Survey.questions` 與 `Question.survey`），而它們靠的是**同一根外鍵**
`Question.surveyId` —— 只是查的方向相反。

形狀不同，用法也跟著不同：

| | 拿到什麼 | 要不要 `orderBy` | 要不要判 null |
| --- | --- | --- | --- |
| `survey.include.questions` | `Question[]`（0 到 N 筆） | **要**（陣列有順序問題） | — |
| `question.include.survey` | `Survey`（一定是 1 筆） | 不需要（單筆沒有順序） | **不需要** |

不必判 null，是因為 `surveyId` 在 schema 是 `String` 而不是 `String?` ——
**題目沒有「不屬於任何問卷」這個狀態**，外鍵約束也保證它指到的問卷存在。

還有一個對照：`include: { x: true }` 跟 `include: { x: { orderBy: ... } }` 是**同一件事的兩種寫法**。
`true` 就是「不加任何條件」的簡寫，要指定什麼才換成物件。一對一那邊寫 `true`
不是偷懶，是**那裡根本沒有 `orderBy` 可寫**（寫了 TypeScript 會直接報錯）。

### 為什麼這裡用 `include` 不用 `select`

③ 才剛因為「多撈東西」開了 `assertExists`，這裡卻用 `include: { survey: true }`
把整筆問卷撈回來，看起來矛盾。**判準是「有沒有上界」，不是「有沒有多撈」：**

| | 多撈的是 | 隨資料成長嗎 |
| --- | --- | --- |
| ③ 修掉的 | 一份問卷的**所有題目** | 會 —— 500 題就搬 500 筆 |
| 這裡 | 一筆問卷的**幾個欄位** | 不會 —— 永遠 1 筆 |

為了省 4 個欄位而寫得更囉嗦不划算；為了省 500 筆才划算。

### 動作型端點：`PATCH /surveys/:id/publish`

`status` **沒有**加進 `UpdateSurveyDto`，而是開兩支自己的路由。
`create-survey.dto.ts` 的註解早就寫了「發布是一個獨立的動作而不是建立時的參數」，這裡是兌現。

理由：發布不只是改一個欄位，它還帶著「撤回時要檢查有沒有人填答」這種規則。
混進 `update` 之後，那支方法就得依 dto 裡有沒有 `status` 分岔判斷，**而網址完全看不出來這件事會發生**。

兩個順帶的點：

- **不會跟 `@Patch(':id')` 撞。** controller 裡講過「路由依宣告順序比對」，
  但那只發生在**同樣段數**的路由之間 —— `:id` 一段、`:id/publish` 兩段，不可能撞上。
- **沒有 `@Body()`，所以不需要 DTO。** 要做什麼已經寫在網址裡了。
  （e2e 一度多送了 `.send({ status: 'PUBLISHED' })`，那個 body 進來就被丟掉 ——
  留著的壞處是**測試在說謊**，讀的人會以為這支 API 需要 body。）

### 冪等：連回應的形狀都算

PATCH 應該是冪等的 —— 送幾次結果都一樣，第二次不該被當成失敗。所以重複發布回 200 而不是 409。

但實作時踩到一個不明顯的地方。最初的寫法是：

```ts
const survey = await this.assertExists(id);
if (survey.status === SurveyStatus.PUBLISHED) {
  return survey;                     // ← 提早 return
}
return this.prisma.survey.update({ ... });
```

兩個出口回傳的**形狀不一樣**：提早 return 的是 `assertExists` 的 `{ id, status }`
（因為 ③ 給它加了 `select`），正常路徑回的是完整 `Survey`。於是同一支 API：

```json
// 第一次
{ "id": "abc", "title": "員工滿意度調查", "status": "PUBLISHED", "createdAt": "...", "updatedAt": "..." }
// 第二次
{ "id": "abc", "status": "PUBLISHED" }        ← title 不見了
```

> **冪等不只是「資料庫狀態一樣」，回應內容也算在內。**

修法是拿掉那個判斷，永遠走 `update` —— 把已發布的設成已發布是無害的。
一個出口、一種形狀，代價是那句 UPDATE 照樣發出去。

這個坑的來源值得記：**它是 ③ 的 `select` 造成的副作用**，而設計 ④ 的時候沒接上。
改了一支方法的回傳形狀，就要回頭想「誰在用它、用來做什麼」。

### `count()` vs 撈出來數 `.length`

`unpublish` 要知道「這份問卷有幾筆填答」：

```ts
const responseCount = await this.prisma.response.count({
  where: { surveyId: id },
});
```

**不要**寫成 `include: { responses: true }` 再取 `.length`。兩層理由：

1. `count` 發出的是 `SELECT COUNT(*)`，**數數在資料庫裡完成，網路上只回一個數字**。
   `.length` 要把 500 筆完整資料搬過網路，只為了看它有幾筆 ——
   **正是 ③ 剛消滅掉的那種浪費，換了個位置。**
2. Ch4 加分頁之後，`.length` 只會是「這一頁幾筆」；`count` 完全不受 `take` / `skip` 影響，
   因為它根本沒有在取資料。

例外：**反正都要撈那筆資料時**，可以叫 Prisma 順便附上數字 ——
`include: { _count: { select: { responses: true } } }` → `survey._count.responses`。
「回一份問卷給前端，順便告訴他有幾人填答」就適合這樣寫。

> 判準：**要的是「數量」就用 `count`；只有當你反正都要那批資料時，`.length` 才不算浪費。**

### `Response` 還沒有端點，規則卻現在就寫

`Response` / `Answer` 要 Ch5 才有 controller/service，但**資料表在 Ch1 的 migration 就建好了**，
所以 `prisma.response.count()` 現在就跑得動 —— 只是實務上一定回 0（沒有任何管道能建立填答）。

規則現在寫下去不是白寫，它在等 Ch5。而 e2e 用 `prisma` 直接塞一筆來驗它：

```ts
await prisma.response.create({ data: { surveyId: survey.id } });
```

只要給外鍵就好（`id` / `createdAt` 都有 `@default`）。這剛好符合專案原則
**「前提資料一律用 prisma 直接建，不透過 API」** —— 而這次是唯一選擇，因為 API 根本還不存在。

## 第二段踩到的坑

### 8. `tsc` 綠燈不代表跑得起來（絕對路徑 import）

```ts
import { canEditQuestions } from 'src/surveys/survey.rules';   // ← VS Code 自動補的
```

`pnpm exec tsc --noEmit` **0 errors**，但 `pnpm test:e2e` 是：

```text
Cannot find module 'src/surveys/survey.rules' from '../src/questions/questions.service.ts'
Test Suites: 3 failed, 3 total
Tests:       0 total
```

**三個測試檔全部連跑都跑不起來。** 原因是 `tsconfig.json` 的 `"baseUrl": "./"`
只影響**編譯期**的型別解析；編譯後 `dist/questions/questions.service.js` 裡的
`require('src/...')` 沒有 `./` 開頭，Node 當成套件名去 `node_modules` 找，當然找不到。

同一輪踩了**兩次**，兩次都是 VS Code 自動 import 幫忙補的路徑。

> **判準：看到 import 路徑開頭是 `src/`，直接改成相對路徑。**
> 更一般的教訓：**型別檢查和模組解析是兩套規則。** `tsc` 過只代表「型別說得通」，
> 不代表「執行時找得到」。三項驗收要全跑，不能只跑 `tsc`。

### 9. 假綠的第六種：查詢語法對、查錯欄位

```ts
const responseCount = await this.prisma.response.count({
  where: { id },              // ← 應該是 { surveyId: id }
});
```

`Response.id` 是合法欄位，型別完全正確 —— 但它問的是「**回覆的 id** 等於這個字串」，
而傳進去的是 survey 的 id。兩者永遠不相等 → `responseCount` 恆為 0 →
`canUnpublish(0)` 恆為 true → **「有人填答就不能撤回」這條規則從來不會生效。**

`tsc`、`lint` 全綠，e2e 也全綠（因為那時還沒寫那條測試）。

> 前五種假綠都跟「測試本身寫錯」有關，這一種不同：**測試沒寫錯，是程式碼寫錯，
> 而所有靜態工具都看不出來。** 唯一的偵測器是「有填答時 unpublish 回 409」那條 e2e。
>
> **寫規則的當下就要寫那條測試**，隔一天再補就只是在驗證「現在的行為」。

### 10. 規則判斷寫反（少一個 `!`）

```ts
if (canEditQuestions(survey.status)) {     // ← 少了 !
  throw new ConflictException('問卷已發布，無法新增題目');
}
```

意思變成「可以改 → 丟 409」：`DRAFT` 全被擋、`PUBLISHED` 反而放行。

**它是被既有的 30 條 e2e 抓到的** —— 那些測試的前提資料全是 `DRAFT` 問卷，
所以 POST / PATCH / DELETE 一次全紅。

> 這是「回歸測試」第一次真的發揮作用：**它們保護的不是自己那條路徑，
> 是「你以為沒動到的地方」。** 加新功能時先跑一次既有測試，就是在買這個保險。

### 11. 借錯規則函式

```ts
if (!canEditQuestions(survey.status)) {          // 意思是「不能改題目」
  throw new ConflictException('問卷為已發布狀態'); // 但想問的是「是不是已發布」
}
```

今天兩者算出來一樣，是因為兩條規則**碰巧**都看 `status === DRAFT`。但它們是不同的概念：
哪天「能不能改題目」的規則變了（例如「發布後 24 小時內仍可改」），
`publish` 的冪等判斷會**跟著一起變**，而那完全不是預期的。

> **判準：規則函式只該用在它被命名的那件事上。** 名字對不上就別借，即使算出來一樣。
> 單純的狀態比對就直接寫 `survey.status === SurveyStatus.PUBLISHED`。

### 12. 註解過期，第四、五次

第四次在補 `PRISMA_LOG_QUERIES` 時（三處把 `setup-env.ts` 的機制寫錯，見 ③）。
第五次是 `findOne` → `assertExists` 這次改動，`surveys.service.ts` 有三處沒跟上：
檔頭兩處，加上 `findOne` 結尾那段「代價：update / remove / QuestionsService 都只是
借這支丟 404……」—— **那段話描述的代價，正是這次改動消滅掉的東西。它是一張已經還掉的欠條。**

> 這一章的建議升級成一個具體動作：**改行為時，搜尋一次被你改掉的那個名字**
> （這次是搜 `findOne`），三處會全部跳出來。

### 13. 其他兩條（不展開）

- **`api.http` 的 `###` 不只是註解，是「請求到此結束」的信號。**
  `@surveyId = ...` 那行前面少了一條 `###`，它就被當成前一個 POST 的 JSON body
  一起送出去 → `Unexpected non-whitespace character after JSON at position 30` → 400。
- **網址大小寫敏感。** 方法名叫 `unPublish` 的話，`@Patch(':id/unPublish')` 就跟
  `/unpublish` 是兩條不同的路由。`unpublish` 是一個英文字（`un-` 是前綴），
  所以不寫 `un-publish` —— 多個單字才用連字號（`/reset-password`）。

### 一個 TypeScript 的小陷阱

```ts
export function canEditQuestions(status: SurveyStatus): boolean;   // ← 分號結尾
```

以**分號**結尾而沒有 `{ }` 的 `function` 宣告，在 TS 裡不是「函式」，
而是**多載簽章（overload）**：它承諾「真正的實作緊接在下面」。所以會看到

```text
遺漏函式實作，或函式實作未緊接在宣告之後。
函式實作名稱必須是 'canEditQuestions'。
```

補上大括號和 `return` 就好。

### `.js` 副檔名：不是本專案的慣例

一度以為「import 產生的 enum 要帶 `.js`」是專案慣例，其實不是。
`package.json` **沒有** `"type": "module"` → 專案是 CJS → extensionless 就能解析。
專案裡自己的檔案一律不帶副檔名，只有少數幾處歷史遺留帶了 `.js`。

（`.js` 的來源是 `"moduleResolution": "nodenext"`：那個模式下 import 路徑寫的是
**編譯後的樣子**，TypeScript 自己對應回 `.ts` —— Prisma 產生的程式碼內部就是這樣寫的。
但那是 ESM 才強制，本專案不是。）
