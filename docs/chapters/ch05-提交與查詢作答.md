# Ch5 — 提交與查詢作答（Responses）

> **狀態：完成。** `pnpm test:e2e` **69 passed**（+17）、`pnpm test` **6 passed**（+2）。

三支端點，分四輪做：

| 輪 | 內容 | 這一輪的主題 |
| :---: | --- | --- |
| ① | `POST /surveys/:surveyId/responses` | 巢狀 write、巢狀驗證、第三條商業規則 |
| ② | 歸屬檢查 | **DTO 永遠做不到的事** |
| ③ | `GET .../responses` 與 `GET /responses/:id` | 分頁沿用、兩層 `include` |
| ④ | 補 Ch3 的 `order` race | **交易保證的沒有你以為的多** |

Ch1 就寫在課綱裡的那條規則（「只有 `PUBLISHED` 的問卷能被填答」），到這一章才真的生效。

## 核心概念

### 巢狀 write：一次呼叫寫兩張表

```ts
prisma.response.create({
  data: {
    surveyId,
    answers: { create: [{ questionId, content }] },
  },
});
```

`answers` 底下那個 `create` 是**動作**不是欄位（`connect` / `connectOrCreate` 是它的同類）——
Prisma 需要知道「這些關聯資料要新建、還是接上既有的」，所以動詞要寫出來。

陣列裡**不用寫 `responseId`**：Prisma 自己會把剛產生的那筆 `Response` 的 id 填進去，
而那個 id 是 `@default(cuid())` 產生的，**送出 SQL 之前連我們都還不知道**。

### 巢狀 write 本身就是一個交易

實測 log（不是推論）：

```sql
SELECT "Survey"."id", "Survey"."status" WHERE id = $1     -- assertExists
INSERT INTO "Response" ... RETURNING "Response"."id"
INSERT INTO "Answer" ... VALUES ($1,$2,$3,$4), ($5,$6,$7,$8)
SELECT "Response".* WHERE id = $1
COMMIT
```

**`COMMIT` 在**，所以「`Response` 寫進去了但 `Answer` 失敗」不可能發生 ——
不需要自己包 `$transaction`。

（`BEGIN` 沒印出來的理由同 Ch4 ①：沒有 `BEGIN` 就 `COMMIT` 會被 PostgreSQL 拒絕，
所以看到 `COMMIT` 就代表 `BEGIN` 一定在。）

另外兩個觀察：

- **N 筆答案批次成一句 `INSERT`**（`VALUES (...), (...)`）。50 題的問卷提交也是這三句，
  **查詢數不隨答案數成長** —— 這正是 N+1 的相反面。
- **多一句 `SELECT "Response".*`**：`INSERT ... RETURNING` 只回了 id，
  要回傳完整的那筆就得再讀一次。這是巢狀 write 的固定成本。

### 什麼時候才需要自己包 `$transaction`

判準是**中間有沒有一段「離開資料庫、回到 Node」的空檔**：

| 形狀 | 要自己包嗎 |
| --- | :---: |
| 巢狀 write（一次呼叫，Prisma 自己算關聯）| **不用** |
| 讀 → 程式判斷／計算 → 寫（中間隔著 JS）| **要**（但不夠，見坑 #4）|

`questions.service.ts` 算 `order` 是後者：`count` 讀到 2 → 回到 Node → `create` 寫 `order: 2`。
那個空檔就是別人插隊的機會。

### 巢狀驗證：`@ValidateNested` 與 `@Type` 缺一不可

```ts
@IsArray()
@ValidateNested({ each: true })   // 「進去檢查每一個元素」
@Type(() => AnswerDto)            // 「這些元素要建成 AnswerDto 的實例」
@ArrayNotEmpty()
answers: AnswerDto[];
```

**只寫 `@IsArray()` 的話，陣列裡的物件會被原封不動放行** —— `AnswerDto` 上的規則一條都不跑：

```
送 { "answers": [{ "隨便": 123 }] }
→ 驗證通過 → prisma.create 收到沒有 questionId 的物件 → 500
```

為什麼兩個都要：`@ValidateNested` 負責「進去」，`@Type` 負責「進去之後認得規則」。
少了 `@Type`，元素還是 plain object，而**規則掛在 class 的屬性上**，
plain object 上沒有那些屬性，於是進去了也查不到東西。

> **`@Type` 在這裡是它的原意**（「建成哪個 class 的實例」）。
> Ch4 那些 `@Type(() => Number)` 是拿它做 primitive 轉型 ——
> 順便沾了 JS 建構函式的行為，不是它本來的用途。

### 外鍵保證「存在」，不保證「屬於這份問卷」

這是這一章最該帶走的一句話。

```
A 問卷有一題 q1
B 問卷已發布
POST /surveys/{B}/responses  { answers: [{ questionId: "q1", ... }] }
→ 201
```

資料庫裡出現一筆「B 問卷的作答，答的卻是 A 問卷的題目」，而**外鍵沒被違反**（`q1` 真的存在）、
`@@unique([responseId, questionId])` 也沒被違反、**沒有任何錯誤訊息**。

這是 Ch1 那句「唯一約束的作用範圍由它所在的表決定」的同族問題：
**約束只知道自己那張表的事。** `Answer` 上的兩根外鍵各自認得自己那根柱子，
「這兩根柱子的爸爸是不是同一份問卷」超出它們的視野。

**而 DTO 永遠做不到這件事** —— 它只看得到「這個請求本身」，看不到資料庫裡有什麼。
跨表檢查一律是 service 的工作。

要問資料庫的問題不是「這些題目存在嗎」，而是
**「這些題目裡，有幾筆是這份問卷的？」**：

```ts
const count = await this.prisma.question.count({
  where: { surveyId, id: { in: questionIds } },
});
```

數量對得上就全部合格；少一筆，就有題目不屬於這份問卷（或根本不存在 —— 在這個問題下是同一種答案）。

### 三層防線各自管什麼

Ch5 把這件事講完整了 —— 同一條規則寫在不同層，**保護範圍完全不同**：

| 層 | 誰執行 | 例子 | 繞過 HTTP 還在嗎 |
| --- | --- | --- | :---: |
| **驗證** | ValidationPipe（controller 邊界）| `@ArrayNotEmpty`、`whitelist` | ❌ **沒了** |
| **商業規則** | service 自己的程式碼 | `canSubmitResponse`、歸屬檢查 | ✅ 還在 |
| **資料完整性** | PostgreSQL | 外鍵、enum 型別、`@@unique` | ✅ 一直都在 |

所以直接呼叫 `ResponsesService.create(surveyId, { answers: [] })`：
**空陣列會成功**（第一層被繞過了），但 `DRAFT` 問卷仍然丟 409（第二層在 service 裡）。

**判準：規則寫在 DTO 上 = 只保護 HTTP 這道門；寫在 service 裡 = 保護所有呼叫者。**
這也是為什麼商業規則不能寫成裝飾器 —— 那樣排程、匯入、其他 service 呼叫都不受保護。

（這個區分前面踩過兩次：Ch3 拔掉 `@IsEnum` 想看資料庫會不會擋，結果**根本沒走到資料庫**；
Ch4 ① 的 DTO 沒被 import，驗證／`whitelist`／預設值**三件事一起失效** ——
它們的共同上游只有一個：pipe 有沒有拿到一個 class。）

## 決策取捨

### 驗證做到「格式 + 歸屬」，不做「每題必答」

「每一題都要作答」是**產品決定**，不是技術問題 —— 多數問卷允許跳題。
加了它會多一條純函式（可以單元測試），但這一章已經夠滿。

**判準：不確定是不是規則的東西，先不要寫進程式。** 之後真的要，加一條規則比拆掉一條容易。

### 作答列表沿用 Ch4 的分頁

`Response` 是全專案**唯一會真的長到幾千筆**的表（一份問卷 N 個人填）。
不分頁正好是 Ch4 開場講的那個 bug，所以照套 `{ data, meta }`。

**列表刻意不帶 `answers`**：100 份作答 × 每份 20 題 = 2000 筆塞進一個回應。
要細節就打 `GET /responses/:id` —— 這是 Ch4 ③「回傳形狀由呼叫端決定」的第二次應用。

### 單筆帶兩層 `include`

```ts
include: {
  answers: {
    include: { question: true },
    orderBy: { question: { order: 'asc' } },
  },
}
```

帶 `question` 是為了**避免前端的 N+1**：不帶的話前端拿到一堆 `questionId` + `content`，
畫不出「題目：答案」，只能對每一筆再打一次 API。

`orderBy` 依的是**關聯表的欄位**（`Answer` 自己沒有 `order`）。
**這是少數 Prisma 真的會產生 JOIN 的場合** —— 排序必須在同一句 SQL 裡完成，
沒辦法像 `include` 那樣分兩句做。

方向選 `asc`，跟 `GET /surveys/:id?includeQuestions=true` 一致。
用 `desc` 的話同一批題目在兩支 API 裡順序相反，前端會很困惑。

> 第一版真的寫成 `desc`，而且**測試是綠的** —— 因為前提資料照 `q1, q2` 建、期望反過來，
> 機制上抓得到「`orderBy` 被拿掉」。**測試綠不代表行為對**：
> 方向是產品決定，前提資料才是測試的工具。正解是 service 用 `asc`、
> **前提資料倒著建**，兩個都顧到。

### service 收 boolean / 收 DTO，看欄位數

`findOne(id, includeQuestions: boolean)` 收 primitive，`findAll(surveyId, query: DTO)` 收 DTO。

判準是**這支方法需要幾個值**，不是「service 能不能碰 DTO」這種鐵律：

| | 需要的值 | 傳法 |
| --- | --- | --- |
| `findAll` | 分頁兩個（之後可能更多）| DTO |
| `findOne` | 一個 boolean | primitive |

檢驗方式：**「如果哪天不是 HTTP 在呼叫它，它得先準備什麼？」**
為了一個 boolean 先 `new` 一份由 HTTP 形狀決定的 class，換不到任何東西。

### 不共用 `FindSurveysQueryDto`

它的 `sort` 白名單是 `['createdAt', 'title']` —— **那是 `Survey` 的欄位**，`Response` 沒有 `title`。
共用會讓 `?sort=title` 通過驗證、然後執行期 500（Ch4 ② 坑 #8 的形狀）。

**白名單綁定在特定資料表上，不能跨表借用。**

### 兩個 controller 的拆法沿用 Ch3

| 需要什麼 | 路由 | 檔案 |
| --- | --- | --- |
| 要知道「哪一份問卷」 | `/surveys/:surveyId/responses` | `survey-responses.controller.ts` |
| 已經知道自己 id | `/responses/:id` | `responses.controller.ts` |

`@Controller('responses')` + `@Get(':id')`，**不是** `@Controller('responses/:id')` + `@Get()`。
兩者路由完全一樣，但後者會讓這個 class 之後**每一條路由都繼承那個 `:id`**。
**前綴放「這組路由共同的部分」，變動的部分放在方法上。**

### `order` 的 race：延後，不是解決

見坑 #4 與 #5。三條可行的路都需要「重試」這個獨立主題，這一章不做。
**延後的理由是「代價還不值得」，不是「沒問題」** —— 差別寫在註解裡。

## 踩到的坑

### 1. `new ConflictException(...)` 少了 `throw`

```ts
if (!canSubmit) {
  new ConflictException('問卷未發布，無法填寫');   // 物件建了就被丟掉
}
```

程式繼續往下跑 → **`DRAFT` 的問卷也能被填答，回 201**。
規則寫了，但**從來不會生效**（Ch3 坑「查錯欄位」的同族）。

`tsc` 0 errors（`new X()` 是合法運算式）、`lint` 也沒抓到。
**唯一的偵測器是那條還沒寫的 409 測試** —— 這就是為什麼「寫規則的當下就要寫那條測試」。

同一個形狀在輪 4 又出現一次：`this.prisma.$transaction(async (tx) => {...})` **少了 `return`**，
方法回 `undefined` → 201 配空 body。那次 `lint` 的 `no-floating-promises` 有抓到 ——
**「沒有 `return` 的 Promise」和「沒人等的 Promise」是同一件事。**

### 2. Module 沒註冊，路由整組消失（**兩次**）

第一次：`AppModule` 的 `imports` 漏了 `ResponsesModule` → 所有 `/responses` 請求 404。
第二次：controller 拆成兩支後，`ResponsesModule` 的 `controllers` 只留了一個 → 7 條測試全紅。

**Nest 不會抱怨你少註冊了什麼，它只是靜靜地沒有那條路由。**
判準沿用 Ch3：**「404 那條綠、其他全紅 → 先懷疑路由沒接上」。**

### 3. 假綠的第八種與第九種

**第八種：空的 `it`。**

```ts
it('questionId 屬於別份問卷時回 400', async () => {});   // 通過
```

Jest 眼中沒有斷言失敗就是通過。`57 → 60`，數字漲了三，**實際保護是零**。

**第九種：測試繞過了被測的程式碼。**

```ts
await prisma.question.create({ data: { order: 0 } });        // 自己寫死
expect(questions.map((q) => q.order)).toEqual([0, 1, 2]);    // 驗自己剛寫的數字
```

名稱說「連續新增三題時 order 依序是 0、1、2」，但那個「依序」是手動排的，
不是伺服器算的 —— 它繞過了 HTTP 與 service，**那段 `count` 邏輯一行都沒被執行**。

實測證明：把 service 的 `order` 改成寫死的 `999`，這條**照樣綠**（改用 API 之後才會紅）。
跟 Ch3 那次「網址少一個 `s`，404 來自路由而不是邏輯」同一族。

**判準：測試數字漲了不代表覆蓋增加了。唯一可靠的檢查是把 bug 放回去看它會不會紅。**

### 4. 「包成一個交易就能根治 race」—— 這句話是錯的

Ch3 的註解寫著「要根治得把兩件事包成一個交易，**那是 Ch5 的主題**」。
Ch5 真的包了，**然後發現那句話不成立**。

PostgreSQL 預設的隔離級別是 **`Read Committed`**，它的規則是
**每一句 SQL 各自取一次快照**，而不是整個交易共用一個。所以：

```
請求 A：  BEGIN ── count 讀到 2 ──────────── INSERT order:2 ── COMMIT
請求 B：       BEGIN ── count 讀到 2 ── INSERT order:2 ── COMMIT
                        ↑ 這一句自己取快照，看到的還是「2 題」
```

**兩題都拿到 `order: 2`，而整個過程沒有任何錯誤。**

交易保證的是「這幾句要嘛全成功、要嘛全失敗」，**它從來沒有保證過「我讀到的值不會過期」**。

> **這個發現連帶推翻了 Ch4 的一句話。** 當時寫「`$transaction` 給你一致的讀取視角，
> 讓 `data` 與 `total` 來自同一個瞬間」—— 同樣的原因，那也不成立。
> 包起來買到的是「兩句跑在同一條連線、中間不回到 Node」，**空檔變小，不是消失**。
> 四處說法已全部更正（`surveys.service.ts`、`關聯式資料庫基礎.md`、`ch04`、`Prisma速查.md`）。
>
> **這是註解寫錯的第七次，也是最貴的一次** —— 前六次是「改了程式忘了改註解」，
> 這次是**一開始就講錯了機制**，而後續每一步都建立在那個錯的理解上。

三條可行的路，這個專案三條都沒選：

| 做法 | 代價 |
| --- | --- |
| `{ isolationLevel: 'Serializable' }` | 衝突方拿 `P2034`，**必須配重試**否則使用者拿 500 |
| `@@unique([surveyId, order])` | 資料庫直接拒絕，同樣要配重試 |
| 把「讀 + 算」交給資料庫在同一句 SQL 裡做完 | 要寫 raw SQL，繞過 Prisma 的型別 |

**延後的理由**：題目只有在 `DRAFT` 時能加，那階段通常只有作者一個人在編輯；
而三條路都需要「重試」這個獨立主題（指數退避、冪等性）。
**撞到時的症狀：兩題 `order` 相同 → 列表順序不確定 → 沒有任何錯誤日誌。**

那 `$transaction` 還留著做什麼？它讓兩句跑在同一條連線上、中間不回到 Node，
**把窗口縮到最小** —— 縮小不等於消滅。

### 5. 併發測試綠了，但那不代表修好了

專案第一條併發測試：

```ts
await Promise.all([
  request(app.getHttpServer()).post(url).send(bodyA),
  request(app.getHttpServer()).post(url).send(bodyB),
]);
expect(questions.map((q) => q.order)).toEqual([0, 1]);
```

**本機是綠的。** 三種可能的結果，每一種都是資訊：

| 結果 | 意思 |
| --- | --- |
| 紅（`[0, 0]`）| `Read Committed` 擋不住，要處理隔離級別 |
| **綠** | **本機重現不出來，不代表問題不存在** |
| 時綠時紅 | 最真實的樣子 |

`Promise.all` 只保證「一起送出」，不保證「同時到達資料庫」——
Nest 處理兩個請求本來就有先後，再加上到 Neon 的網路延遲，兩者實際上還是接近依序。

**判準：測試綠的時候，問自己「我有沒有辦法說明為什麼它不會發生？」**
說不出來就是還在。這條測試的價值不是「證明修好了」，而是**留下一個之後可以再跑的探針**。

### 6. `read ECONNRESET` —— 怎麼分辨環境問題，以及怎麼不浪費兩小時

收尾時測試突然大量失敗（69 條裡紅 1～12 條），而且**每次紅的測試都不一樣**。

**第一個判準（30 秒內就能用）：**

| 觀察 | 代表什麼 |
| --- | --- |
| 每次跑失敗的測試都不一樣 | 程式碼錯會**固定**紅同一條 |
| 錯誤是 `read ECONNRESET`，不是 `Expected` / `Received` | **連 HTTP 都沒打通，斷言根本沒執行到** |
| 單獨跑某個 suite 有時全過 | 資源競爭或環境不穩 |

**「失敗的測試每次不同」+「錯誤不是斷言」= 先懷疑環境，不要回頭改程式碼。**
這一條如果早三十分鐘想到，就不會有後面那兩小時。

#### 實測排除表

第一個假設（並行跑測試留下的孤兒 jest 行程佔住連線）**看起來很合理，但被自己的實測推翻了** ——
清光孤兒行程之後照樣失敗。後面每一項都是實際量出來的：

| 假設 | 怎麼測 | 結果 |
| --- | --- | --- |
| 孤兒 jest 行程佔住連線 | 全部清掉後重跑 | ❌ 還是失敗 |
| **資料庫本身有問題** | 不經過 HTTP，直接用 Prisma 跑 70 圈完整工作量（TRUNCATE + 巢狀 write + count）| ✅ **70/70 成功** |
| 閒置連線被 Neon 切斷 | 開 10 條連線，閒置 10 / 30 / 60 秒後再查 | ✅ 全部正常 |
| Neon 冷啟動 | 探針跑完立刻跑測試（compute 是熱的）| ❌ 還是失敗 |
| 埠耗盡 / TIME_WAIT | `Get-NetTCPConnection` | ❌ TIME_WAIT 只有 20，埠有 14000 個 |
| supertest 每個請求開新 server | `app.listen(0)` 重用同一個 server，跑三次 | ❌ 還是紅 |
| Jest 的 5 秒逾時不夠 | `testTimeout` 改成 30000，跑兩次 | ❌ 還是紅 |

**結論：不是程式碼，也不是資料庫。** 問題在 supertest ↔ Nest 之間的 HTTP socket，
屬於這台機器的環境層級。**沒有繼續往下挖** —— 它不影響正式行為，
而且再挖下去是一個獨立的題目，不屬於 Ch5。

#### 順帶量到的一件事

那支探針跑 70 圈花了 **45 秒**，等於**每次往返 Neon（新加坡）約 500ms**。
69 條 e2e 跑 31 秒，時間幾乎全花在網路上。

這解釋了「為什麼測試越加越慢」，也給了一個之後有用的參考值：
**e2e 的時間 ≈ 資料庫往返次數 × 500ms**，跟程式效率幾乎無關。

- **兩支探針收進 `scripts/`**（`probe-db.js` / `probe-conn.js`），可以直接跑

> **這一輪最貴的不是那個 bug，是「先猜再驗」的順序反了。**
> 第一個假設（孤兒行程）合理、有證據支持（真的有兩個孤兒行程）、清掉之後**確實**變好了一點 ——
> 於是又重試了好幾輪，每輪 30 秒。**「症狀減輕」不等於「找到原因」**，
> 而真正該做的第一件事是那支五分鐘的探針：**把 HTTP 拿掉，看資料庫還會不會壞。**
