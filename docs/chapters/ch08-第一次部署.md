# Ch8 — 第一次部署（後端先上線）

把 Ch0 ~ Ch7 做出來的東西放到公開網址上：**Render**（跑 Node）+ **Neon 的 `production` branch**（資料庫）。
線上位址 `https://survey-backend-0dku.onrender.com`，設定值與維運資訊在
[`docs/專案速查.md`](../專案速查.md) 的「部署與正式環境」。

課綱把部署排在階段一結尾是刻意的：此時沒有認證、沒有前端，變數最少。
這一章分四輪 —— production build、`migrate deploy` 與正式資料庫、Render 上線、連線數量測。

---

## 核心概念

### 部署 = 別人拿你的 repo 去跑

前八章所有的驗收都是「本機的檔案 → 本機跑」。部署是第一次由**別人**執行你的程式碼，
而那個「別人」的環境比你少了三樣東西：

| 你有、它沒有 | 為什麼 | 怎麼補 |
| --- | --- | --- |
| `src/generated/` | 在 `.gitignore` 裡，Prisma Client 是產物 | build 時跑 `prisma generate`（`prebuild` 鉤子） |
| `.env` | 在 `.gitignore` 裡 | 平台的環境變數設定畫面 |
| `dist/` | 在 `.gitignore` 裡 | build 時產生 |

**所以「本機 build 成功」對「線上 build 會不會成功」幾乎沒有保證。**

### `migrate deploy` 的冪等性

`migrate dev` 會比對 schema、產生新的 migration 檔、必要時 reset 資料庫。
`migrate deploy` 只做一件事：**把 `prisma/migrations/` 底下還沒套用的 SQL 依序執行**。

實測（同一個指令連跑兩次）：

```
第一次 → Applying migration `20260807020256_init_survey_schema` … 1 migration applied
第二次 → No pending migrations to apply.
```

**第二次什麼都不做，這就是它能放進 Build Command 的原因** —— 每次部署都會跑一遍，
包括那些完全沒動 schema 的部署。

它靠 `_prisma_migrations` 這張表記住「哪些套用過了」；那張表跟四張業務表住在同一個 schema，
所以 `DROP SCHEMA public CASCADE` 會把它一起刪掉，資料庫就回到「Prisma 從沒碰過」的狀態。

### 環境變數由平台注入

線上沒有 `.env` 檔，但 `ConfigService.getOrThrow('DATABASE_URL')` 照常拿得到值 ——
因為 `ConfigModule` 讀的是 **`process.env`**，`.env` 只是把檔案內容**填進** `process.env` 的一種來源。
平台直接把變數放進 `process.env`，少掉的只是「讀檔」那一步。

同一條規則的另一個現場：`DATABASE_URL="…" pnpm exec prisma migrate deploy` 這種行內寫法
不會被 `.env` 蓋掉，因為 **dotenv 只填「還沒有值」的變數**（`setup-env.ts` 靠的也是這條，第三次現場）。

### 連線其實有三段

連線字串的 host 帶 `-pooler` 時，中間隔著一層 PgBouncer：

```text
你的應用 (pg pool)  →  PgBouncer  →  Postgres
        ↑                       ↑
   DATABASE_POOL_MAX      max_connections
```

實測：持續打 12 條並發請求，`pg_stat_activity` 只看到 **7 條**，
而且 `application_name` 是 **`pgbouncer`**。
也就是說**那張表看到的不是你的應用開的連線**，是中間那層對 Postgres 開的連線。
這台 compute 的 `max_connections` 是 **901**。

## 決策取捨

### `prebuild` 而不是「記得先 generate」

`prebuild` 是 npm 的生命週期鉤子，`pnpm build` 會自動先跑它。
選它是因為「build 前一定有最新的 client」變成**結構上不可能忘記**，代價是本機每次 build 多幾秒。

Ch7 坑 #5 剛示範過反例：「query DTO 裡不能寫 `@ApiProperty`」那條規則事先給了，
10 個屬性仍然 10/10 全錯 —— 因為它被當成「寫的當下要想起來」在用。
**靠紀律的規則會失效，靠結構的不會。**

### `migrate deploy` 放 Build Command，而且放最後

放 Start Command 的話，每次休眠喚醒、每次重啟都會跑一次；放 Build 只跑一次，
而且 build 失敗就不會部署（舊版本繼續服務）。

放**最後**是為了讓「build 失敗時資料庫還沒被改」。順序反過來的話，
新 schema 已經套用、新程式卻沒上線，線上跑的是舊程式配新結構。

### 不設 Health Check Path

`/health` 會做一次真的資料庫查詢，而平台的健康檢查是**定期輪詢**
→ Neon 的 compute 永遠不會 autosuspend。
免費方案是 100 CU-hours／月，最小的 0.25 CU 連續跑一個月是 `0.25 × 730 ≈ 182` CU-hours，
**額度撐不到月底**，而額度用完的症狀不是報錯，是某天發現資料庫連不上。

代價是部署時沒有「等健康檢查過了再切流量」這道保護。這一章選了省額度那邊。

### `/docs` 保持公開

`/docs` 洩漏的是「有哪些端點、參數長什麼樣」。但這個 API **完全沒有認證** ——
任何人拿到網址就能 `POST` 建問卷、`DELETE` 刪掉問卷連同所有作答、讀走全部填答內容。

**關掉 `/docs` 沒有關掉任何一扇門，只是拿掉門牌。** 端點名稱是 REST 慣例，猜三分鐘就出來了。
真正的修法是 Ch9 ~ Ch12 的認證與權限；在那之前唯一有意義的動作是**不要把網址貼到公開的地方**。
（原樣記錄現狀：撰稿當下這個 API 對全世界開放讀寫刪。做到 Ch12 再回頭看這一段。）

### 三條 Neon branch

`production` 給線上、`dev` 給本機、`test` 給 e2e。三條 host 前綴互不相同，
**貼完回頭比對一次 host** 就是防呆。

最危險的填錯法是「正式環境填成 test branch」：網站一切正常，
直到你在本機跑一次 `pnpm test:e2e`，`reset-db.ts` 在每個案例前 `TRUNCATE` 四張表，
線上資料在 70 秒內清空，而測試顯示 84 passed。
**`setup-env.ts` 的防呆只看得到本機那兩個檔案，看不到部署平台上填了什麼。**

## 踩到的坑

### 坑 1：用「改資料夾名字」模擬「資料夾不存在」，被 IDE 當成重構

為了看 Render 上沒有 `src/generated` 的樣子，把它改名成 `.bak`。
VS Code 的「重新命名時自動更新 import」立刻把全專案 **16 行 import、14 個檔案**改成指向 `.bak`，
`.bak` 一刪，那些 import 就指向空氣。

**判準：要模擬「這個資料夾不存在」就 `rm -rf`，不要改名。**
`prisma generate` 一秒就重建回來。這是 `src/generated` 放在 `src/` 底下的代價 ——
好處是 `tsc` 管得到它，壞處是 IDE 也管得到它。

### 坑 2：驗收跑在陳舊的建置產物上 —— 假綠的第十種

`nest build` **不會先清空 `dist/`**，而 `node dist/main` 早就把檔案載進記憶體了。
於是「`pnpm build` 掛掉 → `dist/main.js` 還在 → `pnpm start:prod` 照跑 → `/health` 回 200」
這條路整段成立，看起來像驗收通過。

證據是還原後搜出來的：`dist/` 裡同時有 `dist/generated/` 和一堆引用 `generated.bak` 的 `.d.ts`
—— **兩次不同 build 疊在一起的產物**。

前九種假綠都出在測試或程式碼本身，這次是**驗收對象是上一次的產物**。
**判準：驗證建置產物之前先 `rm -rf dist`。**

### 坑 3：資料庫裡的亂碼，第一嫌疑人是送資料的那一端

線上建立的問卷 title 回來是 `???? whitelist`。沒有直接下結論說伺服器編碼壞了，
改用一個確定是 UTF-8 的檔案重送：

```bash
printf '{"title":"中文編碼測試"}' > body.json   # xxd 確認：e4b8ad e69687 …
curl --data-binary @body.json …                 # → {"title":"中文編碼測試"} 完整回來
```

**伺服器沒問題，壞的是 shell 把命令列參數裡的中文重新編碼了。**
這也回頭解釋了 dev 資料庫裡那三筆 `問卷1/2/3` 亂碼 —— 同一個根因。
**判準：三十秒就能分辨，用一個確定是 UTF-8 的檔案重送一次。**

### 坑 4：Neon 的預設 branch 叫 `production`，但它是開發庫

要建「正式環境的資料庫」時才發現 Neon 的預設 branch 本來就叫 `production` ——
而這個專案已經拿它當開發庫用了七章，裡面有 9 份 seed 與手動測試留下的問卷。

**名字不代表用途，要看 host。** 最後的做法是：先從它分出 `dev`（資料副本一起帶走）、
`.env` 改指 `dev`，再把原本那條 `DROP SCHEMA public CASCADE` 清空當正式環境。

### 坑 5：教練第十一次「先給結論、沒有先量」

Health Check Path 一開始建議「設成 `/health`，讓既有註解成真」。
算了一次 CU-hours 之後自己推翻 —— 設下去會讓 Neon 永遠不休眠，免費額度第 16 天左右就用完。

同一輪還有一次相反的示範：`prisma` 在 `devDependencies` 裡，
擔心平台 `NODE_ENV=production` 會跳過 devDependencies 讓 `prebuild` 掛掉。
這次**沒有猜，直接讓部署當探針** —— build 過了，代表 Render 有裝 devDependencies。
成本是幾分鐘，換到一個確定的答案。

## 作業

1. 為什麼 Build Command 裡 `prisma migrate deploy` 要放在 `pnpm build` **後面**？把順序反過來，什麼情況下會出事？
2. 線上沒有 `.env` 檔案，`ConfigService.getOrThrow('DATABASE_URL')` 為什麼不會炸？
3. `SHOW max_connections` 是 901，`DATABASE_POOL_MAX` 預設是 10。這兩個數字是同一件事的兩種說法嗎？
4. Start Command 是 `pnpm start:prod`（`node dist/main`）而不是 `pnpm start`（`nest start`）。為什麼？
5. `main.ts` 的 `app.enableShutdownHooks()` 在這個部署組合下，效果是可以被觀測到的嗎？

## 作業解答

1. **`build` 失敗、但資料庫已經被改過。** 線上跑的會是舊程式配新 schema，
   而且新程式沒上線、沒有任何錯誤訊息說明這件事。放最後的話 build 一掛就整個停住，資料庫維持原狀。
2. 因為 `ConfigModule` 讀的是 **`process.env`**，不是檔案。`.env` 只是把內容填進 `process.env` 的來源之一，
   平台直接把變數放進去，少掉的只有讀檔那一步。
3. **不是。** `max_connections` 管 PgBouncer → Postgres 那一段（資料庫端能接受的總量），
   `DATABASE_POOL_MAX` 管你的應用 → PgBouncer 那一段（單一實例最多開幾條）。
   中間那層會重用連線，所以 12 條並發只用掉 7 條後端連線。
4. `nest` 這個指令由 `@nestjs/cli` 提供，它在 **`devDependencies`** 裡；
   而且 `nest start` 會即時編譯，正式環境不該把編譯器帶上線。`node dist/main` 直接跑編譯好的產物。
5. **觀測不到。** `pg` 的連線池閒置 10 秒就自己關連線、Neon 免費方案的 compute 也會 autosuspend，
   兩個機制都會搶先把連線收走 —— 所以「重啟後連線沒有累積」這個觀測**不能當成它有效的證據**
   （兩個機制都能解釋同一個結果，那個結果就不是證據）。
   它真正會發威的是「長閒置逾時 + 不會休眠的資料庫 + 頻繁重啟」。
