## 核心概念

### Exception Filter 是什麼：你一直都有一個

`GET /surveys/不存在的id` 在 Ch5 回的是：

```json
{ "statusCode": 404, "message": "問卷不存在", "error": "Not Found" }
```

這串 JSON **不是 service 寫的** —— service 只丟了一個 `NotFoundException` 物件出來，
是 **Nest 內建的預設 filter** 把那個物件翻成這串 JSON 的。

所以 Ch6 做的事不是「加一個新東西」，是**把那個內建的換掉**。
**filter 一直都在運作，只是從來沒被看見。**

### Pipe 與 Filter：同一個家族，位置相反

| | Pipe（`ValidationPipe`） | Filter（Exception Filter） |
| --- | --- | --- |
| 站在哪 | 請求**進來**的路上 | 回應**出去**的路上 |
| 什麼時候跑 | 每個請求都跑 | **只有例外被丟出來時才跑** |
| 做什麼 | 檢查 / 轉型參數 | 把例外翻譯成 HTTP 回應 |
| 註冊在哪 | `setup-app.ts` 的 `useGlobalPipes` | `setup-app.ts` 的 `useGlobalFilters` |

兩者是**並排的兩件事，不是巢狀關係**。實作時把 `useGlobalFilters` 寫進了
`useGlobalPipes` 的括號裡，錯誤訊息是：

```text
類型 'INestApplication' 的引數不可指派給類型 'PipeTransform' 的參數
```

它其實已經把答案講完了：「你把一個**應用程式**當成 **Pipe** 傳進去了。」
為什麼會是應用程式？因為 `app.useGlobalFilters(...)` 回傳 `app` 自己（方便串接）。

> **判準：「XXX 缺少屬性 YYY」通常代表你把 A 放到了 B 該在的位置**，
> 而不是那個東西本身壞掉。先看「它以為我要給什麼」跟「我實際給了什麼」，
> 差距本身就是答案。

### 所有錯誤都經過同一個地方

```text
ValidationPipe ── 不合格 ──┐   BadRequestException
Controller                 │
Service ───────────────────┤   NotFoundException / ConflictException
Prisma ────────────────────┤   P2025 / P2002（沒人接就是 500）
                           ▼
                  ★ Exception Filter ★
```

**改它一次，每一條錯誤路徑都跟著變。** 這是威力，也是這一章要小心的地方。

### `@Catch()` 不帶參數 vs `@Catch(HttpException)`

`@Catch()` 空括號 = 什麼例外都接。寫成 `@Catch(HttpException)` 的話，
只有「有人明確丟出的 HTTP 例外」會進來，而 `TypeError`、Prisma 的錯誤碼這些
**沒人預期的**東西會落回 Nest 內建的 filter —— 於是 500 的格式跟其他錯誤不一樣，
統一格式就破了一個洞。

**「未預期的錯誤」正是最需要被統一格式接住的那一種。**

### filter 只看得到「被丟出來的東西」

Ch5 的「三層防線」在這裡第三次出現，而且這次的角度是新的。

進 Ch6 之前實跑了 `ch05` 作業第 3 題（直接呼叫 `ResponsesService.create`、不走 HTTP）：

| 層 | 住在哪 | 繞過 HTTP 之後 | 證據 |
| --- | --- | --- | --- |
| 驗證（`@ArrayNotEmpty()`） | ValidationPipe | **消失** | 空 `answers` 成功，資料庫真的多了一筆空作答 |
| 商業規則（`canSubmitResponse`） | service | **還在** | 丟 `ConflictException`、`count = 0` |
| 完整性（外鍵） | PostgreSQL | **一直都在** | 探針寫錯時噴 `Question_surveyId_fkey` |

三件跟 filter 直接相關的事：

1. **那個 `ConflictException` 是 HTTP 的類別，而現場根本沒有 HTTP。**
   `getStatus()` 老實回答 409，但沒有任何人要把它變成回應 —— 它只是一個沒人接的物件。
   這就是「決定不做 domain error」那個取捨裡「會後悔的情境」的預演。
2. **filter 能拿到的就是 `getStatus()` 和 `message`。** 沒有「這是哪一種衝突」的資訊 ——
   對 filter 來說，`unpublish` 的 409 和「問卷未發布」的 409 長得一模一樣。
   這是「`code` 只能是狀態碼的鏡像」的**實測證據，不是推論**。
3. **空 `answers` 那個情境完全沒有例外**，filter 一輩子不會知道那筆資料被寫進去了。
   **filter 是錯誤處理，不是防線。** 這一章最該小心的就是把它當成防線用。

## 決策取捨

### 不做 domain error —— 決定不改也是一個決定

Ch2 在 `surveys.service.ts` 檔頭留了一句「Ch6 有了 Exception Filter 之後會回頭重看」。
**重看過了，結論是維持現狀。**

另一條路是 service 改丟 `SurveyNotFoundError` 這類自訂錯誤，由 filter 翻成 404，
service 就徹底不認識 HTTP。

**判準是「這支 service 除了 HTTP 之外，還有沒有第二個呼叫者」：**

| | 直接丟 `NotFoundException` | 丟 domain error 由 filter 翻譯 |
| --- | --- | --- |
| 誰在用 | 絕大多數中小型 NestJS 專案，**官方文件範例就是這樣寫的** | DDD / 六角架構 / Clean Architecture |
| 前提 | service **只有 HTTP 一個入口** | service 有**多個入口** |
| 為什麼 | NestJS 刻意把 HTTP 例外設計成通用的錯誤語彙，不算反模式 | 同一個錯誤，HTTP 要 404、gRPC 要 `NOT_FOUND(5)`、排程只要一行 log、訊息佇列要決定重不重試 |

這個專案是前者：唯一的入口就是 controller，而課綱翻到 Ch17（認證、Swagger、前端）
全部還是走 HTTP。**拆出來買到的好處是假想的。**

**會後悔的情境很具體**：出現排程（每天寄提醒信）、CLI（匯出報表）、
或訊息佇列的消費者。到時候再改也來得及，而且那時會確切知道第二個入口長什麼樣。

> **「決定不改」也要把理由寫下來。** 否則下一個讀到那句「會回頭重看」的人
> （包括三個月後的自己）會以為那件事還沒做。

### `code` 先做狀態碼的鏡像

```jsonc
{ "error": { "code": "NOT_FOUND", "message": "問卷不存在" } }
```

`code` 有五種：`NOT_FOUND` / `CONFLICT` / `BAD_REQUEST` / `VALIDATION_FAILED` /
`INTERNAL_ERROR`，全部由 filter 從狀態碼推導，**一支 service 都不用改**。

誠實的代價：`code` 跟 status 重複，資訊量低。要更細的 code（`SURVEY_NOT_FOUND`）
就得讓 service 送上來 —— `HttpException` 允許傳物件，所以不必真的做 domain error，
但要動到十處 `throw`，而且得約定一張 code 清單。

**這是「決定不改 service」的直接下游後果**，兩個決定之間的耦合直到寫 filter 才看得見。
留到 Ch7 寫 Swagger、真的要把契約交給前端時再評估。

### 500 的 `message` 是常數，不是 `exception.message`

Prisma 的錯誤訊息會帶著**完整的檔案路徑、表名、約束名**
（例如 ``Foreign key constraint violated on the constraint: `Question_surveyId_fkey` ``）。
直接回給前端等於免費送出一張資料庫地圖，而且**沒有任何症狀**：
測試綠、狀態碼對、body 形狀完全正確。

對策不是「記得不要放 `exception.message`」（人一定會忘），
是**讓那條路徑上根本沒有變數可以放** —— 只有一個寫死的常數。

> `LEARNING.md` 說「認得的才翻譯，認不得的原樣往上丟」。但 `@Catch()` 是 catch-all，
> **沒有「往上丟」這個選項**（上面沒有東西了）。所以「不要吞掉錯誤」在這裡的正確兌現是
> **完整堆疊一定要 `logger.error`**。吞掉之後最貴的代價是線上出事時只看得到
> 「伺服器發生未預期的錯誤」。

### 不改 `assertExists` 策略，filter 的 Prisma 分支定位成安全網

Ch2 選了「先 `assertExists` 再操作」而不是 `catch P2025`，代價是同一筆資料查兩次。
Ch6 重新評估後**仍然選先擋** —— 先擋才給得出「問卷不存在」這種具體訊息，
`catch P2025` 只知道「某一筆不見了」。

輪 2 會讓 filter 認得 `P2025` / `P2002` / `P2003`，但那是**縱深防禦**：
漏寫一處 `assertExists` 時，前端拿到 404 而不是 500。

它防的不是假想的情境，是 **TOCTOU** —— `assertExists` 通過之後、`update` 執行之前，
另一個請求把那筆刪掉了。**跟 Ch5 的 `order` race 是同一族的形狀**
（「讀 → 回到 Node 判斷 → 寫」中間那段空檔）。

## 踩到的坑

### 1. 兩種 400 長得一模一樣，只差 `message` 的型別

實際量出來的四種錯誤（Ch6 之前）：

```text
(1) 404 service        {"message":"問卷不存在","error":"Not Found","statusCode":404}
(2) 400 ValidationPipe {"message":["title should not be empty", ...],"error":"Bad Request","statusCode":400}
(3) 400 service        {"message":"有重複的題目ID","error":"Bad Request","statusCode":400}
(4) 409 service        {"message":"問卷未發布，無法填寫","error":"Conflict","statusCode":409}
```

**(2) 和 (3) 的狀態碼、例外型別、`error` 欄位全都一樣**，唯一的差別是
`message` 是陣列還是字串。filter 要分辨它們，只能靠 `Array.isArray`。

混成一種的後果很具體：前端拿到 `VALIDATION_FAILED` 就會去讀 `details` 準備標紅欄位，
結果是 `undefined` → **畫面空白，而狀態碼完全正確、沒有任何錯誤訊息**。

而這也是「同一個欄位兩種型別」這件事本身的問題 —— 改格式的動機就是它。
現在 `message` 永遠是一句字串，逐條細節放 `details`。

### 2. 錯誤回應的格式從來沒有被任何測試保護過

開工前數了一次：`test/` 底下有 **31 條**在斷言錯誤狀態碼，
斷言錯誤 **body** 的是 **0 條**。

意思是**改回應格式，一條既有測試都不會紅**。

這不是好消息。它跟前面幾次「假綠」的差別在於：那些是測試寫錯、或測試繞過了被測的程式碼，
**這次是那個面向從來就沒有測試**。既有的 69 條全綠，只證明「狀態碼沒被弄壞」。

> **判準：改一個東西之前先問「現在有什麼在保護它？」** 答案是「沒有」的時候，
> 「測試全綠」這個資訊的價值是零。

### 3. 環境：一個症狀底下其實是三個問題

Ch5 收尾時記過 `read ECONNRESET`（坑 #6），結論停在「這台機器 HTTP socket 層的問題」。
Ch6 期間它惡化到整輪 `pnpm test:e2e` 卡死不結束，於是回頭徹底處理。

拆開來是**三個各自獨立的問題**：

| | 症狀 | 原因 | 解法 |
| --- | --- | --- | --- |
| A | 測試跑完、summary 都印了，但指令不結束 | jest 在等殘留的 handle | `--forceExit` |
| B | 上一輪被中斷後，裡面的 jest 活了下來 | Windows 沒有 process group | `pretest:e2e` 自動清 |
| C | 隨機大量 ECONNRESET | **見下** | keep-alive |

**C 的根因**：supertest 底下的 superagent 建構時寫死 `this._agent = false`。
在 Node 裡 `agent: false` 代表「每個請求自己開一個一次性 Agent、不做連線池」——
於是每個請求都開一條新 TCP 連線、用完就關。

實測（同一份程式碼、同一個資料庫，各跑三次）：**16 / 9 / 14 條紅 → 0 / 0 / 0。**

Ch5 排除表裡有一行「supertest 每個請求開新 server → 試了 `app.listen(0)` → 沒用」。

> **「重用同一個 server」和「重用同一條連線」是兩件事。**
> 前者省的是 listen，後者省的是 TCP 握手與關閉。差別就是全部的差別。
> Ch5 的結論**方向對，但停得太早**。

順帶第四件：ECONNRESET 歸零之後，剩下唯一的偶發失敗確實是 **5 秒測試逾時**
（併發那條要 6-8 次 Neon 往返 ≈ 3-4 秒）。而 Ch5 排除表寫「`testTimeout` 改 30000 → 沒用」
**也是對的** —— 當時真正的問題是 ECONNRESET，連 HTTP 都沒打通。

> **同一個旋鈕在不同的根因下，結論會完全相反。**
> 改設定沒用時，先問「我修的是不是真正的原因」，而不是直接把方法從清單上劃掉。

完整的排除表、探針與指令在 `docs/專案速查.md`，設定的取捨在 `docs/設定檔導讀.md`。

### 4. 「設定寫了但沒生效」的兩次現場，都在同一輪

修 C 的過程中連續踩到兩次，兩次都**沒有任何錯誤訊息**：

1. **第一版方案根本不會有效果。** 原本打算寫 `http.globalAgent.keepAlive = true` ——
   但 superagent 寫死 `agent: false`，**根本不經過 `globalAgent`**。
   照那樣做會看到「沒改善」，然後錯誤地結論「keep-alive 沒用」。
2. **第一版 patch 打在了沒人用的那一份。** pnpm 的隔離讓
   `require('superagent')` 拿到的，跟 supertest 內部用的**不是同一個檔案**：

   ```text
   node_modules/superagent/lib/node/index.js
   node_modules/.pnpm/superagent@10.3.0_.../node_modules/superagent/lib/node/index.js
   ```

   沒有報錯，`_agent` 就只是還是 `false`。

> **判準：改了一個「應該會生效」的設定之後，先驗證它真的接上了，再去測效果。**
> 這一輪的做法是先寫一條測試印出 `_agent` 的實際值 —— 印出
> `Agent keepAlive=true` 才開始量 ECONNRESET。
> 少了這一步，第 1 點和第 2 點都會變成「keep-alive 沒用」這個錯誤結論。

### 5. `git show` 看換行會騙人

commit 完想確認存進去的是 LF，用 `git show HEAD:<檔案>` 數 CR，
每個檔案都報一堆 CRLF —— 看起來像是 commit 錯了。

實際上 **`git show` 會套用簽出時的換行轉換**，而這台機器的 `core.autocrlf` 是 `true`。
索引裡存的是 LF，完全正常。

> **唯一可信的是 `git ls-files --eol`**：`i/` 是索引、`w/` 是工作區。
> `i/lf w/crlf` 就是對的。順帶更正了 `CLAUDE.md` 裡兩處寫錯的說法
> （`core.autocrlf` 的值，以及原本教的檢查方法）。

### 6. 這一輪切得太大 —— 而這是工作方式的錯誤，不是技術錯誤

輪 2 一次要求六個以前沒見過的東西：`instanceof` 的型別收窄、`Record` 查表、
三支分支的順序、mock、`overrideProvider`、`useLogger`。
結果是使用者第一次**完全寫不出東西** —— 前五章至少都能寫出一版再 review。

專案原本的判準是「**這兩件事會不會在同一條測試裡同時失敗？會，就拆**」。
那條判準沒有失效，但它**太晚生效**：要等到寫完、跑出紅燈才看得出來。

> **新判準（開工前就看得出來）：數一數這一輪有幾個「以前沒見過的東西」。
> 超過兩個就拆。**

另外兩件事讓這一章天生比前幾章難，值得寫下來：

1. **這一章沒有第二個範例可以對照。** 寫 `update` 時手邊有 `findOne`，同一個形狀會看到三四次；
   `AllExceptionsFilter` 全專案只有一支。而「同一條規則的第二次現場」正是這個專案
   讓人學會東西的主要機制 —— 這一章拿不到。
2. **這一章的主題本身就是「沒有症狀的錯誤」。** 前幾章寫錯了 tsc 會紅、測試會紅、API 會 500。
   這一章最容易錯的幾點寫錯了**什麼都不會發生**（見下面作業第 3、4、5 題，
   三題都是「測試全綠」）—— 對「自己寫再 review」這個模式最不友善的一種題目。

所以這一章的驗收標準改了：**不是「能不能從零寫出一支 filter」，是「看得懂、說得出它會怎麼壞」。**
`AllExceptionsFilter` 一個專案寫一次、兩年不會再碰；而「這段程式碼壞了看不看得出來」
是每天都在用的能力。

const prismaCode =

## 作業解答

### 第 1 題 —— 8 條紅，而且全部集中在同一個檔案

```text
Test Suites: 1 failed, 4 passed, 5 total
Tests:       8 failed, 71 passed, 79 total
```

紅的八條全在 `test/errors.e2e-spec.ts`（兩個 `describe` 加起來十條，紅了八條，
綠的兩條是「成功的回應完全不受影響」和「驗證失敗」的其中一部分斷言先撞上）。

**真正該注意的是另外四個 suite 一條都沒紅。**
`surveys` / `questions` / `responses` / `health` 加起來 71 條，
其中有三十幾條在斷言錯誤的**狀態碼** —— 而狀態碼沒變，變的只有 body 的形狀。

這就是坑 #2 的現場重演：**錯誤回應的格式，全靠這一個檔案保護。**
拿掉 filter 之後回的是 Nest 內建的舊格式
（`{ statusCode, message, error }`），對那 71 條測試來說完全無所謂。

順帶：安全網那四條也紅了。沒有 filter，Prisma 的 `P2025` 就是一個沒人翻譯的例外 → 500。
**這正是這一章存在的理由。**

### 第 2 題 —— 只有第 5 條紅

```text
Tests: 1 failed, 9 passed, 10 total
● Prisma 錯誤的安全網 (e2e) › 未知的 Prisma 錯誤碼會留下 logger.error，不被安全網吞掉
```

為什麼只有它：那個改法對前端來說**一模一樣** —— 未知碼還是 500、`code` 還是
`INTERNAL_ERROR`（`STATUS_TO_CODE[500]` 查不到 → `FALLBACK_CODE`）、`message` 還是常數。
狀態碼、`code`、`message` 三件事一字不差。

**唯一的差別是伺服器 log 從此一片空白** —— 因為 `logger.error` 住在最後那支 `else` 裡，
而這個改法讓未知碼提早在 Prisma 分支就被處理掉了。

線上出事時前端拿到 500（正確），你打開 log 什麼都沒有。
**這就是為什麼第 5 條測試要驗一個「body 裡看不見的東西」。**

### 第 3 題 —— 全綠。而教練原本的說法是錯的

```text
Tests: 79 passed, 79 total
```

（第一次跑時 `questions` 的併發測試紅了一條，單獨重跑是綠的、全套再跑一次也是綠的 ——
那是 Ch5 學過的「`Promise.all` 只保證一起送出」，跟這題無關。
**偶發的紅要先重跑一次再下結論**，這本身是一課。）

原本的講法是「`HttpException` 也可能有 `code`，於是 404 會被誤判成 Prisma 錯誤」。
**實測推翻了它。** 原因是下一行還有一道查表：

```ts
const prismaError = prismaCode ? PRISMA_ERRORS[prismaCode] : undefined;
```

Node 的 `ECONNRESET`、任何其他帶 `code` 的東西，查 `PRISMA_ERRORS` 都是 `undefined`，
一樣掉進 500。要真的誤判，得有一個「**不是 Prisma 例外、卻剛好帶著 `P2025` 形狀的 code**」
的東西 —— 實務上很罕見。**那道查表本身就是第二道過濾。**

**那為什麼還是要用 `instanceof`？真正的理由是型別。**
鴨子型別那個版本，TypeScript 不知道 `.code` 是什麼，你得寫
`String((exception as { code: unknown }).code)` 才拿得到。而 `as` 是斷言（「相信我」），
**關掉的是檢查、不是風險**（Ch4 學過的那句）。
`instanceof` 讓型別自己收窄成 `PrismaClientKnownRequestError`，`exception.code`
直接就是 `string` —— 一個 `as` 都不需要。

> **判準：`instanceof` 問「它是什麼」，屬性存在性問「它長得像什麼」。
> 問前者，型別系統才有辦法幫你。**

這是這個專案第八次「先給結論、沒有先量」，形狀跟前幾次一樣：**結論方向對、機制錯**。
`instanceof` 確實是對的寫法，但理由完全不是原本說的那個。
（更正後的版本已經寫進 filter 的註解裡。）

### 第 4 題 —— 全綠。壞在測試看不到的地方

```text
Tests: 79 passed, 79 total
```

十條測試裡沒有一條在驗 Prisma 分支的 `message` —— 前三條只驗狀態碼和 `code`，
第 4 條驗的是 `message` 不含 `'mocked'`，但**它走的是 500 分支**（未知碼），
根本碰不到這個改動。

壞的是：`P2003` 發生時，前端會收到

```text
Foreign key constraint violated on the constraint: `Question_surveyId_fkey`
```

**表名和約束名就這樣送出去了。** 測試綠、狀態碼對、body 形狀一字不差。

這也是為什麼 filter 的對策**不是**「記得不要放 `exception.message`」，
而是讓那條路徑上根本沒有變數可以放：三句訊息都是自己寫的常數。
**與其靠紀律，不如讓錯誤在結構上不可能發生。**

### 第 5 題 —— 現在全綠，改名字的那天才會壞

第一步（讓 `PRISMA_ERRORS` 自帶 `code`）：**79 passed 全綠**。合理 —— 兩張表的值一樣。

第二步就是那個實驗：**只改其中一張表**。把 `STATUS_TO_CODE` 的 404 改名：

```ts
[HttpStatus.NOT_FOUND]: 'RESOURCE_NOT_FOUND',   // 只改這裡，PRISMA_ERRORS 不動
```

結果：

```text
Tests: 1 failed, 9 passed, 10 total
● 錯誤回應格式 (e2e) › id 不存在時 body 是 { error: { code: NOT_FOUND, message } }
```

**只有 `HttpException` 那條路紅，Prisma 那條路照樣綠。**
於是同一個 404，走 `findOne` 回 `RESOURCE_NOT_FOUND`、走安全網回 `NOT_FOUND` ——
API 對前端說了兩種話，而**測試只抓到一半**。

這就是「兩個真相來源」的具體長相：它不會在你寫下去的那天壞，
會在**幾個月後某個人改名字的那天**壞，而且只壞一半。

> **對策的形狀跟第 4 題一樣：不是「記得兩邊都改」，是讓兩邊共用同一張表 ——
> 不一致在結構上就不可能發生。**

## 輪 2 後追加問答（2026-08-24）

作業對完之後又追問了三個問題，補在這裡——理由跟坑 #6 一樣：
這一章沒有第二次現場，補講的內容只存在對話裡，換一個對話就等於沒發生過。

### `logger.error` 到底是什麼

它是 filter 建構時建的一個物件（`private readonly logger = new Logger(...)`），
呼叫 `this.logger.error(...)` 只做一件事：**把文字印到終端機**，
本質上跟 `console.log()` 是同一種東西（Nest 多加了時間戳記、分類 `LOG`/`WARN`/`ERROR`）。

**它完全不影響回應給前端的東西。** 前端只看 `res.status(status).json({...})` 那一行，
`logger.error` 是「順便留一筆紀錄給你自己看」。實測過（作業第 1、2 題）：
拿掉整支 filter、或只讓某個分支跳過 `logger.error`，**回應內容一個位元組都不會變**，
差別全部發生在你看不到的地方——線上真的出事時，有沒有堆疊可查。

### 鴨子型別誤判的具體反例

原本的講法（`if ('code' in exception)` 會誤判）被作業第 3 題的實測推翻了：
`ECONNRESET` 之類的東西雖然有 `code`，但那個值查不到 `PRISMA_ERRORS` 表，
一樣掉進 500 分支，79 條測試全綠。

但這不代表鴨子型別完全安全。**真正會誤判的情境**，是有東西「碰巧」帶著
跟 Prisma 一模一樣的碼：

```ts
throw { code: 'P2025', message: '這只是一個普通物件，不是 Prisma 的錯誤' };
```

- 用 `instanceof Prisma.PrismaClientKnownRequestError`：這個假物件不是那個 class
  的實例，判斷式是 `false`，正確地掉到最後的 `else`，回 500。
- 用 `'code' in exception`：判斷式是 `true`，`prismaCode = 'P2025'`，
  查表 `PRISMA_ERRORS['P2025']` **查得到**（因為 `P2025` 真的在表裡），
  於是被誤判成「找不到資料」、回 404。

**判準沒變：`instanceof` 問的是「出生證明」，鴨子型別問的是「長得像不像」。**
上次的 `ECONNRESET` 沒事，只是運氣好、剛好不在表裡；只要有東西的碼剛好
撞上 `P2025`/`P2002`/`P2003`，鴨子型別就真的會誤判，而 `instanceof` 不會。

### 三條分支的 `message` 各自從哪來

`catch()` 裡是三選一的 `if / else if / else`，`message` 在三支分支裡
被賦不同的值，來源完全不同：

| 分支 | 條件 | `message` 的來源 |
| --- | --- | --- |
| A | `prismaError`（認得的 Prisma 碼） | 自己寫的中文，`PRISMA_ERRORS[code].message` |
| B | `exception instanceof HttpException` | 你自己 `throw` 時寫的那句話 |
| C | 都不是 | 常數 `FALLBACK_MESSAGE` |

`NotFoundException` 之所以走分支 B，是因為它**繼承**自 `HttpException`
（`class NotFoundException extends HttpException`）—— `instanceof` 不只看
「完全同一個 class」，也看繼承鏈上有沒有這個祖先。這也是為什麼一個
`else if (exception instanceof HttpException)` 就能接住 `NotFoundException`、
`ConflictException`、`BadRequestException` 全部，不用每種各寫一支分支。
