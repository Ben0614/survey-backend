# Ch13 — 契約驗收:從 Swagger 產型別

> 階段三的第一章。**前端程式碼由 AI 寫,這一章的驗收標準是後端的交付物。**
> 前端骨架(Nuxt 4 + `openapi-typescript`)不在這份文件裡,它的慣例寫在
> `survey-frontend/docs/前端分層慣例.md`。

Ch7 做的 Swagger 在這一章第一次有了**真實用途**:前端的型別是從 `/docs-json` 產的。
而那件事立刻暴露了一個 Ch7 到 Ch12 都沒人發現的問題 —— entity 標記的品質,
從此直接決定前端拿到什麼。

---

## 核心概念

### 1. 型別品質 = entity 標記品質

```
後端的 entity / DTO        ← 真相在這裡
      ↓  @nestjs/swagger 掃描裝飾器
  /docs-json                ← OpenAPI 規格(一份 JSON)
      ↓  openapi-typescript
  schema.d.ts               ← 前端用的型別
```

這條鏈沒有任何一步會「幫你補完」。`@ApiProperty` 少寫一個 `type:`,
前端就少一份型別 —— 而且**中間沒有人會叫**。

Ch7 那些 `type: String, format: 'date-time'` 的堅持在這裡兌現了:
標成 `Date` 的話產出來就是 `Date`,前端 `.getTime()` 直接炸。

### 2. 兩種錯要兩種偵測器

這一章最該帶走的一句話。

| 錯的種類 | 後端 e2e | 前端 `pnpm typecheck` |
| --- | :---: | :---: |
| **型別標錯**(`ownerId`) | ❌ 抓不到 | ✅ 當場紅 |
| **欄位漏寫**(`AnswerEntity.content`) | ✅ 當場紅 | ⚠️ 不紅,但型別檔已經缺了 |

e2e 的一致性測試比的是**key 集合**,完全不看型別;前端 typecheck 看的是型別,
但少一個欄位只是「型別檔小一點」,要等到有人寫程式碼用到它才會炸。

兩邊漏掉的東西**不重疊**,所以缺一不可。

### 3. `security` 與 `responses.401` 是 spec 裡兩個獨立的欄位

```
@ApiBearerAuth()          → security         說「這支**要帶** token」
@ApiUnauthorizedResponse  → responses.401    說「**不帶**會回什麼」
```

Ch10 只標了前者。開工前實測:18 支端點裡 **16 支沒標 401**,
其中 14 支是要帶 token 的(差的兩支是 `GET /health` 與 `POST /auth/register`,
它們本來就公開,沒有 401 是正確的)。

這是「文件說謊」的第四種形狀:**它沒說謊,它只是沒講。**

---

## 決策取捨

### 先抽再加,不是加完再抽

`swagger.e2e-spec.ts` 原有兩條一致性測試,用同一段雙向比對。這一輪要再加五條,
不抽會有七份。

抽的時機刻意選在**加測試之前** —— 那個當下有兩條現成的綠燈當安全網,抽壞了立刻紅。
反過來的話,紅燈時要同時懷疑「helper 抽對了嗎」與「新測試寫對了嗎」。

同一個判準這一輪用了兩次,第二次是 `seedPublishedSurveyWithResponse()`
(建問卷 → 建題目 → publish → 送作答,要被三條測試用到)。
**判準:同一段東西要出現第三次的時候,就是抽的時候。**

### 組合裝飾器,而不是逐支標 401

14 支端點分佈在 5 個 controller,而 `@ApiBearerAuth()` 本來就標在 class 上。
所以選項不是「逐支加 14 次」,而是「5 個 class 各加一行」還是「做一個裝飾器」。

選了後者(`@ApiAuthenticated()`,用 `applyDecorators`),理由不是省字:
**那兩件事必須同時存在,分成兩個裝飾器就會漏,而漏了沒有任何症狀** ——
今天這 14 支就是這樣來的。綁在一起之後,「標了認證卻忘了說 401」
在結構上不可能發生。

> 它跟 Ch11 的 `@Roles()` 是兩種不同的自訂裝飾器:`SetMetadata` 是貼一筆資料
> 等 guard 來讀,`applyDecorators` 是把多個現成的裝飾器打包。
> 連帶一個差別:`@Roles()` 忘了註冊 guard 的話效果是零,
> 而 `@ApiAuthenticated()` 不需要任何人配合 —— 它要影響的只有那份 JSON。

### `GET /auth/me` 不套通用裝飾器

它的 401 有三種來源(沒帶票／票無效／那個人已被刪),對外一模一樣但值得寫在描述裡。
通用裝飾器講不出這件事。

**判準:組合裝飾器只適合「每一支都一樣」的情況。**

### `expectSchemaMatches` 的第三個參數收「一塊 body」

`SurveyEntity` 比的是整包 `res.body`、`ErrorResponseEntity` 比的是 `body.error`、
`AnswerEntity` 比的是 `answers[0]`。把「要比哪一塊」的決定留在呼叫端,
helper 就不必為每個 entity 加一個分支。

## 踩到的坑

### 1. `emitDecoratorMetadata` 救不了聯集型別

`AnswerEntity.question` 的 `@ApiProperty` **沒寫 `type:`**,卻照樣產出 `$ref` ——
因為 `design:type` 記到的是 `QuestionEntity` 這個 class。

而 `ownerId: string | null` 是聯集,`design:type` 只能記成 `Object`,
於是前端產出 `Record<string, never> | null`。

**判準:欄位型別是聯集(含 `| null`)時,`type:` 一定要自己寫。**

### 2. 文件說謊的第三種形狀 —— 而且會跨 repo 傳染

`QuestionEntity.order` 標了 `default: 0`,但 `schema.prisma` 的 `Question.order`
是 `Int` 沒有 `@default`(值由 service 算)。

前兩種形狀 e2e 抓得到(它比 key 集合):多寫了、少寫了。
**第三種是「寫了一句不成立的話」,`default` 不是 key,測試一條都抓不到。**

更值得記的是修完之後前端型別檔的 diff:

```diff
-ownerId: Record<string, never> | null;
+ownerId: string | null;

-/**
- * @description 題號
- * @default 0        ← 那個不成立的預設，早就被複製到前端的型別檔裡了
- */
+/** @description 題號 */
```

### 3. 「文件過期」的第七次,但形狀不同

前六次都是**某一句話**過期。這次是 Ch10 一個全域 guard
**讓所有端點的契約同時過期** —— 行為的改變是集中的,契約的更新卻是分散的。

驗證:`feat(ch7)` 那次的 diff 裡 `ApiUnauthorizedResponse` 出現 0 次、
`ApiBearerAuth` 也是 0 次(當時還沒有認證這回事)。而 Ch10 新寫的
`/auth/me` 與 `/auth/login` 因為是從零寫的,順手就標了 401。
18 支裡剛好只有那兩支有,原因在此。

### 4. `applyDecorators` 裡不能有 `@`

```ts
applyDecorators(@ApiBearerAuth())   // ❌ 語法錯誤
applyDecorators(ApiBearerAuth())    // ✅
```

`@Foo()` 是兩件事的縮寫:`Foo()` 呼叫工廠拿到裝飾器,`@` 把它貼上去。
`applyDecorators` 要的是第一步的產物,貼的動作它自己會做。

### 5. 通用裝飾器套到有特殊描述的端點上,兩個 401 會打架

`GET /auth/me` 一度同時有 `@ApiAuthenticated()` 與它自己的
`@ApiUnauthorizedResponse` —— 而裝飾器由下往上套用,贏的那個不一定是你想要的。

### 6. 教練給錯測試名稱,人就寫不出來

輪 ② 原本給的名稱是「…**而公開的兩支都沒標**」,但 `POST /auth/login` 是
`@Public()` 卻**有 401 而且應該有**(帳密錯就是 401)。名稱裡的斷言不成立,
照著它寫當然寫不出來。

`CLAUDE.md` 那條「測試名稱由教練先給」的理由是「命名該由 AI 負責」——
這次證明了那條規則的另一半:**給錯名稱的成本也由教練承擔。**
