# Ch18 —— 前端部署與端到端驗收

前端上 Vercel、把兩個 origin 接起來,在**線上**跑通「註冊 → 建立 → 發布 → 填寫 → 看結果」。
這是最後一章,也是整個專案第一次有東西同時跑在兩個平台上。

驗收:線上端到端跑通;後端 `pnpm test:e2e` **182 passed**、`pnpm test` **32 passed**、
`tsc` 0、`eslint` 0(這一章沒有動後端程式碼)。

---

## 核心概念

### 一句話:SSR 讓「誰在發請求」有兩個答案,而 CORS 只管其中一個

這一章最值錢的一件事,而且它會騙人:

```
瀏覽器 → 後端     受 CORS 管   登入、送出、刪除…
Vercel → 後端     **不受管**   SSR 那一輪的 useAsyncData（server-to-server，瀏覽器不在場）
```

所以 `CORS_ORIGIN` 設錯時的症狀是:**首頁看起來完全正常**(SSR 那一輪成功,畫面連資料
都渲染好了),**按下任何按鈕才開始壞**。

而且失敗的樣子本身也在騙人 —— preflight 回的是:

```
HTTP/2 204
access-control-allow-headers: Content-Type,Authorization
access-control-allow-methods: GET,HEAD,PUT,PATCH,POST,DELETE
（沒有 access-control-allow-origin）
```

**204 成功,只是少一個標頭**,然後瀏覽器自己把回應丟掉。`curl` 永遠打得通,console 一片紅。

### 第二句話:環境變數的兩種失敗形狀,在線上第一次同時出現

Ch16 定的那條判準(**預設值安不安全**)在這一章拿到了兩個現場:

```
後端 CORS_ORIGIN 拿不到   → 應用啟動失敗           大聲、立刻、不可能忽略
前端 NUXT_PUBLIC_API_BASE → 安靜退回 localhost:3100  沒有錯誤，只是每個使用者
   拼錯或沒設                                        的瀏覽器都去打他自己的 3100 埠
```

所以前端那個**一定要驗**,不能假設它生效了。驗法是看 SSR payload:

```bash
curl -s https://<前端>/login | grep -oE 'apiBase[^,}]{0,80}'
# apiBase:"https://survey-backend-0dku.onrender.com"   ← 生效
# 找不到、或看到 localhost:3100                          ← 沒生效
```

## 決策取捨

### 為什麼是 Vercel

「前端 = Vercel」這個印象有一半是真的:**Vercel 幾乎等於 Next.js 的預設答案**,
但出了 Next 就分散得多(Nuxt 的 Nitro 有十幾個 preset,官方自己推的是跑在
Cloudflare 上的 NuxtHub;企業則多半不在 Vercel,理由通常不是技術)。

這個專案選它的三個理由都不是「它有名」:

1. **Nuxt 4 零設定** —— Nitro 偵測到 Vercel 就自動切 preset,`nuxt.config.ts` 一個字不用改
2. **環境變數的操作跟 Render 一樣** —— 已經在 Render 設過 `CORS_ORIGIN`,這是同一件事的第二次
3. **它讓 Ch14/Ch16 做的 CORS 真的被用到** —— 前後端不同網域正是這一章要驗的東西。
   放同一個平台反而繞過了

### `CORS_ORIGIN` 保留 localhost

```
CORS_ORIGIN=http://localhost:3000,https://survey-frontend-1eep.vercel.app
```

兩個都留、逗號分隔 —— 只留線上的話本機開發就斷了。這也是 Ch16 把它做成**清單**
而不是單一值的兌現。

### Vercel 的 preview 部署:記成已知限制,不做

Vercel 每個 PR 會產生一個網址不同的 preview 部署(`<專案>-<hash>-<團隊>.vercel.app`),
而後端的白名單是**精確字串比對**,不吃萬用字元 —— 所以 preview 的瀏覽器端動作一律被擋
(而 SSR 那一輪照樣成功,所以**首頁是好的、按鈕才壞**,同上面那條)。

三條路:只用 production 網址、後端支援 pattern、用 Vercel 的固定 alias。
**選了第一條**,理由是這個專案沒有 PR 流程(單人、直接推 `main`),preview 根本不會被用到。
真的需要時再處理,不要為了假想的用法先做。

## 踩到的坑

### 1. `/auth/login` 的 401 被當成「你的票過期了」

上線第一天使用者就撞到:**用沒註冊過的帳號登入,跳的是「登入逾時,請重新登入」**。
他從來沒登入過,沒有東西可以逾時。

根因是 `useMyService` 的一個假設:**401 = 你的票有問題**。那句話**只在「帶票去要資源」
的請求上成立**,而 `/auth/login` 是「去換一張票」—— 它的 401 意思是「帳密不對」。

順帶查出來的第三件事:註冊撞名是 409,後端的 `fields` 明確說了是 email,
但前端顯示的是通用的「資料已存在」。

### 2. 第一版的修法是錯的,而且要讀程式碼才知道

原本打算讓 `/auth/*` 帶 `silent: true`(既有的旗標,語意是「失敗的處置由呼叫端負責」)。
讀了程式碼才發現:

```ts
if (error.code === 'UNAUTHORIZED') { auth.clearSession() }   // ← 不看 silent
if (!option.silent) { toast }
if (UNAUTHORIZED && client && !option.silent) { redirect }
```

**`silent` 只關掉 toast 與導頁,`clearSession` 照樣執行。** 而且它不能搬進 `!silent` ——
路由守衛用的就是 `fetchMe({ silent: true })`,而它**需要**那個 clearSession。

所以加了第二個旗標 `anonymous`,兩個各管一件事:

```
silent     錯誤要不要由這裡跳 toast、要不要導頁
anonymous  這個 401 算不算「session 壞了」
```

### 3. 註解說了一句不成立的話 —— 第八次

修 #1 時順手寫了「少了 anonymous 的第二個症狀:已登入的人在 `/login` 打錯密碼會被登出,
**實際發生過**」。

上線驗證時導到 `/login`,畫面直接停在 `/surveys` —— `auth.global.ts` 的最後一段
把已登入的人導走了。**那條路走不到**,清 session 的程式碼存在但沒有入口。

「實際發生過」是我推論出來的,不是觀察到的。差別在**這次是當場抓到的**,不是隔幾章才發現。
旗標仍然留著,但註解改成誠實的版本:一件真的發生過、一件是縱深防禦。

### 4. repo 重建之後 Render 的自動部署沒有恢復,而且**沒有任何症狀**

⚠️ **這一條到收尾時仍然沒有解決,是這個專案的已知限制。**

砍掉重建 repo 之後(見「轉 public」那節),Render 那一側斷了。第一個困難是
**找不到重連的入口**:去 GitHub 的 **Installed GitHub Apps** 找 Render 找不到 ——
那一頁明說「Render has not been installed on any accounts」。
Render 在這個帳號是 **OAuth 授權**(帳號層級),不是 GitHub App;
重連的入口在 **Render 的 Settings → Build → Source → 把 source 重新選到那個 repo**。
官方文件沒有寫清楚,是實際操作才確定的。

**但那只修好一半,而另一半沒有任何症狀:**

```
Manual Deploy      成功
/health            200、database connected
線上服務           好好的
Auto-Deploy 的設定  顯示 On Commit
push 到 main       ← **不會部署**
```

判準性的證據是 `github.com/<repo>/settings/hooks` **是空的** ——
Render 的 OAuth 整合靠一條 repo webhook 收 push 通知,而重選 source 只更新了
「要 build 哪個 repo」,沒有把那條 webhook 建回來。

**所以「設定說會自動部署」與「通知管道存在」是兩件事**,而 Render 的介面只顯示前者。
這一章反覆出現的形狀在這裡出現了最後一次:**「看起來好了」跟「真的好了」不是同一回事。**

試過而無效的:重選 source(第一次做的)、`Use My Credentials`(按鈕是灰的,
因為憑證本來就是自己的)。沒有試的:切一次 Auto-Deploy 開關、Disconnect 再 Connect。

**決定:接受手動部署,不修。** 理由是後端在 Ch18 之後幾乎只會有文件變更,
而文件變更本來就不需要部署 —— 為了一年觸發兩次的便利,不值得付出重建服務的代價
(網址一定會變,而它寫在兩個 repo 的 7 個檔案 15 處,還要重填所有環境變數與設定,
其中 `Health Check Path` 刻意不設那一項忘了就會讓 Neon 的免費額度撐不到月底)。

**這跟同一章對 preview CORS 的判斷是同一條:沒有那個用法就不要先做。**

還有一條保證會動的路,留著沒用:Render 的 **Deploy Hook**(一個私密 URL,POST 進去
就觸發部署)配一個 GitHub Actions。它的好處是**壞掉會在 Actions 頁面直接紅給你看**,
比現在這種「安靜地不部署」好。哪天後端要頻繁改了再回來做,那時它才划算。

環境變數綁在**服務**上不是 repo 上,重連不會弄掉(`CORS_ORIGIN` 驗證過還在)。

### 5. `/health` 回 ok 不代表新的環境變數已經上線

改完 `CORS_ORIGIN` 立刻驗,結果 localhost 那條在、Vercel 那條不在。
不是值填錯 —— 是 **Render 零停機切換,舊實例會繼續服務直到新的起來**。
輪詢第 6 次(約 60 秒)才生效。

**判準:驗證環境變數要驗那個變數的效果,不要用 `/health` 當作「新版上線了」的證據。**

### 6. 搜尋框的 `clearable` 給的是 `null`,不是空字串

使用者回報「按了叉叉,字不見了但清單沒變」。

```ts
q.value = value.trim() || undefined   // ← null.trim() 丟 TypeError
```

而那個例外在 `setTimeout` 裡,**沒有任何地方接** —— 所以 `q` 永遠沒被更新。
console 以外看不出任何東西。

這個洞從 Ch17 輪 ① 就在,只是沒有人按過那個叉叉。型別改成 `ref<string | null>('')`
讓「叉叉會給 null」在型別上看得見,而不是靠註解提醒。

## 這一章新增的驗證動作

- **環境變數要驗效果,不要驗「服務還活著」**(坑 #5)
- **CORS 要驗四項**:目標 origin 有標頭、既有的 origin 沒斷、不在白名單的拿不到標頭、
  帶 `Authorization` 的 preflight 過得了
- **自動部署要用資源指紋驗**:抓 `/login` 裡 `/_nuxt/*.js` 的清單做 hash,
  push 之後輪詢它變不變(Vercel 實測約 40 秒)
- **上線之後 console 仍然要看** —— CORS 失敗不會有錯誤狀態碼,只會少一個標頭
- ⚠️ **後端 push 之後要去 Render 按一次 Manual Deploy**(見坑 #4)。
  前端的 Vercel 是自動的,後端不是 —— **兩邊不一樣,這件事很容易忘**
