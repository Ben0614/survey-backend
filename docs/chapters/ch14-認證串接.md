# Ch14 — 認證串接:CORS 與 401 的一致性

> 階段三第二章,拆成三輪:① CORS 上線 ② 401 的 code 一致性 ③ 前端 `/login` 頁。
> **這份文件只寫後端相關的部分**(`CLAUDE.md` 的規則)——
> 前端的實作教訓寫在 `survey-frontend/docs/前端分層慣例.md`。

這一章是這個專案**第一次有真的瀏覽器打後端**。前十三章的 138 條 e2e 都是
`supertest` 對伺服器發請求 —— 那不是瀏覽器,沒有同源政策、不會發 preflight。
所以有一整類問題,它們一條都碰不到。

---

## 核心概念

### 1. CORS 不是後端擋下請求,是瀏覽器擋下回應

開工前實測(帶 `Origin` 的 `GET /health`):

```
HTTP/1.1 200 OK          ← 伺服器照常執行了
Content-Type: application/json
（沒有任何 Access-Control-* 標頭）
```

**請求進到了 controller、也真的執行了。** 如果那是 `DELETE /surveys/:id`,
東西已經被刪掉了。瀏覽器做的只有一件事:看回應**有沒有** `Access-Control-Allow-Origin`,
沒有就不讓 JS 讀到那份回應。

判準:**`curl` 正常但瀏覽器紅,先想 CORS,不要改後端邏輯。**

### 2. preflight 回 404 而不是 401

```
OPTIONS /surveys  →  404 {"error":{"code":"NOT_FOUND","message":"Cannot OPTIONS /surveys"}}
```

「preflight 會不會被全域 guard 擋成 401」是個常見的擔心,**在這個專案不成立**:
沒有 OPTIONS 路由,Express 找不到 handler,guard 根本沒被執行到。
加了 `enableCors` 之後,cors 中介層在路由之前就把 OPTIONS 處理掉並回 204。

### 3. 錯誤訊息要不要一致,判準是 enumeration 風險

實測 401 的三種來源:

| 失敗 | HTTP | `code` | `message` |
| --- | :---: | --- | --- |
| 沒帶票 | 401 | `UNAUTHORIZED` | 缺少存取權杖 |
| 票無效／過期 | 401 | `UNAUTHORIZED` | 存取權杖無效或已過期 |
| 票有效、人已被刪 | 401 | `UNAUTHORIZED` | 查無此用戶 |

`message` 三種都不同 —— **而那是對的**。實務判準不是「一致比較好」,而是
**攻擊者能不能靠訊息的差異問出他本來不知道的事**:

- `POST /auth/login` 的兩條失敗**必須一模一樣**(email 沒註冊 vs 密碼錯),
  否則可以拿 email 清單掃出誰有帳號 —— 那叫 user enumeration。
  專案已經這樣做了,`auth.e2e-spec.ts:288` 守著。
- **已認證端點的 401 不必一樣**:要走到那裡,對方手上已經有一張簽章正確的票,
  訊息告訴他的事他本來就知道。

RFC 6750 也是分三種(`invalid_request` / `invalid_token` / `insufficient_scope`),
而且 `error_description` 這個欄位存在的目的就是給人看的除錯訊息。

## 決策取捨

### `enableCors` 放 `setup-app.ts` 不放 `main.ts` —— 測試逼出來的

`main.ts` 的設定不會被 `Test.createTestingModule()` 建出來的應用套用。
放那裡的話,三條 CORS 測試會全部拿不到標頭 —— **CORS 就成了沒有測試守著的設定**。

對照 `src/swagger.ts` 刻意**不**放進 `setup-app`(理由在它的檔頭)。
判準是「它產出的是**行為**還是**文件**」:CORS 改變回應標頭,是行為。

### 不開 `credentials`

`LEARNING.md` 的進度表原本寫「`enableCors` 上線(**含 credentials**)」,
這一輪做出相反的決定並改掉了那句話。

理由:`credentials` 管的是「**瀏覽器要不要自動帶上 cookie**」。
前端雖然把 token 存在 cookie,但送出時是自己讀出來、放進 `Authorization` 標頭 ——
瀏覽器全程不需要自動帶任何東西。開了只是擴大攻擊面(而且 `origin` 就不能用 `*`)。

### 401 那一輪:一行程式碼都不改

輪 ② 的結論是現有設計符合實務標準,只補了兩條 `code` 的斷言。
**「不必改」也是合格的驗收結果** —— 前提是你用實測而不是印象得出那個結論。

唯一沒做的是 401 不帶 `WWW-Authenticate` 標頭(RFC 6750 要求)。
自家前後端的 JSON API 多數不帶(前端只讀狀態碼與 body 的 `code`),現階段不加。

## 踩到的坑

### 1. `allowHeaders` 拼錯,而且「看起來有效」

正確是 `allowedHeaders`(有 `ed`)。少了 `ed` 之後:

- **`tsc` 抓不到** —— `enableCors` 的參數是聯集型別(`CorsOptions | CorsOptionsDelegate`),
  TypeScript 的「多餘屬性檢查」在聯集上不生效
- **實測看起來還是對的** —— 沒設定 `allowedHeaders` 時,cors 中介層會把請求的
  `Access-Control-Request-Headers` **原樣反射回去**,所以你問什麼它就答什麼

兩件事疊起來,這個錯字完全無聲。

### 2. `allowedHeaders` 漏了 `Content-Type`

前端送 JSON 一定帶 `Content-Type: application/json`,而那個值**不在 CORS 的安全清單裡**
(只有 `text/plain`、`multipart/form-data`、`application/x-www-form-urlencoded` 是)。
漏了它,所有 POST/PATCH 都會在 preflight 就失敗。

而它**一開始沒有偵測器**:測試只問了 `authorization`。突變測試(把 `Content-Type`
從設定裡拿掉)三條全綠 —— 補上斷言之後才紅。

### 3. 三次「打錯字但測試不紅」

同一輪撞到三次,值得放在一起看:

| 打錯的地方 | 為什麼不紅 |
| --- | --- |
| `allowHeaders` 少了 `ed` | 聯集型別讓 tsc 失效 + cors 的反射行為蓋過去 |
| 漏 `Content-Type` | 測試只問了另一個標頭 |
| 測試裡的 `http://localho**i**st:3000` | `origin` 給字串時 cors **不比對**請求的 Origin,一律回那個固定值 |

第三個順帶推翻了一個直覺:**「不在白名單就不回 Allow-Origin」是錯的**。
真正擋下來的是瀏覽器 —— 它拿 `Allow-Origin` 跟自己的 origin 比,不相等就不放行。

這也改變了那條測試該怎麼寫:名稱從「不在白名單的 Origin,回應不帶 Allow-Origin」
改成「**換一個 Origin 來問,Allow-Origin 不會跟著變**」,而改完之後它剛好同時是
`origin: true`(反射)與 `origin: '*'` 兩種寫錯的偵測器。

### 4. 教練給錯測試名稱,人就寫不出來

輪 ② 原本給的名稱是「…**而公開的兩支都沒標**」,但 `POST /auth/login` 是
`@Public()` 卻**有 401 而且應該有**(帳密錯就是 401)。名稱裡的斷言不成立,
照著它寫當然寫不出來。這是 Ch13 同一個問題的第二次。

### 5. 回頭補測試時,不知道哪些已經有人補過

輪 ② 開工前只掃了 `auth-guard.e2e-spec.ts` 的 9 條(當時全部只斷言狀態碼),
就下結論「三種失敗都沒有測試守著」—— 漏看了 `auth.e2e-spec.ts:361` 那條
名字完全不同、而且連 `error.code` 都驗了的測試。

寫完的第三條因此是**重複的**,突變測試(把 `findMe` 改丟 `NotFoundException`)
同時打紅兩條就是證據。刪掉,原地留註解。

`ch05` 那條「測試數字漲了不代表覆蓋增加了」在這裡多了一種形狀:
**不只可能沒增加,還可能是重複的。**
