# Ch12 — 資源層授權：只能改自己的問卷

Ch11 判斷「你是什麼角色」，Ch12 判斷「**這筆資料是不是你的**」。
兩輪：問卷自己的三支（`ownerId` 就在那筆資料上），子資源五支（要**追溯**回問卷）。

階段二到此結束。**`Survey.ownerId` 是 Ch10 輪 3 填進去的，隔了兩章才第一次被讀。**

---

## 核心概念

### 角色與擁有權是兩條獨立的規則

| | 問什麼 | 資料從哪來 | 失敗 |
| --- | --- | --- | :---: |
| `RolesGuard`（Ch11） | 你是什麼角色 | **token** | 403 |
| `canManageSurvey`（Ch12） | 這筆資料是不是你的 | **token + 資料庫** | 403 |

兩者都回 403，但需要的東西不同——而那個差別決定了判斷放在哪一層。

### 為什麼放 service 不放 guard

**guard 看不到資料。** 它跑在 controller 之前，那時還沒有人查過那份問卷。
要在 guard 裡判斷擁有權，它得自己查一次——而 service 的 `assertExists` 本來就在查同一筆。

```ts
const survey = await this.assertExists(id);        // 本來就有
this.assertCanManage(survey.ownerId, user);        // 順手問一句，零額外查詢
```

`assertExists` 的 `select` 加一格 `ownerId` 是整章最划算的一行：**五個呼叫點因此都不必為了授權再查一次資料庫。**

判準：**授權需要的資料，跟業務資料在同一次查詢裡拿到。**
（這是 Ch3「同一批題目撈了兩次」那個教訓的正面應用。）

### 子資源要追溯到擁有者

題目和作答自己都沒有 `ownerId`，得往上找：

| 端點 | 追溯路徑 | 額外查詢 |
| --- | --- | :---: |
| `POST /surveys/:surveyId/questions` | 手上就有 `surveyId` | 0 |
| `PATCH` / `DELETE /questions/:id` | `findOne` 早就 `include: { survey: true }` | 0 |
| `GET /surveys/:surveyId/responses` | 手上就有 `surveyId` | 0 |
| `GET /responses/:id` | `include` 多撈一格 `survey.ownerId` | 0 |

**整章零額外往返**，而那是因為 `assertCanManage` 收的是 `ownerId` 而不是 `surveyId`——
收 `surveyId` 的話，這四個已經有答案的地方全都要再查一次。

### 授權要排在商業規則之前

```
先問「你能不能碰」（403），再問「這件事現在能不能做」（409）
```

反過來的話，一個完全不相干的人去改別人**已發布**問卷的題目，會拿到
**409「問卷已發布，無法修改題目」**——那句話告訴他這份問卷存在、而且已經發布。

更根本的是**順序本身說錯了話**：「現在不能改題目」的前提是「你有資格改它」。

## 決策取捨

### 保護八支，刻意不保護兩支

| 保護 | 不保護 |
| --- | --- |
| `PATCH /surveys/:id` | `GET /surveys`、`GET /surveys/:id` |
| `PATCH /surveys/:id/publish` / `unpublish` | **`GET /surveys/:surveyId/questions`** |
| `POST /surveys/:surveyId/questions` | **`POST /surveys/:surveyId/responses`** |
| `PATCH` / `DELETE /questions/:id` | |
| `GET /surveys/:surveyId/responses`、`GET /responses/:id` | |

粗體那兩支**保護了這個產品就沒有用了**：填答的人要看得到題目、要填得了問卷。

**這一輪的風險有一半是「保護過頭」**，不是保護不足——所以 e2e 有一條
「任何人都能填別人的問卷 → 201」當反面對照。

### ADMIN 一律跨過擁有權檢查

Ch11 已經讓 `ADMIN` 能刪任何問卷，「能刪不能改」說不通。

代價是每條規則都多一個例外分支，**而例外分支是漏洞最常藏的地方**——
所以那個例外只寫在 `canManageSurvey` 一個地方，八個呼叫點共用。

### 一條規則、一個翻譯層、八個呼叫點

```
canManageSurvey(ownerId, user)          純函式，回 boolean         ← 規則
SurveysService.assertCanManage(...)     不合格就丟 ForbiddenException ← 翻譯
八個 service 方法                        各呼叫一次                  ← 使用
```

八處各寫一次 `if (!canManageSurvey(...)) throw` 就是八次寫反條件的機會。
規則檔本身仍然不認識 HTTP（Ch3 定下的界線沒有破）。

### `404` 先於 `403`

現在的順序是 `assertExists`（404）→ 擁有權（403）。反過來的話，
403 會洩漏「這個 id 存在」——拿一堆 id 去打就能探測。

這一章維持現狀：問卷 id 是 cuid、猜不到，探測價值很低。
但要知道另一條路存在（GitHub 對你沒權限的 private repo 回的是 **404**）。

### 填答仍然匿名

`Response` 沒有任何欄位記錄「誰填的」（Ch5 的決定）。所以
「填答者能不能看自己填的那一筆」**現在沒有答案**——不是漏了，是那個問題還不存在。
要回答它得先在 schema 加一個提交者欄位，那是另一章的事。

## 踩到的坑

### 坑 1：測試的前提資料造出了無主問卷

輪 1 上線後，`PATCH` / `publish` / `unpublish` 那三組**共 6 條測試同時 403**——
連建立者自己都被擋。

原因不在程式碼：那些測試用 `prisma.survey.create({ data: { title } })` 建前提資料，
而**填 `ownerId` 的是 `POST /surveys`（從 token 拿）**，繞過 HTTP 就繞過了它。
所以那些問卷的 `ownerId` 是 `null`，`canManageSurvey` 正確地擋下了。

**這個紅燈是好消息。** 如果規則寫成

```ts
if (survey.ownerId && survey.ownerId !== user.id) throw;   // ✗
```

那 6 條會**全綠**，而那才是壞的：`&&` 在 `null` 短路，整個檢查被跳過 → 任何人都能改無主問卷。

`ownerId` 是 `String?`（Ch9 加不了 `NOT NULL` 的結果），所以無主問卷是真的存在
——dev 資料庫裡就有 9 份。

**「排除誰不行」的寫法永遠會多出一批「條件不成立所以被放行」的情況，而那批通常就是你沒想到的那批。**
（`null`、`undefined`、空字串、空陣列都是同一族。這是「預設拒絕」的第六次。）

### 坑 2：修完前提資料，順帶修好三條假綠

那三條原本是**綠的**：

```
改別人的問卷 → 403
發布別人的問卷 → 403
撤回別人的問卷 → 403
```

但問卷是無主的，所以**任何人**去打都是 403，包括建立者自己。
它們驗的是「無主問卷擋所有人」，不是「別人的問卷擋你」。

**假綠的第十種：斷言正確、狀態碼正確、名稱也正確，但前提資料沒有建立起測試名稱描述的那個情境。**

### 坑 3：撈進來忘了剔除，會靜默改掉 API 契約

`responses.findOne` 跟其他四個呼叫點不一樣：**它撈回來的那個物件就是 API 的回應本身**。

所以 `include: { survey: { select: { ownerId: true } } }` 之後，回應會多一個 `survey` 欄位——
而 `ResponseEntity` 沒宣告它，`swagger.e2e-spec.ts` 的一致性測試**只涵蓋
`SurveyEntity` 與 `ErrorResponseEntity`**，`ResponseEntity` 不在守備範圍。

**沒有任何工具會叫。** 所以這一章順手補了一條 `GET /responses/:id 的回應不含 survey 欄位`。

（對照 `questions` 的 `update` / `remove`：它們回的是 `prisma.question.update(...)`
另一次查詢的結果，`findOne` 的 `include` 不會漏出去。**同一個手法，一支要剔除、兩支不用**——
判準是「這個查詢的結果會不會被當成回應送出去」。）

### 坑 4：檔頭從 Ch5 漂移到 Ch12

`survey.rules.ts` 的檔頭一直寫著「**兩條**商業規則」，而 `canSubmitResponse` 是 Ch5 加的
——**漏了七章**。同一件事也發生在 `CLAUDE.md`（「Ch5 的…**預計**是第三條」）、
`LEARNING.md` 的「貫穿全程的商業規則」、以及 `src/swagger.ts` 的 `/docs` 說明。

四個地方全部說「兩條」，而實際是四條。

**加函式時回頭看一眼同一個檔案最上面的檔頭**——它就在那裡，但沒有人會被迫看到它。

## 作業

1. `if (survey.ownerId && survey.ownerId !== user.id) throw` 這行，
   `ownerId` 是 `null` 時會怎樣？為什麼測試抓不到？
2. `assertCanManage` 收 `ownerId` 而不是 `surveyId`，省下了什麼？
3. 擁有權檢查放在 `canEditQuestions` **後面**，一個不相干的人去改別人已發布問卷的題目
   會拿到什麼？為什麼那是問題？
4. `questions.findOne` 的 `include` 撈了整份 survey，為什麼不必剔除；
   `responses.findOne` 撈了 `survey.ownerId`，為什麼一定要剔除？
5. 為什麼 `POST /surveys/:surveyId/responses` 不能加擁有權檢查？
   哪一條測試會告訴你加錯了？

## 作業解答

1. `null` 是 falsy，`&&` **短路**——右邊那個 `!==` 從頭到尾沒被執行，
   整個條件是 `null`（falsy）→ **不丟例外 → 放行**。
   測試抓不到是因為 `resetDb` 之後所有問卷都是測試自己建的、都有擁有者，
   **e2e 造不出無主問卷**。抓得到它的是單元測試 `canManageSurvey(null, 一般使用者)`。
2. 省下**四次資料庫往返**。八個呼叫點裡有七個手上早就有 `ownerId` 了
   （`assertExists` 的回傳、`questions.findOne` 的 `include`）；收 `surveyId` 的話
   那些地方全都要為了授權再查一次——正是 Ch3「同一批題目撈了兩次」的重演。
3. 拿到 **409「問卷已發布，無法修改題目」**。問題有兩層：它洩漏了「這份問卷存在
   而且已發布」，而且**順序本身說錯了話**——「現在不能改」的前提是「你有資格改」。
   而這個錯很難發現，因為改題目的正常測試一定用 DRAFT，剛好繞過這個分岔。
4. 差別在**那個查詢的結果會不會被送出去**。`questions.update` 回的是
   `prisma.question.update(...)` 另一次查詢的結果，`findOne` 只是中間步驟；
   `responses.findOne` 撈到的那個物件**直接就是回應**。
5. 填答是這個平台的用途——任何登入的人都該能填任何已發布的問卷。加了檢查
   就只有問卷的主人能填自己的問卷，等於沒有人能填。
   告訴你加錯的是 `任何人都能填別人的問卷 → 201`，那條反面對照就是為此而寫。
