# Ch9 — 認證基礎（User model、bcrypt、註冊登入）

階段二第一章，也是這個專案第一次處理**機密資料**。四輪：`User` model 與 migration、
註冊、登入、`Survey.ownerId`。

**這一章做完，登入不會有任何效果** —— 沒有 token、沒有 session，回應完伺服器就忘了。
真正讓它有用的是 Ch10 的 JWT。這一章驗證的只有「密碼比對這段邏輯是對的」。

---

## 核心概念

### 雜湊不是加密：它沒有反向

`bcrypt.hash(密碼, 10)` 產生的東西**無法還原成原本的密碼**，所以驗證的方式不是
「解開來比對」，而是 `bcrypt.compare(明文, 雜湊)` —— 由演算法自己判斷。

也因此不能寫成 `user.passwordHash === await bcrypt.hash(dto.password, 10)`：
**bcrypt 每次都用新的隨機 salt**，同一個密碼雜湊兩次結果不一樣。

那個 `10` 是 cost factor，成本與安全的取捨。**雜湊慢是刻意的** —— 慢的是攻擊者的暴力破解。

### 三層防線，這一章第一次三層都用到

| 層 | 這一章的體現 | 繞過 HTTP 還在嗎 |
| --- | --- | --- |
| DTO（`ValidationPipe`） | email 格式、密碼長度 → 400 | ❌ |
| service | 密碼比對、統一的失敗訊息 → 401 | ✅ |
| 資料庫（`@unique`） | email 不可重複 → P2002 → 409 | ✅ **一直都在** |

**409 完全不用自己寫**：`@unique` 讓 Prisma 丟 `P2002`，Ch6 的 filter 翻成 409。
Ch6 那一章的投資在這裡回本。

### 「一個名字，三種包裝」

401 的英文是 `Unauthorized`，於是：`HttpStatus.UNAUTHORIZED` /
`throw new UnauthorizedException(...)` / `@ApiUnauthorizedResponse`。
命名完全規則，學會英文名字就同時學會三個。完整對照表在
[`docs/錯誤處理與狀態碼.md`](../錯誤處理與狀態碼.md)。

### 對已有資料的表加欄位

輪 4 的整堂課。dev branch 當時有 **9 份問卷、0 個使用者**，而 `ownerId` 有外鍵約束
—— 所以「填一個合法的 User id」根本做不到，`NOT NULL` 的 migration 會直接失敗。
真實專案的標準解是**三步 migration**（先 nullable → 回填 → 再改 `NOT NULL`），
這裡做不了，因為連可以回填的值都還不存在。

## 決策取捨

### `bcryptjs` 而不是原生 `bcrypt`

原生版有安裝腳本，而 pnpm 10+ 預設不執行 —— 要加進 `pnpm-workspace.yaml` 的
`allowBuilds`（那個檔案已經為 Prisma 踩過一次），Windows 上還可能要裝編譯工具。
`bcryptjs` 是純 JS、沒有 install script、自帶型別。代價是慢 2~3 倍，這個規模無所謂。

### 全域 `omit`，不是每支查詢各寫一次 `select`

`passwordHash` 擋在 `PrismaService` 的 `omit` 裡，是**預設拒絕**。
逐一排除要在 N 個查詢點各對一次，漏一處的症狀是雜湊出現在 API 回應裡 ——
tsc 綠、測試綠、`/docs` 看起來也正常。

代價要記住：**之後新增的欄位預設會被送出去**。所以規則是「機密欄位一律加進那一層」。

### 兩條失敗路徑同一個例外、同一句訊息

分開回（404 查無此帳號 / 401 密碼錯誤）的話，任何人拿一份 email 清單掃一遍
就能篩出誰是使用者，**連猜密碼都不用**（user enumeration）。

訊息抽成常數不是為了少打字，是讓「兩處分岔」在結構上不可能發生。

**時間差沒有處理**（帳號不存在時比走完 `bcrypt.compare` 快得多，時間本身就洩漏答案）。
成本與收益在這個階段不成比例 —— 但要知道那個洞還在，而不是以為統一訊息就完事了。

### 登入不重用 `RegisterDto`

兩個理由都跟 `@MinLength(8)` 有關：密碼規則會變，套用新規則會把用舊密碼的人鎖在門外；
而登入時回「密碼至少要 8 碼」等於免費告訴攻擊者你的規則。
**驗證「新密碼合不合規」和驗證「這個密碼對不對」是兩件事。**

### `onDelete: SetNull` 而且明寫

選填關聯的預設就是 `SetNull`，但**預設值是隱形的** —— 而隔壁 `onUpdate` 的預設是
`Cascade`，兩個不一樣。語義上也對：帳號刪掉、問卷留著變無主，
別人填的作答不該因為建立者離職就消失。已實測：刪掉 user 之後
survey / question / response / answer **四樣全留**，只有 `ownerId` 變 `null`。

## 踩到的坑

### 坑 1：`migrate dev` 不會順帶 `generate`，而 `tsc` 是綠的

輪 1 與輪 4 各一次。`prisma migrate dev` 跑完、migration 也套用了，
但 `src/generated/` 停在幾小時前 —— 而 `tsc` **0 errors**，因為那時候還沒有任何程式碼
用到新的 model／欄位。

**判準：改完 schema 的驗收不能只看 `tsc`，要直接查產物** ——
`ls src/generated/prisma/models/` 或 `grep -rl "<新欄位名>" src/generated/`。

### 坑 2：test branch 沒套用 migration，症狀指著自己的程式碼

輪 2 第一次跑 e2e 就 500：

```
The table `public.User` does not exist in the current database.
   at auth.service.ts:10
```

看起來像 service 寫錯，其實是**那條資料庫沒有那張表**。`migrate dev` 只動 `.env` 指的
dev branch。（Ch6 的 filter 認得 P2025/P2002/P2003，**不認得 P2021**，所以落到 500。）

**這一章因此多了一支 `pnpm migrate:test`** —— 靠結構，不靠紀律。

### 坑 3：entity 寫了 `passwordHash`，文件承諾一個不存在的欄位

`UserEntity` 一度有 `passwordHash` 屬性。實際回應沒有它（全域 `omit` 擋掉了），
於是 `/docs` 上的契約在說謊，而 tsc 綠、測試綠、Swagger 也不會抱怨。

**entity 不過濾任何東西** —— 少寫是「文件漏講」，多寫是「文件說謊」，兩個方向都是 bug。

### 坑 4：`login` 直接 `return user`，雜湊會被送出去

`login` 是全專案唯一寫 `omit: { passwordHash: false }` 的地方（比對密碼需要它）。
**要回來之後那個物件就帶著雜湊了**，直接 `return` 等於送給前端。
三道防線都不擋：tsc 綠（型別本來就有）、Swagger 綠（entity 只是文件）、測試綠（還沒寫）。

「預設拒絕」的價值正是如此 —— 需要例外的地方只剩一處，而那一處你會知道自己在做什麼。

### 坑 5：改了 schema 沒重新產生 migration，資料庫其實是 `CASCADE`

輪 4 最貴的一個。先產生 migration、再回頭把 `onDelete` 改成 `SetNull` 而沒有重新產生
—— 那行字只存在於 `schema.prisma`。後果不只一張表：`Question` / `Response` / `Answer`
對 `Survey` 都是 `Cascade`，**刪一個帳號會把所有人填的作答一起帶走**。

而 `prisma migrate status` 說 **`Database schema is up to date!`** ——
它只比對「`migrations/` 資料夾」與「已套用清單」，**完全不看 `schema.prisma`**。
抓得到的只有 `prisma migrate diff`。

**判準：`schema.prisma` 不是資料庫的真相，`prisma/migrations/` 才是。**

（`prisma/migrations/` 有兩個 `add_survey_owner` 資料夾就是這件事的痕跡，刻意不壓平。
只有「還沒進版控、也還沒套到別人的資料庫」的 migration 才可以重做。）

### 坑 6：檔頭沒有在實作最後一輪寫完

`CLAUDE.md` 寫著「檔頭在實作最後一輪就寫完，不留到收尾」，但 `src/auth/` 六個檔案
加測試檔全部是收尾才補的，動線斷了三輪。**原因是開工指引裡沒有把它列進「要改的檔案」**
—— 規則存在、但沒有被放進那份逐檔案清單，於是它跟沒有一樣。
這是 Ch7 坑 #5 的同一個形狀：**規則有效，但使用時機錯了。**

## 作業

1. `bcrypt.compare(明文, 雜湊)` 為什麼不能寫成 `雜湊 === await bcrypt.hash(明文, 10)`？
2. `register` 沒有「先查 email 有沒有重複」那段。把它加回去，第 4 條測試會不會紅？這說明了什麼？
3. 登入失敗時，「帳號不存在」與「密碼錯誤」回一模一樣的訊息。**這樣就沒有洩漏了嗎？**
4. `Survey.ownerId` 如果寫成 `String`（不加問號），`migrate dev` 會發生什麼事？
5. `prisma migrate status` 說 `Database schema is up to date!`，能不能據此判斷「資料庫跟 `schema.prisma` 一致」？

## 作業解答

1. **bcrypt 每次都用新的隨機 salt**，同一個密碼雜湊兩次結果不同，直接比對永遠是 `false`。
   `compare` 會從既有的雜湊裡讀出當初那個 salt 再算一次。
2. **不會紅。** 409 是 `@unique` → `P2002` → Ch6 filter 給的，那段檢查只是多一次資料庫往返
   （約 500ms）。而且它擋不住併發 —— 兩個請求可以同時查到「沒有」。**真正的防線在資料庫。**
3. **沒有。** 時間差還在：帳號不存在時直接 return，比走完 `bcrypt.compare` 快得多。
   這個專案刻意不處理，但「知道洞在哪」和「以為補好了」是兩回事。
4. **直接失敗。** 既有的 9 份問卷需要一個值，而 `ownerId` 有外鍵約束、`User` 表當時是空的
   —— 沒有任何合法的值可以填。這不是 Prisma 的限制，是外鍵的定義。
5. **不能。** 它只比對 `migrations/` 資料夾與資料庫記錄的已套用清單，**不讀 `schema.prisma`**。
   輪 4 就是這樣：三個 migration 都套用了（所以它說 up to date），
   但 schema 寫 `SetNull`、資料庫是 `CASCADE`。唯一抓得到的是 `prisma migrate diff`。
