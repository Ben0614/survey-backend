# 教學註解設計（2026-07-31）

## 背景

專案是教學型的，但 Ch0 的環境建置程式碼由 AI 產生。程式碼能跑、作業也做出預期結果，`LEARNING.md` 因此把 Ch0 標成 ✅ —— 但那個 ✅ 只代表環境可用，不代表使用者讀得懂。

準備進 Ch1 時，使用者表示對 NestJS 與 Prisma 7 都陌生，連 `main.ts`、`@Controller('health')`、`schema.prisma` 都看不懂。此時推進 Ch1，只會讓看不懂的檔案從 9 個變成 12 個。

根因：既有註解幾乎都在解釋**為什麼這樣選**，那是寫給「已看得懂程式碼、但不知當初決策脈絡」的讀者。對初學者順序反了 —— 要先有「這行在做什麼」，「為什麼」才有掛載的地方。

## 決策

### 1. 兩種註解並行，靠標記區分

| 寫法 | 內容 | 生命週期 |
| --- | --- | --- |
| `// [教學] ...` | 這行在做什麼 | 暫時鷹架，日後搜尋 `[教學]` 整批清除 |
| 無標記 | 為什麼這樣選 | 永久 |

既有的無標記註解一律不改寫、不加標記。

**取捨：** 也考慮過把說明全部放在獨立文件、程式碼保持乾淨。否決的理由是「看 code 卡住時要跳出去查」這個摩擦太大，對初學者尤其致命。標記制讓兩者兼得：現在就地可讀，日後可一鍵清除。

### 2. 密度：逐段，不逐行

每個「做一件事」的段落配一個註解區塊，`import` 這類一看就懂的不寫。

**取捨：** 逐行註解看似最保險，實際上會讓真正重要的那幾句被淹沒，而且「建立 app 實例」這種把程式碼用中文再唸一遍的註解零資訊量，日後改 code 時還會慢慢變成謊言。決定原則是：**只寫程式碼裡看不到的東西** —— 誰呼叫這行、背後發生什麼、名詞是什麼意思。

### 3. 「下一站」閱讀動線

每個檔案的檔頭最後一行指向下一個該讀的檔案，把 9 個檔案串成單行道：

```text
src/main.ts → src/app.module.ts → src/health/health.module.ts
  → src/health/health.controller.ts → src/prisma/prisma.module.ts
  → src/prisma/prisma.service.ts → prisma/schema.prisma
  → prisma.config.ts → test/health.e2e-spec.ts
```

**理由：** 使用者一半的困難不是看不懂單一檔案，而是不知道從哪開始看、看完接哪個。動線依「一個 HTTP 請求的生命週期」排序，讀完自然理解整體結構。

### 4. 一個概念只解釋一次

decorator、DI、module、provider 等名詞在動線上第一次出現的檔案講清楚，後續改寫「（見 `xxx.ts` 檔頭）」。這是避免鷹架變成噪音的關鍵。

### 5. 標示可跳過的內容

Prisma 7 版本相容產物（`moduleFormat = "cjs"`、`--experimental-vm-modules`、`moduleNameMapper`）明確註明「這現階段可以跳過」。這些與學後端無關，是版本太新的一次性成本，不該消耗使用者的注意力。

### 6. 純 JSON 檔另立文件

`package.json`、`test/jest-e2e.json` 加註解會壞，說明寫在 `docs/設定檔導讀.md`。`tsconfig.json` 可直接加（TypeScript 讀 JSONC）。

## 明確不做

不改程式邏輯、不碰 `src/generated/`、不做逐行註解、不重複解釋同一概念。

## 後續影響

`CLAUDE.md` 的註解規則已同步更新，Ch1 之後新寫的程式碼沿用同一標準；新增檔案時必須插進「下一站」動線，不能讓鏈斷掉。

## 驗收

`pnpm lint`、`pnpm build`（`dist/main.js` 存在）、`pnpm test:e2e` 全數通過，`git diff` 確認無邏輯行異動 —— 已完成。

最終驗收由使用者執行：照動線讀完一遍，能口述「一個 HTTP 請求進來會經過哪些檔案、依賴注入在哪一刻發生」。哪一站卡住，該站的註解就要再補。
