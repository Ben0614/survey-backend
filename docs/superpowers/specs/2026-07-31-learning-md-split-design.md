# `LEARNING.md` 拆分設計（2026-07-31）

## 背景

使用者提議：`LEARNING.md` 的「作業」段落是否該拆出去，否則 18 章會塞爆。

量測後發現前提對、但拆的對象錯。Ch0 共 306 行，拆開來看：

| 區塊 | 行數 | 每章都會有 |
| --- | ---: | --- |
| 核心概念 | 64 | ✅ |
| 決策取捨 | 42 | ✅ |
| 作業 | 49 | ✅ |
| 踩到的坑 | 13 | ✅ |
| **每章重複小計** | **168** | |
| 換機接續 | 45 | ❌ |
| 指令速查 | 24 | ❌ |
| 檔案地圖 | 27 | ❌ |
| 閱讀動線 | 35 | ❌ |
| **專案層級小計** | **131** | |

推估 18 章：`168 × 18 + 131 + 78 ≈ 3,200 行`。只拆作業的話是 `≈ 2,350 行` —— 減 27%，仍然過大，而且多出 18 個作業檔要管理。

**同時發現一個既有錯誤：** 那 131 行的專案層級內容放錯位置。`檔案地圖` 掛在 Ch0 底下卻描述整個專案，從 Ch1 起就會過時 —— 每次新增檔案都得回頭修改一個「已完成」章節。`指令速查` 同樣已經在列 Ch1、Ch14 的指令，本來就超出 Ch0 範圍。

## 需求

使用者三種用法都有（回頭查、接續進度、給 AI 讀），且尚未形成固定習慣。三者指向同一結論：`LEARNING.md` 應瘦身為索引，章節內容分檔 —— 回頭查需要好跳轉、接續進度需要進度表醒目、AI 讀取需要能只讀單章。

## 決策

### 1. 拆兩刀，不是一刀

```text
LEARNING.md                  進度表 + 商業規則 + 課綱修訂 + 索引（~96 行，不再成長）
docs/
├── 專案速查.md              指令速查 / 檔案地圖 / 換機接續 / 閱讀動線
└── chapters/
    └── ch00-環境建置.md     核心概念 / 決策取捨 / 踩到的坑 / 作業
```

檔名用 `chNN-` 前綴確保排序。章節檔**寫到才建立**，不預先產生 17 個空檔。

**取捨：** 只抽專案層級參考（章節仍留在 `LEARNING.md`）會剩 3,100 行，等於沒解決；只拆作業（使用者原提議）投報率最差。拆兩刀讓 `LEARNING.md` 固定在 ~96 行。

### 2. `專案速查.md` 的定位是「現況」而非「歷史」

這是搬移之外的實質修正。放在章節裡的東西隱含「這是當時的紀錄」，更新它感覺像竄改歷史；獨立成檔後定位變成隨專案演進持續更新，`檔案地圖` 過時的問題就消失了。

### 3. 純搬移，兩處例外

內容逐行搬移不改寫。兩處必要調整：

- `檔案地圖` 補上 `docs/` 與 `LEARNING.md`（原本沒有，已經不準確）
- 「`LEARNING.md` 是唯一的跨機進度來源」改為涵蓋 `docs/`

Ch1 那三行「尚未開始」的佔位文字未搬移 —— 進度表已有同樣資訊，等實際開始 Ch1 再建檔。

### 4. 同步更新規則與交叉引用

`CLAUDE.md` 的「每章完成後補進 `LEARNING.md`」改為「補進 `docs/chapters/chNN-*.md`，並更新進度表與索引」，並加上「不要把章節內容寫回 `LEARNING.md`」。不改的話下次仍會往 `LEARNING.md` 塞。

另有 5 處指向舊位置的交叉引用需更新：`docs/從零建置.md`（2 處）、`docs/設定檔導讀.md`、`prisma/schema.prisma`、`prisma.config.ts`。

### 5. 時機：現在做

目前只有 Ch0 一章，搬移成本最低。到第 5 章再拆是五倍工作量。

## 驗收

- 搬移完整性由建構保證：所有區段行號連續覆蓋原檔，僅排除標題、進度表、分隔線與 Ch1 佔位
- 死連結檢查：`LEARNING.md`、`CLAUDE.md`、`docs/**/*.md` 的相對連結全數可解析
- `pnpm lint` / `pnpm build`（`dist/main.js` 存在）/ `pnpm test:e2e` 全數通過 —— 確認只動註解與文件
