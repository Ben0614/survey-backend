## 指令速查

```bash
# 開發
pnpm start:dev          # 啟動並監看檔案變更（開發時都用這個）
pnpm build              # 編譯到 dist/
pnpm start:prod         # 跑編譯後的產物，模擬正式環境

# 測試
pnpm test:e2e           # E2E 測試（會連真實資料庫，約 30 秒 —— 時間幾乎都花在網路往返）
pnpm test               # 單元測試（rootDir=src、*.spec.ts；目前只有 survey.rules.spec.ts，0.5 秒）
pnpm kill:jest          # 清掉殘留的 jest 行程（test:e2e 之前會自動跑，很少需要手動）
pnpm lint               # ESLint 檢查並自動修正

# API 文件（Ch7；要先 pnpm start:dev）
#   http://localhost:3100/docs        Swagger UI，給人看、可以直接送請求
#   http://localhost:3100/docs-json   OpenAPI 規格，給機器讀（Ch13 產型別的輸入）

# 看 Prisma 實際送出的 SQL（Ch3 第二段加的，預設關）
# 改 .env 的 PRISMA_LOG_QUERIES=1，或只影響當下視窗：
$env:PRISMA_LOG_QUERIES=1; pnpm start:dev

# Prisma
pnpm exec prisma generate        # 依 schema 重新產生 client（改完 schema 一定要跑）
pnpm exec prisma migrate dev     # 產生並套用 migration（Ch1 開始用）
pnpm migrate:test                # 把 migration 套用到 test branch（改完 schema 一定要跑，見下）
pnpm exec prisma migrate deploy  # 只重播既有 migration，不產生新的（建測試/正式資料庫用）
pnpm exec prisma db seed         # 塞開發用假資料（可重複執行）
pnpm exec prisma studio          # 開瀏覽器 GUI 瀏覽資料

# 線上環境（Ch8 起）—— 服務跑在 Render，資料庫是 Neon 的 production branch
#   https://survey-backend-0dku.onrender.com/health   確認服務活著、資料庫連得上
#   https://survey-backend-0dku.onrender.com/docs     Swagger UI（刻意保持公開，理由見 ch08）
#   https://survey-backend-0dku.onrender.com/surveys  API 本身
#
# 對正式資料庫下指令：行內帶 DATABASE_URL（Git Bash 語法，PowerShell 沒有這種寫法）
DATABASE_URL="<production 連線字串>" pnpm exec prisma migrate deploy
DATABASE_URL="<production 連線字串>" pnpm exec prisma studio
```

> **最常忘記的一件事：** 改完 `schema.prisma` 之後沒跑 `prisma generate`，於是 TypeScript 型別還是舊的，出現「明明欄位加了卻說不存在」的錯誤。
> **`prisma migrate dev` 不會幫你跑它**（Ch9 實測兩次都沒有），而且 `tsc` 在還沒有人用到新欄位時一定是綠的 —— 要查就直接看產物：`ls src/generated/prisma/models/`。

> **改完 schema 之後，三條 branch 各自怎麼套用：**
>
> | branch | 誰套用 |
> | --- | --- |
> | dev | `prisma migrate dev` 當下就套用了 |
> | **test** | **只有這條要你動手：`pnpm migrate:test`** |
> | production | `git push` 之後 Render 的 Build Command 自動跑 |
>
> 忘記 test 的症狀有誤導性：e2e 突然 500，訊息是 `The table public.X does not exist`
> 而且指著你剛寫的 service（Ch9 輪 2 實際踩過）。

## 閱讀動線

Ch0 的程式碼是由 AI 產生的，所以額外補了一批**教學註解**幫助理解。有兩個約定：

- `// [教學] ...` —— 解釋「這行在做什麼」。這是**暫時的鷹架**，等你熟了之後全域搜尋 `[教學]` 就能整批清掉。
- 沒有標記的註解 —— 解釋「為什麼這樣選」，長期保留。

每個檔案的檔頭最後一行寫著「下一站」，把所有檔案串成一條單行道。**卡住時就從起點照著走一遍**：

## 什麼時候用 API、什麼時候用 Prisma

寫到 Ch3 後半最容易卡住的一個問題。它其實是**三個不同的問題**被混在一個詞裡。

### 先破一個前提：應用程式內部永遠不打自己的 HTTP

`QuestionsService` 要確認問卷存在，是**直接呼叫 `SurveysService.assertExists()` 這個方法**，不是去打 `GET /surveys/:id`。同一個行程裡的東西不會繞出去再繞回來。

所以在 `src/` 底下，「用 API 還是用 Prisma」根本不是一個選項：

| 檔案 | 只會出現 | 絕對不該出現 |
| --- | --- | --- |
| `*.controller.ts` | `@Param` / `@Body` / 呼叫 service | **任何 `prisma.`** |
| `*.service.ts` | `prisma.` / 呼叫別的 service | `req` / `res` / `@Param` |

判斷方法很機械：這行在處理「網址和 body 長什麼樣」→ controller；在處理「資料怎麼存取」→ service。

（唯一的例外是 service 丟 `NotFoundException`。Ch2 把它標成「一道刻意留著的裂縫」，**Ch6 回頭重看過了，結論是維持** —— 判準是「這支 service 除了 HTTP 之外還有沒有第二個呼叫者」，完整理由見 `surveys.service.ts` 檔頭。）

### service 內部：什麼時候呼叫別的 service、什麼時候直接用 prisma

每張表有一個**擁有者** service（`Survey` → `SurveysService`，`Question` → `QuestionsService`，`Response` / `Answer` 目前還沒有）。擁有者的意思是：**跟這張表有關的規則只寫在那一個檔案裡。**

判準不是「這是誰的表」，是**「這裡有沒有規則要遵守」**。三種情況：

| 情況 | 怎麼寫 | 例子 |
| --- | --- | --- |
| 要**套用別人的規則**（含錯誤語意） | 呼叫那個 service | `await this.surveysService.assertExists(surveyId)` —— 要的不只是查到，是「不存在要照 Survey 的規矩回 404」 |
| 只是**順路帶關聯資料** | 直接用 prisma 的 `include` | `question.findUnique({ include: { survey: true } })` —— 主詞還是題目，沒有套用任何 Survey 的規則 |
| 那張表**還沒有擁有者** | 暫時直接用 prisma | `prisma.response.count({ where: { surveyId: id } })` |

> **嗅覺測試：如果你正要寫「查別人的表 + 丟例外」，停手** —— 那段邏輯已經存在了。複製一份的代價是：哪天加了軟刪除，漏改的那一份不會報錯，只會安靜地放行。

一個必須知道的限制：**依賴只能單向。** `QuestionsService` 注入 `SurveysService`，所以反過來不行（Nest 會噴循環依賴）。這就是為什麼 `SurveysService.remove` 不去呼叫「刪掉所有題目」，而是靠資料庫的 `onDelete: Cascade`。

### e2e：兩種都會出現，所以規則要更清楚

> **API 只出現在「這條測試要測的那一行」，前後都用 prisma。**

```ts
it('有填答時 unpublish 回 409', async () => {
  // ① 前提 Arrange —— prisma
  const survey = await prisma.survey.create({
    data: { title: '已發布問卷', status: SurveyStatus.PUBLISHED },
  });
  await prisma.response.create({ data: { surveyId: survey.id } });

  // ② 被測的行為 Act —— API
  await request(app.getHttpServer())
    .patch(`/surveys/${survey.id}/unpublish`)
    .expect(409);

  // ③ 驗證 Assert —— prisma
  const after = await prisma.survey.findUnique({ where: { id: survey.id } });
  expect(after?.status).toBe(SurveyStatus.PUBLISHED);
});
```

**前提為什麼不能用 API**（由輕到重）：

1. 有些狀態 API 根本做不出來 —— 「有人填答」的端點要 Ch5 才有
2. `POST /surveys` 一壞，全部測試一起紅，看不出到底哪一支端點有問題
3. 「測 unpublish」變成同時也在測 create，一條測試不再只回答一個問題

**驗證為什麼要用 prisma**：**回應 body 不等於資料庫的真相。** `DELETE` 回的是刪除前的快照，有內容不代表資料還在；`409` 只證明它拒絕了，不證明它沒有先動資料再拒絕。

不過也不必每條都查 —— 分兩種：

| 情況 | 要不要二次查詢 | 為什麼 |
| --- | --- | --- |
| `DELETE` 回 200 | **要** | body 是刪除前的快照 |
| 任何 `409` / `400` | **要** | 錯誤回應完全沒提到資料庫現在長怎樣 |
| `PATCH` / `POST` 回 200/201 | 可省 | `prisma.update()` 回的**就是**寫入後的那一列，再查是問同一個來源 |

### 卡住時問自己三句

1. **我在哪個檔案？** `src/` 底下 → 看上面那張表，沒有選擇
2. **這一行是「準備」還是「被測的動作」？** 準備 → prisma；動作 → API
3. **我要驗的是「回應長怎樣」還是「資料庫變怎樣」？** 前者看 `res.body`，後者用 prisma 再查一次

## e2e 測試連線問題怎麼查

`pnpm test:e2e` 突然大量失敗、而且**每次紅的測試都不一樣**時看這一節。
這是 Ch5 收尾時實際花掉兩小時換來的，寫下來就是為了下次十分鐘解決。

> ### 2026-08-22 更新：根因找到了，而且已經修好
>
> Ch5 當時的結論是「這台機器 HTTP socket 層的環境問題」，**那個結論方向對、但不是終點**。
>
> **真正的原因**：supertest 底下的 superagent 在建構時寫死 `this._agent = false`。
> Node 裡 `agent: false` 的意思是「這個請求自己開一個一次性的 Agent、不做連線池」——
> 於是**每一個請求都開一條新的 TCP 連線、用完就關**。全套 e2e 打下來是
> 兩三百條 socket 的開開關關，Windows 的 socket 層扛不住就開始 reset。
>
> **修法**：`test/setup-env.ts` 把它換成 keep-alive 的 Agent（那段有完整註解）。
>
> **實測**（同一份程式碼、同一個資料庫，各跑三次）：
>
> | | 失敗數 | ECONNRESET | 斷言失敗 |
> | --- | :---: | :---: | :---: |
> | 修之前 | 16 / 9 / 14 | 16 / 9 / 13 | 0 |
> | 修之後 | 0 / 0 / 0 | **0 / 0 / 0** | 0 |
>
> **這一節底下的排除表與探針仍然留著** —— 它們是「怎麼查」的方法，
> 下次遇到別的連線問題還是從那裡開始。而且那張表現在多了最有價值的一行：
> **Ch5 試過「重用同一個 server」，但沒試過「重用同一條連線」——
> 那是兩件不同的事，而差別就是全部的差別。**

### 第一步：先判斷是環境還是程式碼（30 秒）

| 觀察 | 代表什麼 |
| --- | --- |
| **每次跑失敗的測試都不一樣** | 程式碼錯會**固定**紅同一條 |
| 錯誤是 `read ECONNRESET` 之類的，**不是 `Expected` / `Received`** | 連 HTTP 都沒打通，**斷言根本沒執行到** |
| 單獨跑某個 suite 有時全過 | 資源競爭或環境不穩 |

**「失敗的測試每次不同」+「錯誤不是斷言」= 先懷疑環境，不要回頭改程式碼。**

### 第二步：跑那支關鍵探針（2 分鐘）

```bash
pnpm build && node scripts/probe-db.js
```

它**把 HTTP 拿掉**，只用 Prisma 重現 e2e 的資料庫工作量（TRUNCATE + 巢狀 write + count）。
結果只有兩種意思：

- **全部成功** → 資料庫沒問題，往 HTTP 那一層查（supertest ↔ Nest）
- **有失敗** → 資料庫或網路真的有問題

> **這一支要第一個跑。** Ch5 那次的教訓就是順序反了 —— 先猜「孤兒行程」、清掉之後
> 症狀確實減輕，於是又重試了好幾輪。**「症狀減輕」不等於「找到原因」。**

需要看連線池本身（能開幾條、閒置多久被收掉、重連多慢）就跑：

```bash
node scripts/probe-conn.js
```

### 第三步：清掉孤兒行程（**現在是自動的**）

中斷過測試（Ctrl+C、逾時、關掉終端機）之後，**外層的 `pnpm` 被殺掉了，裡面的 jest 還活著**
—— Windows 沒有 process group，殺父行程不會連坐子行程。每個殘留的 jest 都握著一組連線。

**2026-08-22 起不必再手動處理**：`package.json` 的 `pretest:e2e` 會在每次
`pnpm test:e2e` 之前自動跑 `scripts/kill-stale-workers.js`，所以**每一輪都從乾淨狀態開始**，
不管上一次是怎麼死的。有清到東西時它會印出來，沒有就完全安靜。

想手動清（例如 Ctrl+C 之後不打算馬上重跑）：

```bash
pnpm kill:jest
```

> **為什麼是 `pre` 而不是 `post`**：`post` 在被中斷時根本不會執行 ——
> 而「被中斷」正是產生殘留行程的那個情況。
>
> **為什麼腳本叫 `kill-stale-workers.js` 而不是 `kill-stale-jest.js`**：
> 它用「命令列含 `jest.js`」找目標，而後者的檔名裡就含有 `jest.js` 這個子字串，
> **它會把自己殺掉**。比對條件也刻意不用 `test:e2e` —— 那會匹配到正在呼叫它的 pnpm 父行程。

另外，`--forceExit` 解決的是另一半問題：**測試跑完、summary 都印出來了，但指令不結束**
（jest 在等殘留的 handle）。實測差別是「8 分 20 秒還在卡」對「40 秒自己結束」。

**不要並行跑 `pnpm test:e2e`。** `test/jest-e2e.json` 的 `maxWorkers: 1` 只擋得住
「同一個 jest 行程內」的並行，**擋不住兩個 jest 行程**
（Ch3「隔離做得夠不夠，要等第二個參與者出現才知道」的第二次現場）。

### Ch5 那次的實測排除表

七個假設，全部實際量過。**留著是為了不要再測一次**：

| 假設 | 怎麼測 | 結果 |
| --- | --- | --- |
| 孤兒 jest 行程佔住連線 | 全部清掉後重跑 | ❌ 還是失敗 |
| **資料庫本身有問題** | `scripts/probe-db.js` 跑 70 圈 | ✅ **70/70 成功** |
| 閒置連線被切斷 | `scripts/probe-conn.js`，閒置 10 / 30 / 60 秒 | ✅ 全部正常 |
| Neon 冷啟動 | 探針跑完立刻跑測試（compute 是熱的）| ❌ 還是失敗 |
| 埠耗盡 / TIME_WAIT | `Get-NetTCPConnection` | ❌ TIME_WAIT 只有 20，埠有 14000 個 |
| supertest 每個請求開新 server | `app.listen(0)` 重用同一個 server | ❌ 還是紅 |
| Jest 的 5 秒逾時不夠 | `testTimeout` 改成 30000 | ❌ 還是紅（當時） |
| **supertest 每個請求開新 TCP 連線** | 換成 keep-alive 的 Agent | ✅ **ECONNRESET 歸零**（2026-08-22 補測） |

Ch5 當時的結論是「不是程式碼、也不是資料庫，是這台機器 HTTP socket 層的環境問題」——
**方向對，但停得太早**。最後那一行是 2026-08-22 補上的，它才是答案。

兩個值得帶走的判準：

1. **「重用同一個 server」和「重用同一條連線」是兩件事。** 上面第六行試的是前者，
   最後一行試的是後者 —— 前者省的是 listen，後者省的是 TCP 握手與關閉。差別就是全部的差別。
2. **`testTimeout` 那一行標「當時」是有意義的。** 它在 ECONNRESET 還在的時候確實沒用
   （因為根本沒打通 HTTP），但 ECONNRESET 修好之後，剩下唯一的偶發失敗**確實是逾時**
   （併發那條測試要 6-8 次 Neon 往返 ≈ 3-4 秒，貼著預設的 5 秒），改成 30000 就穩了。
   **同一個旋鈕在不同的根因下，結論會完全相反。**

### 順帶的參考值

`probe-db.js` 跑 70 圈約 45 秒，等於**每次往返 Neon（新加坡）約 500ms**。

**e2e 的時間 ≈ 資料庫往返次數 × 500ms**，跟程式效率幾乎無關。
所以測試變慢通常代表「多了幾次查詢」，不是「程式變慢了」——
想確認就開 `PRISMA_LOG_QUERIES=1` 數 SQL。

### 連線池的大小

`PrismaService` 的連線池上限由 `DATABASE_POOL_MAX` 決定（沒設就用 `pg` 的預設 10）。
`.env.test` 設成 **1** —— e2e 是單執行緒（`maxWorkers: 1`），一條連線就夠，
開 10 條純粹是讓 socket 變多。

**這不是 `ECONNRESET` 的解法**（上面的排除表已經證明修不了），
單純是「不要開用不到的連線」。

#### 連線其實有三段，不是兩段（Ch8 量出來的）

連線字串的 host 帶 `-pooler` 時，中間隔著一層 **PgBouncer**：

```text
你的應用 (pg pool)  →  PgBouncer  →  Postgres
        ↑                        ↑
   DATABASE_POOL_MAX       max_connections
   管這一段（預設 10）      管這一段（這台 compute 是 901）
```

**兩個數字管的是不同的兩段**，中間那層會重用連線，所以請求數和後端連線數不是一對一。
實測：對線上服務持續打 **12 條並發**請求時，`pg_stat_activity` 只看到 **7 條**，
而且 `application_name` 是 **`pgbouncer`** —— 也就是說，
**你在 `pg_stat_activity` 看到的不是你的應用開的連線，是 PgBouncer 對 Postgres 開的連線。**
應用端到 PgBouncer 那一段從這裡看不到。

查法（Neon Console → SQL Editor，branch 選對）：

```sql
SHOW max_connections;

SELECT application_name, state, count(*)
FROM pg_stat_activity
WHERE datname = current_database()
GROUP BY application_name, state;
```

> 查之前要先確認 compute 是 `Active`。Neon 免費方案閒置會 autosuspend，
> 而且 `pg` 的連線池閒置 10 秒就自己關連線 —— 兩件事都會讓你數到 0，
> 那不代表「沒有連線洩漏」，只代表當下沒人在用。**要量就要一邊持續打負載一邊查。**

**正式環境維持不設 `DATABASE_POOL_MAX`。** 免費方案只有一個實例、上限 10 條，
離 901 遠得看不到，沒有觀測到瓶頸就不要調數字。
會變成問題的是「多實例 × 每實例 10 條」，那是自動擴展之後的事。

## 換機接續（筆電 ↔ 桌電）

這個專案在兩台機器上輪流開發，所以要清楚哪些東西跟著 git 走、哪些不會。

**跟著 git 走的：** 程式碼、`LEARNING.md`、`docs/`、`CLAUDE.md`、`.agents/skills/`。

**不會跟的：**

| 類別 | 內容 |
| --- | --- |
| AI 工具的本機狀態 | 對話歷史、記憶、全域設定（都在 `~/.claude/`，且以絕對路徑當專案識別碼） |
| 有 gitignore 的機密／產物 | `.env`、`.env.test`、`src/generated/` |
| 含絕對路徑的連結 | `.claude/skills/*`、`.windsurf/skills/*` 的 junction |

**因此有一條原則：`LEARNING.md` 與 `docs/` 是唯一的跨機進度來源。** 一章的決策與踩坑如果只存在於對話裡，換一台機器就等於沒發生過。這也是為什麼每章結束要把 `docs/chapters/chNN-*.md` 補完、並更新 `LEARNING.md` 的進度表再 commit —— 它們不是心得感想，是接續工作的依據。

換機開工的步驟：

```bash
git pull
pnpm install
pnpm exec prisma generate   # src/generated 沒進版控，不跑就沒有型別
```

再照 `.env.example` 建立 `.env`（`DATABASE_URL` 從 Neon Console 的 Connection Details 複製）。

**Ch8 之後 Neon 上有三條 branch，複製前先看清楚選的是哪一條：**

| branch | 誰在用 | 會不會被清空 |
| --- | --- | --- |
| `production` | 線上服務（填在 Render 的環境變數裡，本機不需要） | 不會 |
| `dev` | **本機開發 —— `.env` 要指的是這條** | 不會，可以隨便玩 |
| `test` | E2E 測試（`.env.test`） | 每個測試案例前 `TRUNCATE` 五張表 |

三條的 host 前綴互不相同（例如 `ep-some-name` / `ep-other-name` / `ep-third-name`），
**貼完回頭比對一次 host** 就是最便宜的防呆。

> **Neon 的預設 branch 就叫 `production`，但名字不代表用途。** 這個專案原本拿它當開發庫用了七章，
> Ch8 才把它清空改成真正的正式環境、另開 `dev` 給本機。**要看 host，不要看名字。**

> **`.env` 從 Ch3 起有第二個 key：`PRISMA_LOG_QUERIES`。** 留空就好 ——
> 它預設關，只有想看 Prisma 實際送出的 SQL 時才改成 `1`。
> 少了它不會壞（程式用 `config.get`、不是 `getOrThrow`），所以換機時漏掉不會有任何症狀。

> **`prisma generate` 那一行漏掉會長這樣**（2026-08-09 實際踩過）：ESLint 報
> `Unsafe call of a type that could not be resolved`，紅線畫在你自己寫的程式碼上，
> 看起來像是程式寫錯了。真正的訊息要跑 `pnpm exec tsc --noEmit` 才看得到 ——
> `PrismaClient<never, ...>`，那個 `never` 代表 client 認識的 model 集合是空的。
> **Prisma 7 的 `pnpm install` 不會自動 generate**，所以換機後這一步沒有任何東西會幫你補。
> 完整診斷過程見 [`ch01` 的「Prisma Client 沒跟上 schema」](chapters/ch01-schema設計與第一次migration.md)。

### `.env.test` 也要重建（Ch2 之後）

E2E 測試連的是**另一個**資料庫，設定在 `.env.test`，同樣不進版控。少了它，`pnpm test:e2e`
會被 `test/setup-env.ts` 的防呆直接擋下並印出步驟 —— **那是預期行為，不是壞掉。**
（這個防呆存在的理由就是這一刻：沒有它，測試會安靜地跑在開發資料庫上並把資料 `TRUNCATE` 掉。）

```powershell
# 1. Neon Console → Branches → New branch → 命名 test，複製它的連線字串
# 2. 在專案根目錄建立 .env.test，只需要一個變數：
#      DATABASE_URL="<test branch 的連線字串>"
# 3. 新 branch 是空的，要先建表：
$env:DATABASE_URL="<test branch 的連線字串>"
pnpm exec prisma migrate deploy
```

第 3 步用 `migrate deploy` 而不是 `migrate dev`：前者只照著 `prisma/migrations/` 重播、
不會產生新的 migration。**這就是「migrations 必須進版控」的實際兌現** ——
一份全新的空資料庫靠那個資料夾就能重建出相同結構。

`$env:` 只影響當下那個終端機視窗，關掉就沒了，不會弄髒 `.env`。

> 如果複製 `.env` 過來只改檔名，第二道防呆會擋下並告訴你「兩個 `DATABASE_URL` 相同」。

> 如果是**專案目錄改名**而非全新 clone，`node_modules` 裡 pnpm 的連結同樣存絕對路徑、同樣會全斷（症狀：`Cannot find module '.../node_modules/prisma/build/index.js'`）。此時 `pnpm install` 會跳出互動式確認，直接用 `pnpm install --force` 重裝。

> **不要用 `npm` 裝這個專案的依賴。** 兩個套件管理器的 `node_modules` 結構不相容，混用之後 `pnpm install` 會把 npm 裝的東西全部搬到 `node_modules/.ignored`，還會多出一個不該存在的 `package-lock.json`。若 `git status` 出現 `package-lock.json`，就是踩到了：刪掉它、`git checkout -- package.json`、重跑 `pnpm install`。

> **pnpm 主版本變了 → `node_modules` 要整個重建。** 症狀非常好認：**所有** `pnpm` 指令都失敗，連 `pnpm --version` 都回 `ERROR packages field missing or empty`。
>
> 這代表執行到的是舊版 pnpm。`pnpm-workspace.yaml` 是照 pnpm 11 的規格寫的 —— pnpm 11 允許省略 `packages` 欄位，pnpm 9 卻視為必填；而且 `allowBuilds` 是 pnpm 11.0 才有的欄位（取代舊的 `onlyBuiltDependencies` / `neverBuiltDependencies`），舊版根本不認得。**檔案沒有寫錯，是機器上跑到了不該跑的那份 pnpm。**
>
> Windows 上 `pnpm` 可能來自 Yarn 全域 bin、Node 安裝目錄、或 corepack —— **pnpm 行為詭異時第一件事是確認執行到哪一份**，而不是先懷疑專案設定：
>
> ```powershell
> (Get-Command pnpm).Source   # 實際執行的是哪一個檔案
> pnpm --version              # 它是幾版
> ```
>
> 解法三步：**移除舊版 pnpm**（讓新版接手）→ **`pnpm install`**（會問要不要移除 `node_modules`，因為舊版裝的結構不相容，**回答 Y**；非互動環境會以 `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY` 中止）→ **`pnpm exec prisma generate`**（引擎二進位檔在 `node_modules` 裡，被刪過就要重產 client）。
>
> **不要為了消掉錯誤訊息去補 `packages:` 欄位。** 訊息會消失，但 `allowBuilds` 在舊版仍然無效、Prisma 引擎不會下載，只是把症狀換成更難診斷的形式，而且會跟另一台機器分岔。
>
> 一句話原則：**`node_modules` 綁在裝它的那個 pnpm 版本上。**

> **`pnpm` 完全找不到（`command not found`）→ 先看 `node -v`。**
>
> 這跟上面那則是**不同的根因**，但症狀很像，所以判準要分清楚：
>
> | 症狀 | 根因 |
> | --- | --- |
> | `pnpm --version` 回 `ERR_PNPM_ABORTED...` 之類的錯誤 | pnpm 主版本不符（見上面那則） |
> | **`pnpm` 這個指令根本不存在** | **多半是 nvm 切走了 Node 版本** |
>
> 這台機器的 `pnpm` 是 **corepack 提供的**，而 **corepack 從 Node 16.9 才內建** ——
> 所以 `nvm use 14`（或任何 16.9 以前的版本）之後，`corepack` 和 `pnpm` 會**一起消失**。
> Ch9 收尾時實際發生過一次：驗收跑到一半 `pnpm: command not found`，
> 而幾分鐘前它明明還在。
>
> ```powershell
> node -v                                   # 先看這個
> (Get-Item "C:\Program Files
odejs" -Force).Target   # nvm 的 symlink 指到哪
> ```
>
> **切回去要用系統管理員身分**：`nvm use 24.11.0`。
> **nvm-windows 在沒有權限時會印「Now using node v24.11.0」然後靜靜地失敗** ——
> 別相信那句話，回頭再看一次 `node -v`。
>
> 急著跑驗收又不想切版本的話，可以繞過 pnpm 直接用那個版本的 node 跑本地工具：
> `& "$env:APPDATA
vm24.11.0
ode.exe" node_modules/jest/bin/jest.js ...`
> —— `pnpm` 只是外殼，真正執行的是 `node_modules` 裡的東西。

`pnpm-workspace.yaml` 的 `allowBuilds` 是**必要設定，不是可選的**。pnpm 10 之後預設不執行依賴的安裝腳本，而 Prisma 需要靠它下載查詢引擎。沒有這個檔案的話，pnpm 會產生一份待填的骨架，並且在填完之前**連 `pnpm exec` 都會失敗**（它會先跑一次 install 檢查）。所以這個檔案要進版控。

最後重建 skills 的 junction。**junction 存的是絕對路徑，換機或專案目錄改名一定會斷**（曾因 `survey-api` 更名為 `survey-backend` 而全斷，見 commit `1b83a4d`）。在專案根目錄跑這段 PowerShell，不需要系統管理員權限：

```powershell
$root = $PWD
foreach ($mirror in @('.claude','.windsurf')) {
  # 全新 clone 時 .claude\ 與 .windsurf\ 整個目錄都不存在（只有 skills/ 被 gitignore，
  # 但這兩個目錄裡也沒有其他進版控的檔案）。New-Item -ItemType Junction 不會自動建父層，
  # 少了這行會噴 Could not find a part of the path。
  New-Item -ItemType Directory -Force -Path "$root\$mirror\skills" | Out-Null
  foreach ($s in Get-ChildItem "$root\.agents\skills" -Directory) {
    $link = Join-Path "$root\$mirror\skills" $s.Name
    if (Test-Path $link) { (Get-Item $link).Delete() }
    New-Item -ItemType Junction -Path $link -Target $s.FullName | Out-Null
  }
}
```

驗證：`Test-Path .claude\skills\prisma-cli\SKILL.md` 應為 `True`。

### 最後：跑四項驗收確認環境真的可用

```powershell
pnpm test                # 6 passed（單元測試，約 3 秒、不連資料庫）
pnpm test:e2e            # 95 passed（會連 .env.test 的 Neon test branch，約 80 秒）
pnpm exec tsc --noEmit   # 0 errors
pnpm lint                # 0 problems
```

**數字對不上就是環境還沒好，先別開始寫程式。** 常見對應：

| 症狀 | 多半是 |
| --- | --- |
| `pnpm test:e2e` 被防呆擋下並印出步驟 | `.env.test` 沒建（預期行為，照上面那節做） |
| ESLint 紅線畫在自己寫的程式碼上 | 忘了 `pnpm exec prisma generate` |
| 所有 `pnpm` 指令都失敗 | pnpm 版本問題，見上面那則 |
| e2e 偶發外鍵錯誤，重跑就好 | 有兩個行程同時連 test 資料庫（例如另一個視窗還在跑 `pnpm test:e2e`）。`maxWorkers: 1` 只隔離**同一個 Jest 行程內**的測試檔，管不到另一個行程 |

## 部署與正式環境（Ch8）

後端跑在 **Render**（免費方案），資料庫是 **Neon 的 `production` branch**。
網址：`https://survey-backend-0dku.onrender.com`

### Render 上的設定值

| 欄位 | 值 |
| --- | --- |
| Region | Singapore（跟 Neon 的 `ap-southeast-1` 同區） |
| Branch | `main` |
| Build Command | `pnpm install && pnpm build && pnpm exec prisma migrate deploy` |
| Start Command | `pnpm start:prod` |
| Instance Type | Free |
| 環境變數 | 只有 `DATABASE_URL`（`production` branch 那條） |
| Health Check Path | **刻意不設**，理由見下面 |

**`PORT` 不要設。** Render 會自己注入，`main.ts` 用 `process.env.PORT ?? 3000` 接；
自己設反而會蓋掉平台給的值。

**Build Command 三段的順序有意義**：`migrate deploy` 放最後，是為了讓
「build 失敗時資料庫還沒被改」。反過來的話，新 schema 已經套用、新程式卻沒上線，
線上跑的是舊程式配新結構。

**`migrate deploy` 每次部署都會跑**，包括你只改了一行程式碼、完全沒動 schema 的那些次。
這樣做是安全的，因為它是冪等的：沒有待套用的 migration 時它只印
`No pending migrations to apply.`，什麼都不做。

### 怎麼觸發重新部署

`git push` 到 `main` 就會自動重新 build + 重啟。
**Render 讀的是 GitHub 上的程式碼，不是你本機的** —— 本機再綠，沒 push 就不算數。

### 免費方案的兩個限制

| 平台 | 限制 | 超過會怎樣 |
| --- | --- | --- |
| Render Free | 一段時間沒有請求就休眠，下次要冷啟動 | 第一個請求變慢（**這次沒量到實際秒數**，量的時候服務剛好還醒著） |
| Neon Free | 0.5 GB 儲存、100 CU-hours／月、10 條 branch | **服務暫停，不是寄帳單**（兩邊都沒綁卡）。儲存滿了連 `DELETE` 都會失敗 |

**Health Check Path 刻意不設**，就是因為第二列：`/health` 會做一次真的資料庫查詢，
而健康檢查是定期輪詢的 → Neon 的 compute 永遠不會 autosuspend。
最小的 0.25 CU 連續跑一個月是 `0.25 × 730 ≈ 182` CU-hours，**額度撐不到月底**。

### `/docs` 在正式環境是公開的

這是刻意的決定，不是漏掉。理由與取捨寫在
[`ch08`](chapters/ch08-第一次部署.md) 的「決策取捨」——
一句話版本：**這個 API 目前完全沒有認證，關掉 `/docs` 只是把門牌拿掉、門還是開的。**
真正的修法是 Ch9 ~ Ch12。在那之前**不要把網址貼到公開的地方**。

## `api.http` 怎麼用

手動打 API 用的檔案（`GET /health` 到 `DELETE /surveys/:id` 都在裡面）。
它跟 e2e 的分工：**e2e 回答「有沒有壞」，`api.http` 回答「我想看看它實際回什麼」** ——
例如打開 `PRISMA_LOG_QUERIES` 之後想看某一支端點跑幾句 SQL。

### 第一次使用

1. **裝擴充套件**（只需一次）：VS Code 的 Extensions（`Ctrl+Shift+X`）→ 搜 `REST Client`
   → 作者 **Huachao Mao** → Install。裝好之後每個請求上方會出現可點的灰字 `Send Request`；
   **看不到那行字就是還沒裝成功**（或右下角語言模式不是 HTTP）。
2. **另開一個終端機跑 `pnpm start:dev`**，等到 `Nest application successfully started`。
   這個檔案打的是 `http://localhost:3100`（`@host` 變數，第 10 行），伺服器沒跑就
   `ECONNREFUSED`。
3. 回到 `api.http`，點請求上方的 `Send Request`（快捷鍵 `Ctrl+Alt+R`），
   回應會開在右邊的分割視窗。

### 四種語法

| 寫法 | 意思 |
| --- | --- |
| `###` | **「上一個請求到此結束」的分隔線**，順便當註解用。不是純註解 |
| `@host = ...` / `{{host}}` | 定義變數 / 使用變數 |
| header 與 body 之間的**空行** | HTTP 協定本身的規定，少了它 body 會被當成 header |
| `# @name createSurvey` | 幫請求命名，之後可用 `{{createSurvey.response.body.id}}` 取它的回應欄位 |

**`###` 是最容易踩的一個。** 變數定義如果緊接在 body 後面而中間沒有 `###`，
它會被當成 JSON body 的一部分送出去，回 `400 Unexpected non-whitespace character after JSON`。
（實際踩過，見 `ch03` 第二段的坑。）

### 順序很重要

後面的請求靠 `{{surveyId}}` / `{{questionId}}` 取前面的回應，所以要**由上往下依序送**：
先 `POST /surveys` 建問卷，`{{surveyId}}` 才有值。沒送過時 VS Code 會提示
`Request 'createSurvey' has not been sent` —— 那是正常的，送過就消失。

### 兩個提醒

- **它打的是開發資料庫**（`.env` 的 `DATABASE_URL`），不是測試資料庫。
  這裡建的資料會真的留著，用 `pnpm exec prisma studio` 看得到。
  玩完送最後一個 `DELETE /surveys/{{surveyId}}` 就會連題目一起消失（cascade）。
- **改了 port 只要改 `@host` 一行**（本機是 3100，因為 3000 被 Nuxt 佔用）。
