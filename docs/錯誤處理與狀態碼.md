# 錯誤處理與狀態碼

**這份文件回答一件事：一個錯誤從資料庫走到前端，中間經過哪些層、每一層說什麼語言。**

跨章節的參考資料，隨專案演進更新。Ch6 的決策與踩到的坑在
[`chapters/ch06-統一錯誤處理與回應格式.md`](chapters/ch06-統一錯誤處理與回應格式.md)，
這裡只放**每一章都會回來查的東西**：

- 401 / 403 要到 **Ch10–Ch12** 才用得到
- Ch7 已照著第 2 節把每支端點的回應碼標進 Swagger（`@ApiNotFoundResponse` 等）。
  **`code` 的合法值現在活在兩個地方**：filter 裡的四個常數，與
  `src/common/entities/error-response.entity.ts` 的 `enum` 清單。
  `test/swagger.e2e-spec.ts` 只比對**欄位名**（`code` / `message` / `details`），
  **不會**發現 `enum` 少列了一個值 —— 那一半仍然靠人。新增錯誤碼時兩邊都要改。
- Ch13 前端串接時要照著第 4 節做錯誤處理

## 一句話的心智模型

**同一個錯誤，在不同層有不同的名字，而翻譯只發生在一個地方。**

```text
PostgreSQL      "duplicate key value violates unique constraint ..."
                        ↓
Prisma          code: 'P2002'          ← Prisma 自己的編號
                        ↓
【  filter  】  ←←←←← 翻譯就發生在這裡，全專案只有這一個地方
                        ↓
HTTP            409 + { error: { code: 'CONFLICT', message: '資料已存在' } }
                        ↓
前端            看到 409 → 顯示「這個名稱已經有人用了」
```

兩套碼**服務不同的讀者**：

- **Prisma 錯誤碼**說「**資料庫發生了什麼**」。讀者是後端工程師。
- **HTTP 狀態碼**說「**前端接下來該怎麼辦**」。讀者是前端。

前端不知道什麼是 `P2025`，也不該知道。這就是為什麼對照表的判準是
**「前端拿到之後能做什麼」**，而不是「這個錯誤有多嚴重」。

## 1. 例外的完整路徑

### 為什麼 controller 不用寫 try/catch

`surveys.service.ts` 裡有這一行：

```ts
if (!survey) throw new NotFoundException('問卷不存在');
```

而 `surveys.controller.ts` 裡**一個 try/catch 都沒有**。那個 `throw` 之後發生了什麼：

```text
你的 service      throw new NotFoundException('問卷不存在')
                      ↓  往上冒（沒人接）
你的 controller       ← 這裡沒有 try/catch，繼續往上冒
                      ↓
Nest 的 router        ← 它把每一次 controller 呼叫都包在自己的 try/catch 裡
                      ↓  接住了，交給 ExceptionsHandler
Nest 找 filter        ← 誰註冊了 filter？→ AllExceptionsFilter.catch()
                      ↓
你的 filter           算出 status / code / message → res.status(404).json({ ... })
                      ↓
前端                  404 + { error: { code: 'NOT_FOUND', message: '問卷不存在' } }
```

**核心答案：你不用寫 try/catch，是因為 Nest 已經幫你包了一層。**
你的 `throw` 一定會被接住，接住之後一定會走到 filter。

這也是為什麼 service 可以放心「丟了就不管」——
它不需要知道自己被誰呼叫、也不需要知道回應長什麼樣。

### 三件順帶要記住的事

1. **正常回應完全不經過 filter。** 沒有例外 → `catch()` 一次都不會被呼叫。
   `errors.e2e-spec.ts` 的「成功的回應完全不受影響」那條測試就是把這個邊界寫成斷言。
2. **不管例外從哪一層冒出來都一樣**：ValidationPipe（驗證失敗）、controller、service、
   Prisma、甚至一個 `undefined.foo` 的 `TypeError` —— 全部走同一個出口。
3. **`useGlobalFilters` 是「註冊」那一步。** 少了它，Nest 會用內建的 filter、回舊格式。
   所以測試裡建完 app 一定要呼叫 `setupApp(app)`（`errors.e2e-spec.ts` 兩個
   `describe` 各有一次，缺一個就整組回舊格式）。

> **filter 是錯誤處理，不是防線。**
> 沒有例外被丟出來的時候它什麼都不知道 —— 詳見 `ch06` 的「filter 只看得到被丟出來的東西」。

## 2. HTTP 狀態碼（`HttpStatus`）

### 它只是一張數字的名字表

`HttpStatus.NOT_FOUND` 求值之後就是 `404`，直接寫 `404` 完全一樣、沒有任何差別。
用它只是為了讓「這個數字是什麼意思」寫在程式碼裡。

Nest 的 `HttpStatus` 有 60 幾個值（100~508，包含 `I_AM_A_TEAPOT = 418` 這種愚人節產物）。
**後端實際會用到的只有這九個：**

| 值 | 名字 | 什麼時候用 | 這個專案用在哪 |
| :---: | --- | --- | --- |
| 200 | `OK` | 成功 | 預設 |
| 201 | `CREATED` | 建立成功 | `POST /surveys` |
| 204 | `NO_CONTENT` | 成功但沒有東西要回 | 還沒用到 |
| **400** | `BAD_REQUEST` | **請求內容本身有錯** | 驗證失敗、重複的題目 ID |
| 401 | `UNAUTHORIZED` | 沒登入 | **Ch10** |
| 403 | `FORBIDDEN` | 登入了但沒權限 | **Ch11 / Ch12** |
| **404** | `NOT_FOUND` | **東西不存在** | `findOne` 查不到 |
| **409** | `CONFLICT` | **請求合法，但跟現在的狀態衝突** | 未發布不能填答、有人填答就不能撤回 |
| **500** | `INTERNAL_SERVER_ERROR` | **伺服器自己壞了** | 沒人預期的例外 |

粗體那四個是目前用得到的。401 / 403 現在還沒有，因為還沒有登入系統。

### 400 / 404 / 409 的判準

這三個最常混淆，判準是**「錯在哪裡」**：

| | 意思 | 換個時間點重送會成功嗎 |
| :---: | --- | --- |
| **400** | 你送來的東西**本身**就不對 —— 少欄位、型別錯、id 重複。<br>看請求就知道錯了，不必查資料庫 | **不會**。除非你改請求內容 |
| **404** | 請求沒問題，但**你要的那個東西不在** | 那個東西被建出來就會 |
| **409** | 請求沒問題、東西**也在**，但它**現在的狀態**不允許你做這件事 | **會**。問卷發布之後同一個請求就成功了 |

「問卷是 `DRAFT`，不能填答」是 409 的標準形狀：請求完全合法，只是**現在**不行。

### 401 和 403 的差別（Ch10 會用到，先記著）

- **401 = 我不知道你是誰**（沒帶 token、token 過期）→ 前端該做的是**導去登入頁**
- **403 = 我知道你是誰，但你不能做這件事**（一般使用者想刪別人的問卷）→ 前端該顯示**「權限不足」**

判準一樣是「前端拿到之後能做什麼」—— 兩者要前端做的事完全不同，所以不能混用。

## 3. Prisma 錯誤碼

### 錯誤物件長什麼樣

Prisma 執行查詢失敗時丟出來的東西：

```ts
PrismaClientKnownRequestError {
  code: 'P2002',                                              // ← 錯誤碼
  message: 'Unique constraint failed on the fields: (`title`)',
  meta: { target: ['title'] },                                // ← 細節：哪個欄位撞了
  clientVersion: '7.x.x',
}
```

`code` 是 **Prisma 自己定義的一套編號**，跟 HTTP 一點關係都沒有。

### 編號分區

| 區段 | 管什麼 | 例子 |
| --- | --- | --- |
| `P1xxx` | **連線**問題 | `P1001` 連不到資料庫、`P1002` 連線逾時、`P1017` 連線被關掉 |
| `P2xxx` | **查詢**問題（後端最常遇到的） | `P2002` 唯一約束、`P2003` 外鍵約束、`P2025` 找不到要操作的記錄 |
| `P3xxx` | **migration** 問題 | 跑 `prisma migrate` 才會遇到 |
| `P4xxx` / `P5xxx` | introspection / Accelerate | 這個專案用不到 |

完整清單在 Prisma 官方文件的 **Error Reference**。
但實際會反覆遇到的就是 `P2002` / `P2003` / `P2025` 這三個 —— 所以 filter 的表裡就這三個。

### 陷阱：不是每個 Prisma 錯誤都有 `code`

Prisma 丟的錯誤不只一種 class：

| class | 有 `code` 嗎 | 什麼時候丟 |
| --- | :---: | --- |
| `PrismaClientKnownRequestError` | **有** | 查詢送到資料庫、被資料庫拒絕（上面那些 `P####`） |
| `PrismaClientValidationError` | **沒有** | **你傳給 Prisma 的參數形狀不對**，根本沒送到資料庫 |
| `PrismaClientUnknownRequestError` | 沒有 | 引擎層的未知錯誤 |

**第二個你已經遇過了。** Ch4 那個「`GET /surveys` 每一次都 500」的 bug ——
DTO 三處一致地把 `createdAt` 寫成 `createAt`，於是 `orderBy: { createAt: 'asc' }`。
丟出來的就是 `PrismaClientValidationError`。

它**沒有 `code`**，所以 filter 的安全網不會翻譯它，它會掉進 500 分支。
**而那是正確的**：欄位名寫錯是你的程式碼有 bug，不是使用者送錯東西 —— 500 才是誠實的答案。

> **判準：`P####` 是「資料庫拒絕了這個查詢」，沒有 `code` 通常是「這個查詢根本不合法」。**
> 前者可能是使用者造成的（該翻譯），後者一定是你造成的（該 500 並留下堆疊）。

## 4. 訊息為什麼不能直接轉發

`exception.message` 拿來當回應的 `message`，測試會**全綠**、狀態碼**完全正確**、
body 形狀**一字不差**。但那句話長這樣：

```text
Foreign key constraint violated on the constraint: `Question_surveyId_fkey`
```

裡面有你的**表名**和**約束名**。對後端有用，對前端沒用，對攻擊者**很有用** ——
它等於免費送出一張資料庫地圖。

**對策不是「記得不要放 `exception.message`」**（人一定會忘），
是讓那條路徑上**根本沒有變數可以放**：filter 裡 500 的訊息是寫死的常數
`FALLBACK_MESSAGE`，Prisma 錯誤的三句訊息也是自己寫的中文。

> 這是這個專案反覆出現的一種對策形狀：**與其靠紀律，不如讓錯誤在結構上不可能發生。**
> 同一個形狀的第二次現場是 filter 裡的 `code = STATUS_TO_CODE[status]` ——
> 不自己寫 `'NOT_FOUND'`，就不可能跟別處不一致。

## 5. 這個專案現在的對照表

`src/common/filters/all-exceptions.filter.ts` 的 `PRISMA_ERRORS`：

| Prisma code | → HTTP | → `error.code` | 為什麼 |
| :---: | :---: | --- | --- |
| `P2025` | 404 | `NOT_FOUND` | 「那筆資料不在了」＝前端可以顯示「查無此項目」 |
| `P2002` | 409 | `CONFLICT` | 唯一約束衝突＝請求合法但跟現況衝突 |
| `P2003` | 400 | `BAD_REQUEST` | 外鍵指向不存在的東西＝**請求內容本身有錯** |
| 其他 `P####` | 500 | `INTERNAL_ERROR` | 認不得就不翻譯，走 500 分支並留下完整堆疊 |
| 沒有 `code` 的 | 500 | `INTERNAL_ERROR` | 同上（`PrismaClientValidationError` 走這裡） |

`P2003` 選 400 而不是 404，是為了跟 `responses.service.ts` 已經做過的判斷保持一致
（那裡對「題目不屬於這份問卷」也是回 400，理由是那些題目**確實存在**）。
**同一種錯誤走兩條路卻回兩種狀態碼**，前端只會覺得這支 API 反覆無常。

### 這張表是安全網，不是主要防線

service 該擋的還是自己擋（`assertExists` 先查一次、`canSubmitResponse` 先判斷）。
這張表只負責「萬一漏上來，別回一個誤導前端的 500」。

所以翻譯成功時 filter 還是會寫一筆 `logger.warn` ——
**安全網每被觸發一次，都代表有一條路徑漏掉了 service 那一層的檢查。**

## 附：HTTP 狀態碼的三位數規律

第一位決定大類，記這個比記個別數字有用：

| 開頭 | 意思 | 誰的問題 |
| :---: | --- | --- |
| `2xx` | 成功 | — |
| `3xx` | 重新導向（「東西搬到別的網址了」） | — |
| **`4xx`** | **請求有問題** | **客戶端**（前端 / 呼叫方） |
| **`5xx`** | **伺服器有問題** | **後端（你）** |

**4xx 和 5xx 的分界就是「這是誰的錯」。** 所以把一個「使用者送錯東西」回成 500 是在說謊
（明明是對方的錯），而把一個「我的程式碼寫錯了」回成 400 也是在說謊（甩鍋給前端）。

這也是 Ch6 這一章存在的理由：**沒有 filter 的話，Prisma 的錯誤一律變成 500** ——
每一個「查無此項目」都在對前端說「伺服器壞了」。
