# 設定檔導讀

`package.json`、`test/jest-e2e.json` 與 `.vscode/settings.json` 是純 JSON，**加註解會讓檔案壞掉**（JSON 規格不允許 `//`），所以它們的說明寫在這裡。

其餘設定檔的說明直接寫在檔案裡：`tsconfig.json`、`prisma.config.ts`、`prisma/schema.prisma`。

---

## `package.json` → `scripts`

這一區是「指令的縮寫表」。`pnpm start:dev` 實際執行的是這裡對應的那串字。

| 指令 | 實際做什麼 | 什麼時候用 |
| --- | --- | --- |
| `pnpm start:dev` | `nest start --watch` —— 啟動服務，改檔案自動重啟 | 開發時開一個終端機掛著 |
| `pnpm build` | `nest build` —— 把 TypeScript 編譯成 JavaScript 放到 `dist/` | 部署前，或想確認沒有型別錯誤 |
| `pnpm start:prod` | `node dist/main` —— 直接跑編譯後的產物 | 正式環境。要先 `build` 過 |
| `pnpm lint` | ESLint 檢查並自動修正 | 提交前 |
| `pnpm format` | Prettier 排版 | 提交前 |
| `pnpm test` | 單元測試（只掃 `src/` 底下的 `*.spec.ts`） | 這個專案很少用，見下方說明 |
| `pnpm test:e2e` | E2E 測試（掃 `test/*.e2e-spec.ts`，連真實資料庫） | 每章驗收 |

**為什麼 `test` 幾乎用不到？** 這個專案的策略是 E2E 優先。後端大多數程式碼只是「HTTP 請求 → Prisma → 資料庫」的轉發，把 Prisma mock 掉之後測的其實是 mock 本身。單元測試只寫在有真正判斷邏輯的地方（`Survey.status` 那兩條規則）。

### 測試指令為什麼長這麼奇怪

```json
"test": "node --experimental-vm-modules node_modules/jest/bin/jest.js --passWithNoTests"
```

正常應該只要寫 `jest` 就好。之所以要拆成這樣，是因為 Prisma 7 的查詢編譯器用 WASM，載入時會用到動態 `import()`，而 Jest 預設的沙箱環境不支援 —— 必須加上 `--experimental-vm-modules` 這個 Node 旗標，而旗標沒辦法透過 `jest` 指令傳進去，只能直接呼叫 Jest 的進入點。

> **這是 Prisma 7 太新造成的一次性成本，跟學後端無關。** 你只需要記住一件事：**日後新增測試腳本時，要保留這段前綴**，否則測試會以 `A dynamic import callback was invoked without --experimental-vm-modules` 失敗。

`--passWithNoTests` 則是「一個測試都沒有時不算失敗」，因為目前 `src/` 底下確實還沒有單元測試。

## `package.json` → `jest`

單元測試的設定。E2E 有自己的一份（見下一節）。

```json
"rootDir": "src",              // 只在 src/ 底下找測試
"testRegex": ".*\\.spec\\.ts$" // 檔名以 .spec.ts 結尾的才算測試
```

```json
"moduleNameMapper": { "^(\\.{1,2}/.*)\\.js$": "$1" }
```

這行是把 `import ... from '../generated/prisma/client.js'` 裡的 `.js` 拿掉，好讓 Jest 找到真正的 `.ts` 檔。

> 為什麼 import 要寫 `.js`？因為 `tsconfig.json` 用的是 `nodenext` 模組解析，它要求 import 路徑寫「編譯後」的副檔名。Jest 不吃這套，所以要靠這行對應回去。**同樣是 Prisma 7 的相容性處理，現階段可略過。**

```json
"collectCoverageFrom": ["**/*.(t|j)s", "!generated/**"]
```

算測試覆蓋率時排除 Prisma 產生的程式碼 —— 那不是我們寫的，不該算進去。

## `test/jest-e2e.json`

E2E 測試的設定，跟上面那份的差別只有兩處：

| 欄位 | 單元測試 | E2E |
| --- | --- | --- |
| `rootDir` | `src` | `.`（專案根目錄，因為測試檔在 `test/`，但要 import `src/` 的東西） |
| `testRegex` | `.*\.spec\.ts$` | `.e2e-spec.ts$` |

`moduleNameMapper` 兩份都有，原因同上 —— 兩份設定各自獨立，改一份不會影響另一份，**新增設定時記得兩邊都要改**。

## `.vscode/settings.json`

```json
"typescript.tsdk": "node_modules/typescript/lib",
"typescript.enablePromptUseWorkspaceTsdk": true
```

**這兩行是讓編輯器與指令列用同一個 TypeScript。**

VS Code 內建了自己的一份 TypeScript，預設就是拿它來畫紅線、做自動完成。但這個專案刻意把 TypeScript 從 7 降到 5.9（理由見 `docs/chapters/ch00-環境建置.md` 的「為什麼 TypeScript 從 7 降到 5.9」），兩者一旦版本不同、或對 pnpm 的 symlink 解析方式不同，就會出現**「`tsc` 完全沒錯，編輯器卻滿江紅」**的分歧。

典型症狀是測試檔冒出「找不到名稱 `describe`，請安裝 `@types/jest`」—— 但 `@types/jest` 其實裝好好的。

- `typescript.tsdk` 指定改用 `node_modules/` 裡那一份（也就是 `pnpm test` 和 `nest build` 用的那一份）。
- `enablePromptUseWorkspaceTsdk` 讓 VS Code 開啟專案時主動詢問要不要套用 —— 因為前者本身只是「提供選項」，不會自動生效。第一次開啟時要在跳出的通知按 **Allow**，或手動下 `Ctrl+Shift+P` → `TypeScript: Select TypeScript Version` → **Use Workspace Version**。

> **這也是換機接續的一部分。** 這個檔案進版控，所以兩台機器只要各自允許一次即可。

### 判讀原則：紅線不等於壞掉

編輯器的語言伺服器與 `tsc` / Jest 是三套獨立的 TypeScript 實例。真假以指令列為準：

```bash
node node_modules/typescript/lib/tsc.js --noEmit   # 無輸出 = 型別真的沒問題
```

若 `tsc` 是綠的而編輯器是紅的，**要修的是編輯器，不是程式碼**。特別是不要照錯誤訊息的建議去改 `tsconfig.json`：它會叫你加 `types: ["jest"]`，但那個欄位一出現，語意就從「自動載入 `@types/` 底下全部型別」變成「只載入列出的這幾個」，專案裡的 `@types/node`、`@types/express`、`@types/pg`、`@types/supertest` 會集體失效。
