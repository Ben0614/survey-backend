# 設定檔導讀

`package.json`、`test/jest-e2e.json` 與 `.vscode/settings.json` 是純 JSON，**加註解會讓檔案壞掉**（JSON 規格不允許 `//`），所以它們的說明寫在這裡。

其餘設定檔的說明直接寫在檔案裡：`tsconfig.json`、`prisma.config.ts`、`prisma/schema.prisma`。

---

## `package.json` → `scripts`

這一區是「指令的縮寫表」。`pnpm start:dev` 實際執行的是這裡對應的那串字。

| 指令 | 實際做什麼 | 什麼時候用 |
| --- | --- | --- |
| `pnpm start:dev` | `nest start --watch` —— 啟動服務，改檔案自動重啟 | 開發時開一個終端機掛著 |
| `pnpm prebuild` | `prisma generate` —— 依 schema 產生 Prisma Client | **不用自己打** —— pnpm 會在 `build` 之前自動跑（Ch8 加的，理由見下方） |
| `pnpm build` | `nest build` —— 把 TypeScript 編譯成 JavaScript 放到 `dist/`（會先自動跑 `prebuild`） | 部署前，或想確認沒有型別錯誤 |
| `pnpm start:prod` | `node dist/main` —— 直接跑編譯後的產物 | 正式環境。要先 `build` 過 |
| `pnpm lint` | ESLint 檢查並自動修正 | 提交前 |
| `pnpm format` | Prettier 排版 | 提交前 |
| `pnpm test` | 單元測試（只掃 `src/` 底下的 `*.spec.ts`） | 這個專案很少用，見下方說明 |
| `pnpm test:e2e` | E2E 測試（掃 `test/*.e2e-spec.ts`，連真實資料庫） | 每章驗收 |
| `pnpm pretest:e2e` | 清掉殘留的 jest 行程 | **不用自己打** —— pnpm 會在 `test:e2e` 之前自動跑 |
| `pnpm kill:jest` | 同上，手動版 | Ctrl+C 中斷測試後不打算馬上重跑時 |
| `pnpm migrate:test` | 讀 `.env.test` 的 `DATABASE_URL`，對 test branch 跑 `prisma migrate deploy` | **改完 `schema.prisma` 一定要跑**（Ch9 加的，理由見下方） |

**為什麼 `test` 幾乎用不到？** 這個專案的策略是 E2E 優先。後端大多數程式碼只是「HTTP 請求 → Prisma → 資料庫」的轉發，把 Prisma mock 掉之後測的其實是 mock 本身。單元測試只寫在有真正判斷邏輯的地方（`src/surveys/survey.rules.ts` 的四條規則）。

### 測試指令為什麼長這麼奇怪

```json
"test": "node --experimental-vm-modules node_modules/jest/bin/jest.js --passWithNoTests"
```

正常應該只要寫 `jest` 就好。之所以要拆成這樣，是因為 Prisma 7 的查詢編譯器用 WASM，載入時會用到動態 `import()`，而 Jest 預設的沙箱環境不支援 —— 必須加上 `--experimental-vm-modules` 這個 Node 旗標，而旗標沒辦法透過 `jest` 指令傳進去，只能直接呼叫 Jest 的進入點。

> **這是 Prisma 7 太新造成的一次性成本，跟學後端無關。** 你只需要記住一件事：**日後新增測試腳本時，要保留這段前綴**，否則測試會以 `A dynamic import callback was invoked without --experimental-vm-modules` 失敗。

### `test:e2e` 的 `--forceExit`，以及 `pretest:e2e`（2026-08-22 加的）

```json
"pretest:e2e": "node scripts/kill-stale-workers.js",
"test:e2e": "node --experimental-vm-modules node_modules/jest/bin/jest.js --config ./test/jest-e2e.json --forceExit"
```

這兩個東西各自解決**一半**的問題，不要混在一起理解：

| | 症狀 | 原因 | 解法 |
| --- | --- | --- | --- |
| **A** | 測試跑完、summary 都印出來了，但指令不結束 | jest 在等殘留的 handle（沒關乾淨的 socket） | `--forceExit` |
| **B** | 上一輪被中斷後，裡面的 jest 活了下來 | Windows 沒有 process group，殺 `pnpm` 不會連坐子行程 | `pretest:e2e` |

**A 的實測**：加旗標之前是「8 分 20 秒還在卡」，之後是「40 秒自己結束」。

`--forceExit` 的代價要知道：**它會遮蔽真正的資源洩漏**。判準是
**「你知不知道那個 handle 為什麼沒關」** —— 這裡知道（見 `docs/專案速查.md` 的
「e2e 測試連線問題怎麼查」）。`app.close()` 與 `enableShutdownHooks` 照跑，
只是 jest 不再無限等待。

**B 為什麼用 `pre` 而不是 `post`**：`post` 在被中斷時根本不會執行 ——
而「被中斷」正是產生殘留行程的那個情況。`pre` 的保證是「每次開跑都從乾淨狀態開始」。

> **pnpm 會不會執行 `pre` 腳本是實測過的**，不是假設 —— pnpm 有一個
> `enable-pre-post-scripts` 設定，而且它的預設值在不同版本改過。
> 這台機器是 pnpm 11.18.0、沒有 `.npmrc`，實測 `pre` 會執行。
> **若哪天換到會關掉它的版本，`pretest:e2e` 會靜靜地不生效**（不會報錯），
> 症狀就是孤兒行程又開始累積 —— 驗證方式是隨便加一個 `preXXX` 腳本看它印不印。

**已知的取捨**：`kill-stale-workers.js` 用「命令列含 `jest.js`」找目標，
所以它也會殺掉同時在跑的 `pnpm test`（單元測試）。實務上不會撞到
（單元測試 0.5 秒就結束），但知道一下比較好。

---

`--passWithNoTests` 則是「一個測試都沒有時不算失敗」。加它是因為 Ch0～Ch3 前半
`src/` 底下真的一個 `*.spec.ts` 都沒有，`pnpm test` 會直接以錯誤結束。

Ch3 第二段之後已經有 `src/surveys/survey.rules.spec.ts` 了，這個旗標**目前是多餘的** ——
留著是為了避免「哪天把唯一那支 spec 刪掉，指令就紅了」。
專案的測試策略刻意讓單元測試很少（見 `CLAUDE.md`），所以這個情況不是假設性的。

### `prebuild` —— 讓「忘記 generate」在結構上不可能發生（Ch8 加的）

```json
"prebuild": "prisma generate",
"build": "nest build",
```

`prebuild` 是 npm 的生命週期鉤子：跑 `pnpm build` 時它會**自動先執行**，不用自己打。
（同一套規則也產生了上面那個 `pretest:e2e`。）

**為什麼非要它不可**：`/src/generated` 在 `.gitignore` 裡，Prisma Client 是**產物、不進版控**。
部署平台是把 repo `git clone` 一份乾淨的下來，那個資料夾根本不存在 ——
沒有 `prebuild` 的話 `nest build` 會直接以
`TS2307: Cannot find module '../generated/prisma/client'` 掛在**建置階段**，服務連起都沒起來。

而這件事**在本機永遠測不出來**：你的電腦上那個資料夾早就存在，`pnpm build` 怎麼跑都是綠的。
（想看它壞掉的樣子：`rm -rf src/generated` 之後跑 `pnpm build`。
**不要用「改資料夾名字」來模擬** —— VS Code 會把它當成重構，把全專案的 import 一起改掉，Ch8 踩過。）

選 `prebuild` 而不是「記得先跑 `generate`」是刻意的：靠紀律的規則會失效，靠結構的不會。

### `migrate:test` —— 三條 branch 裡只有一條要你動手（Ch9 加的）

```json
"migrate:test": "node scripts/migrate-test.js",
```

改完 `schema.prisma` 之後，三條 Neon branch 的套用方式不一樣：

| branch | 誰套用 |
| --- | --- |
| dev | `prisma migrate dev` 當下就套用了 |
| **test** | **沒有人會幫你做** —— 就是這支腳本 |
| production | `git push` 之後 Render 的 Build Command 會跑 `migrate deploy` |

**忘記補 test 的症狀有誤導性**（Ch9 輪 2 實際踩過）：e2e 突然 500，
訊息是 `The table public.User does not exist` 而且指著你剛寫的 service ——
看起來像程式碼寫錯，其實是那條資料庫沒有那張表。

**為什麼要包成 node 腳本，而不是直接寫成一行指令**：行內設環境變數
（`DATABASE_URL="..." pnpm exec ...`）是 bash 語法，PowerShell 沒有；
而 `package.json` 的 script 在 Windows 上是用 cmd 跑的。包起來之後
`pnpm migrate:test` 在哪個終端機都一樣。腳本裡用的是 `migrate deploy` 而不是
`migrate dev` —— 後者會拿 schema 去跟那個資料庫比對，可能產生新的 migration、甚至 reset 它。

## `package.json` → `packageManager` 與 `engines`（Ch8 加的）

```json
"packageManager": "pnpm@11.17.0",
"engines": { "node": ">=22" },
```

這兩個欄位在本機幾乎沒有作用，它們是**寫給部署平台看的**。

`packageManager` 解決的問題：`pnpm-lock.yaml` 雖然進了版控，但 Render 這類平台**預設用 npm**，
而 npm 讀不懂 `pnpm-lock.yaml` —— 它會**直接忽略**那個檔案，改照 `package.json` 的 `^` 範圍
重新解析一次版本。結果是 build 成功、服務起得來、**但裝的是跟你本機不同的版本組合**，
而且沒有任何地方會告訴你。有了這一行，平台（透過 corepack）才知道要用 pnpm、用哪一版。

`engines` 同理：不寫就跟著平台的預設 Node 版本走，哪天它升版你才會知道。

> **改本機 pnpm 版本時，這一行要跟著改。** 兩者不一致時 corepack 會擋下你本機的 `pnpm` 指令
> ——那是預期行為，不是壞掉。查目前版本：`pnpm -v`。

## `package.json` → `jest`

單元測試的設定。E2E 有自己的一份（見下一節）。

```json
"rootDir": "src",              // 只在 src/ 底下找測試
"testRegex": ".*\\.spec\\.ts$" // 檔名以 .spec.ts 結尾的才算測試
```

```json
"moduleNameMapper": { "^(\\.{1,2}/.*)\\.js$": "$1" }
```

這行是把 import 路徑裡的 `.js` 拿掉，好讓 Jest 找到真正的 `.ts` 檔。

> **誰在寫 `.js`？是 Prisma 產的程式碼，不是你。** `src/generated/` 底下的檔案互相 import 時帶著 `.js`（例如 `client.ts` 裡的 `from "./enums.js"`），因為那份產物要同時能被 ESM 專案使用。Jest 不吃這套，所以要靠這行對應回去。
>
> **你自己寫的 import 一律不帶副檔名**（`.js` / `.ts` 都不寫）—— 這個專案是 CJS（`package.json` 沒有 `"type": "module"`），CJS 解析規則允許省略，這也是 NestJS 的預設寫法。只有 ESM 專案才規定要帶。
>
> **同樣是 Prisma 7 的相容性處理，現階段可略過。**

```json
"collectCoverageFrom": ["**/*.(t|j)s", "!generated/**"]
```

算測試覆蓋率時排除 Prisma 產生的程式碼 —— 那不是我們寫的，不該算進去。

## `test/jest-e2e.json`

E2E 測試的設定，跟上面那份的差別有四處：

| 欄位 | 單元測試 | E2E |
| --- | --- | --- |
| `rootDir` | `src` | `.` |
| `testRegex` | `.*\.spec\.ts$` | `.e2e-spec.ts$` |
| `setupFiles` | 無 | `["<rootDir>/setup-env.ts"]` |
| `maxWorkers` | 無 | `1` |
| `testTimeout` | 無 | `30000` |

**`rootDir` 是相對於「設定檔所在的目錄」解析的，不是專案根目錄。** 這份設定檔在 `test/`，
所以 `"rootDir": "."` 展開後 `<rootDir>` 就是 `test/` —— 這也是為什麼 `setupFiles`
寫的是 `<rootDir>/setup-env.ts` 而不是 `<rootDir>/test/setup-env.ts`（後者會噴
`Module <rootDir>/test/setup-env.ts in the setupFiles option was not found`，
而錯誤訊息會順便印出它認定的 `<rootDir>` 是什麼，卡住時看那一行最快）。

至於測試檔 import `../src/...` 為什麼照樣找得到 —— 那是 Node 的模組解析，
相對於**引用它的那個檔案**，跟 `rootDir` 無關。這兩件事很容易混在一起。

`setupFiles` 指定的檔案在**測試框架載入任何測試檔之前**執行，因此比 `beforeAll` 更早。
`test/setup-env.ts` 靠這個時機差把 `DATABASE_URL` 換成測試資料庫，
趕在 `AppModule` 的 `ConfigModule` 讀 `.env` 之前（詳見該檔案的註解）。

### `maxWorkers: 1` —— 測試檔之間也需要隔離

**Jest 預設把不同的測試檔分配到不同的 worker 並行執行。** 對純運算的單元測試沒問題，
但 E2E 全部連**同一個**測試資料庫，而每個 e2e 檔的 `beforeEach` 都會
`TRUNCATE` 五張表（`test/helpers/reset-db.ts`）—— 於是：

```text
worker A（surveys）建好一份問卷，正要 PATCH 它
worker B（questions）此時跑 beforeEach → TRUNCATE 全部
worker A 回頭找那份問卷 → 不見了 → 404
```

`maxWorkers: 1` 強制所有測試檔**依序**執行。

> **這個坑在 Ch3 才第一次出現**（2026-08-11）。Ch2 結束時只有兩個 e2e 檔，
> 而 `health.e2e-spec.ts` 不寫資料也不 truncate，等於只有一個檔案在動資料庫。
> 新增 `questions.e2e-spec.ts` 之後才有兩個檔案會清空資料庫。
>
> 症狀很好認：**每次跑失敗的組合都不一樣**，而且失敗的往往是「上一章明明會過」的測試。
> 這是併發問題的招牌。

寫在設定檔而不是在指令加 `--runInBand`，是因為常會單獨跑某一個檔案
（`pnpm test:e2e -- test/questions.e2e-spec.ts`）—— 設定寫在這裡，不管怎麼呼叫 jest 都生效。

代價是測試變慢。目前三個檔案 23 個案例約 9 秒，可以接受。
真要並行，得讓每個測試檔用各自的資料庫 schema，那個複雜度對這個專案不划算。

**注意 `.env.test` 隔離的是「測試 vs 開發」，`maxWorkers` 隔離的是「測試 vs 測試」——
兩層是不同的問題，都要處理。**

### `testTimeout: 30000` —— 因為每次資料庫往返要 500ms

Jest 的預設是**每條測試 5 秒**。這對純運算的測試綽綽有餘，但這裡的 e2e 連的是
Neon（新加坡），**每次往返約 500ms**（`docs/專案速查.md` 有實測值）。

最貼線的是 `questions.e2e-spec.ts` 的「同時新增兩題時 order 不會重複」——
它要跑 `survey.create` + 兩個並行 POST（各含 `assertExists` 與 `count` + `create` 交易）
+ 驗證查詢，大約 **6-8 次往返 ≈ 3-4 秒**。偶爾超過 5 秒就紅一次，
而且**每次紅的不一定是同一條**，看起來很像併發 bug。

> **同一個旋鈕在不同的根因下，結論會完全相反。** Ch5 排除表裡
> 「`testTimeout` 改成 30000」那一行寫的是 ❌ 沒用 —— 那是對的，
> 因為當時真正的問題是 ECONNRESET（連 HTTP 都沒打通，改逾時當然沒用）。
> ECONNRESET 修好之後，剩下唯一的偶發失敗**確實是逾時**，這個旋鈕才對症。
>
> 判準：**改設定沒用的時候，先問「我修的是不是真正的原因」，
> 而不是直接把那個方法從清單上劃掉。**

---

`moduleNameMapper` 兩份都有，原因同上 —— 兩份設定各自獨立，改一份不會影響另一份，**新增設定時記得兩邊都要改**。

## `.vscode/settings.json`

```json
"typescript.tsdk": "node_modules/typescript/lib",
"typescript.enablePromptUseWorkspaceTsdk": true
```

**這兩行是讓編輯器與指令列用同一個 TypeScript。**

VS Code 內建了自己的一份 TypeScript，預設就是拿它來畫紅線、做自動完成。但這個專案刻意把 TypeScript 從 7 降到 5.9（理由見 `docs/chapters/ch00-環境建置.md` 的「為什麼 TypeScript 從 7 降到 5.9」），兩者一旦版本不同、或對 pnpm 的 symlink 解析方式不同，就會出現**「`tsc` 完全沒錯，編輯器卻滿江紅」**的分歧。

典型症狀是測試檔冒出「找不到名稱 `describe`，請安裝 `@types/jest`」—— 但 `@types/jest` 其實裝好好的。

- `typescript.tsdk` 指定改用 `node_modules/` 裡那一份（也就是 `pnpm test` 和 `nest build` 用的那一份）。
- `enablePromptUseWorkspaceTsdk` 讓 VS Code 開啟專案時主動詢問要不要套用 —— 因為前者本身只是「提供選項」，不會自動生效。第一次開啟時要在跳出的通知按 **Allow**，或手動下 `Ctrl+Shift+P` → `TypeScript: Select TypeScript Version` → **Use Workspace Version**。

> **這也是換機接續的一部分。** 這個檔案進版控，所以兩台機器只要各自允許一次即可。

### 判讀原則：紅線不等於壞掉

編輯器的語言伺服器與 `tsc` / Jest 是三套獨立的 TypeScript 實例。真假以指令列為準：

```bash
node node_modules/typescript/lib/tsc.js --noEmit   # 無輸出 = 型別真的沒問題
```

若 `tsc` 是綠的而編輯器是紅的，**要修的是編輯器，不是程式碼**。特別是不要照錯誤訊息的建議去改 `tsconfig.json`：它會叫你加 `types: ["jest"]`，但那個欄位一出現，語意就從「自動載入 `@types/` 底下全部型別」變成「只載入列出的這幾個」，專案裡的 `@types/node`、`@types/express`、`@types/pg`、`@types/supertest` 會集體失效。
